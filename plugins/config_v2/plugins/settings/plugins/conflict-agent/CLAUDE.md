# conflict-agent

The **Ask an agent** button inside a config detail's conflict banner: opens the
standard `TaskDraftPopover` with the conflict already written out as the task's
first turn — which fields both sides changed, which only upstream moved, or (for
an invalid document) which schema issues it fails on.

**Why a separate plugin.** The config editor is generic; filing a task itself
would drag the whole tasks stack into every composition that ships Settings. So
`config_v2/settings` owns the `ConfigDetailSlots.ConflictAction` render slot and
hands contributions a plain `ConfigConflictContext` (descriptor, scope, kind,
per-field classification, pre-joined issues, the banner's button tint). The
editor names neither this plugin nor tasks.

**The insert is a request, not a seed.** `draftInsert(text)` mints a one-shot
request the popover applies once and *appends* to the persisted draft — shared
across the category and alive while the popover is closed. Minting it in render
would append the prompt to the user's draft merely because they opened the config
page, and again every re-render. So it is minted on the open transition only,
keyed on the prompt string as its own signature; `onSuccess` clears the mark so a
fresh draft is described again.

**The prompt** (`web/internal/build-prompt.ts`, pure + unit-tested) lists only
fields carrying a decision, clips any serialized value past 200 chars, and asks
for the `defineConfig` descriptor's recent history and a source-level fix. It
also states that the user's config layer is forked per worktree
(`~/.singularity/state/config/<worktree>/…`, spelled via `paths/display`) —
without that, an agent "fixes" the conflict in its own fork and reports success
on a change the user never receives.

The server half only registers the **Config** task category.
