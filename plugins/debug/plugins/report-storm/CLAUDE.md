# report-storm

The **`report-storm` report kind**: what a burst of alerts becomes once the
reports engine's cross-fingerprint fan-out ceiling collapses it
(`plugins/reports/server/internal/fan-out.ts`,
`research/2026-09-02-global-alert-fan-out-ceiling.md`).

Every other guard on the report path keys on the *fingerprint* (the `ON
CONFLICT` dedup, the velocity throttle, the bell cooldown, the duress shed's
first-N), so a burst spread **across** fingerprints engages none of them. The
ceiling counts how many distinct fingerprints of one kind may each raise their
own alert per window; past the budget they fold into one row of this kind
carrying the accounting — how many fingerprints, how many occurrences, over how
long, against which budget, with the loudest keys named inline.

## What is collapsed, and what is not

Only the **alert**. Per-occurrence detail is written before the report path
runs and is untouched (for `slow-op`: Debug → Slow Ops, every occurrence with
counts, `maxMs`, attribution, contention). This row carries the fact no single
occurrence could: *N unrelated operations degraded at the same instant*.

Safe even for kinds whose row is the only evidence (crash), because the budget
is spent by a fingerprint **newly alerting** (a repeat passes through with its
row, count and cooldown intact — repeats are not fan-out) and it **refills every
window** (anything persistent mints its own row within one window).

## `fanOutExempt` — the accounting must never collapse itself

The kind marks itself `fanOutExempt: true`. Without it, a long incident's
per-window rollups would themselves go past the ceiling, and the record of what
was collapsed would be the thing collapsed. Same reason `duress-shed` declares
`duressExempt`.

## Fingerprint

`report-storm:<collapsedKind>:<windowStartedAt>` — one row per (kind, window),
like `duress-shed`'s (buffer, episode). A 24 s burst yields one row; a
ten-minute stall yields ten, each with its own roster. No notification
cooldown: each window is already its own row.

## Why here and not in `reports`

Import direction, as with `duress-shed`. The engine files the rollup with a
plain `recordReport({ kind: "report-storm", data: { ...summary } })` and names
nothing else; the schema, fingerprint, task rendering and list view live here,
with a compile-time drift guard tying the payload schema to the engine's
`StormSummary`.

Tuning: `reports.fanOutPerWindow` (20), `reports.fanOutWindowMs` (60 s),
`reports.stormRosterMax` (50) in Settings → Config, read per admit. A kind may
**raise** its ceiling via `ReportKindSpec.meta.fanOutPerWindow`; there is no
spelling for removing one.
