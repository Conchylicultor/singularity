# op-store

The op log's DB read model. `op-log.jsonl` stays the one write path (CLI
processes write it and must never depend on the DB); this plugin folds it into
`op_log_ops`, one row per op, so surfaces read ops **live** instead of re-folding
the file per request. Plan: `research/2026-09-29-global-unified-op-status.md` §5.

A child of `op-log` rather than part of it: the CLI imports `op-log/server`
(profiler, `readOpenWait`), and tables there would pull the database module into
every CLI process. **Never import this plugin's `server` barrel from CLI code.**

## Collections (`core`)

| collection | rows | default window |
|---|---|---|
| `opsInFlight` (`op-store.in-flight`) | `closed_by IS NULL` — boot-preloaded | `requestedAt asc`, 200 (max 500) |
| `opsHistory` (`op-store.history`) | every stored op (30-day retention) | `requestedAt desc`, 500 (max 2000) |

Both serve `OpRowSchema`: the reducer's `OpFoldState` flattened onto columns plus
`closedWaitMs` (sum of the closed waits). The open wait's elapsed time is not
stored — it grows with `now`; compute it with
`liveTimes(opRowToFoldState(row), now)` from `op-log/core`.

**In flight is `closedBy === null`, not `completedAt === null`**: a reconciler
close has no real end, so its `completedAt` stays null. `closedBy` adds
`ingest-gap` to the reducer's `self` / `reconciler` (see below).

Readers: the op-status banner and chip (`opsInFlight`), the Ops Gantt and op
detail (`opsHistory`), and — server-side, as SQL over the exported `_opLogOps`
table — the stats/pushes charts. Nothing but the ingester and the worktree
reconciler writes the table.

## Ingester (`server/internal/ingest.ts`, `segments.ts`, `store.ts`)

Runs on **every serving backend**, into its own DB: a worktree DB is a fork of
main's, so it resumes from the cursor it inherited instead of freezing main's
in-flight rows at fork time.

- The cursor is `(inode, offset)` in `op_log_ingest_cursor`. The sink rotates by
  rename (`live → .1 → .2 → .3`), so only the inode can find the cursor's bytes
  after a rotation. `offset` is always just past a `\n`: a line still being
  appended is left for the next pass.
- A pass opens the live file and each rotation **newest first** and reads each
  inode off its fd — a file renamed between two opens is seen twice (deduped),
  never missed — then `planSegments` (pure) says which byte ranges to read, in
  order. Cursor not found (rotated past `.3`, or the dir replaced) or file
  shorter than the offset: `gap_at = now`, and the live file's last 16 MB is read.
  First boot (no cursor): the same 16 MB tail, no gap.
- Each ~1 MB chunk is one transaction under `pg_try_advisory_xact_lock`: check the
  cursor is still where the pass started, fold the lines into the touched rows
  (`applyOpEvent`), upsert, advance the cursor. Busy lock / moved cursor ends the
  pass without error. A headless op (its `requested` clipped by the seed tail) is
  not stored until its self-contained terminal arrives.
- Enum values unknown to this backend's code (a worktree on newer code writing
  the shared log) are mapped to a fallback with a warning rather than wedging
  ingest on one line.

Boot order (`onReady`): drain → reconcile, awaited; then a `@parcel/watcher`
subscription on the op-log dir (`op-log.jsonl*`) and a 30 s reconcile tick, each
scheduling one serialized pass (drain → reconcile).

## Reconciler (`server/internal/reconcile.ts`)

An op hard-killed mid-flight never writes its terminal. After each drain, the
in-flight rows whose process is gone are closed:

- **main** appends `completed{by:"reconciler"}` to the **file** — every DB, and
  `await`, then learns of it the same way, by reading the log;
- a **worktree** backend never writes the log. It closes a row locally
  (`closed_by: "ingest-gap"`) only when its ingest had a gap and the row predates
  it: main's terminal for that op may be in the bytes it never read.

Liveness (`isOpLive`) is the op's per-op flocked marker
(`worktrees/<opSlug>/ops/<opId>.json`, `infra/worktree`'s `probeWorktreeOp`):
locked → live, unlocked → dead — exact, and immune to pid reuse. Every writer
publishes the marker before `requested` and releases it after appending
`completed`, so a logged op with no locked marker really died. Only an op with
no per-op marker at all (a CLI from before them) falls back, until phase 5: a
legacy marker naming the `opId`, else the v2 op's own `pid` alive, else (legacy
op, no pid) any live marker in the op's worktree. A SIGKILL leaves no
filesystem event; the 30 s tick is what notices it.
