# node

The Lexical-valued half of the inline-token primitive: `defineInlineTokenNode`
(the `DecoratorNode` subclass factory), the two caret/line materializers
(`$insertTokenizedText`, `$tokenizedLineNodes`), and the registry-driven
`TokenPastePlugin`.

## Why this is a separate plugin

Not modularity — **loadability**.

`@plugins/page/plugins/editor/server` imports `tokenExtension` from the parent
barrel. drizzle-kit loads every schema-glob file
(`server/**/internal/{tables,schema}.ts`) with a synchronous `require()` when it
generates migrations, and several page schema files reach that editor barrel.
`lexical` has a top-level-`await` module in its graph, so it cannot be required
synchronously — and a module graph is only as synchronous as its worst edge.

When `defineInlineTokenNode` lived in the parent, importing the parent's barrel
for `tokenExtension` alone evaluated the whole barrel, which pulled `lexical` in
as a value. Nine schema files stopped loading, and drizzle-kit reported success
with those tables silently absent from migration generation. The
`schema-files-loadable` check turns that silence into a build failure; this split
is what makes the check pass.

So the line between the two plugins is exactly one question: **does the module
need `lexical` at RUNTIME?**

- `import type { … } from "lexical"` → parent. Type imports emit nothing.
- `DecoratorNode`, `$createTextNode`, `$getSelection`, any `$…` function → here.

## Rules

- **The dependency runs one way: here → parent.** The parent imports nothing
  from this plugin, which is also what keeps the pair out of an import cycle.
  That is why `token-scan.test.ts` lives here rather than beside `token-scan.ts`
  — it exercises the scan through real token families, and a real family can only
  come from `defineInlineTokenNode`.
- **The parent must never re-export these values.** It would read as a
  convenience and would restore the runtime `lexical` edge. It is also forbidden
  outright by the no-cross-plugin-re-export boundary rule.
- **The design of the token family itself is documented in the parent**, on the
  types (`token-extension/core/inline-token-types.ts`) and in its `CLAUDE.md`:
  why `fields` is a list of names, why there are two descriptor types, and why
  the headless class and its decorated twin share one hierarchy. This plugin owns
  the class, not the contract.

## The paste handler

`TokenPastePlugin` sits here because it calls `$insertTokenizedText`. It gates on
the parent's `hasToken`, declines a clipboard carrying
`application/x-lexical-editor` (an intra-app copy already holds materialized
nodes, and re-parsing it from `text/plain` would drop the marks around the
token), and registers at `COMMAND_PRIORITY_LOW` — below the file/forest handlers,
above the default insert.
