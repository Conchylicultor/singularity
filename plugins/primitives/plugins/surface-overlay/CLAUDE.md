# surface-overlay

The sanctioned home for a **surface-filling overlay** — a box that covers the
whole app tab surface (everything below the tab bar and right of the app rail)
while the app chrome around it stays visible and usable.

```tsx
<SurfaceOverlay className="bg-background" role="dialog" aria-modal="true">
  {stage}
</SurfaceOverlay>
```

## Why this primitive exists

A pane that wants to fill its tab is never rendered at the tab's outer box. It
is somewhere down a pane tree: a Miller column, a scroll body, a card. Writing
`absolute inset-0` there fills *that column*, and no combination of classes at
the call site reaches past an ancestor that is `relative` or `overflow-hidden`.

The only other thing that escapes is `<ViewportOverlay>` — and it escapes too
far, covering the rail and the tab bar with it. So "fill my tab, keep the
chrome" had no spelling at all. This primitive is that spelling.

## The two halves

- **`<SurfaceOverlayHost>`** declares *"overlays may fill this box"*. It is a
  plain `relative size-full` box plus a context carrying its own **ref object**
  (not the element) — a stable value for the host's whole life, so mounting a
  host never re-renders its subtree. `apps-core/tab-surface` mounts exactly one
  per app tab, which is why an overlay lands in the right box under every
  placement (docked / floating window / solo): each hands the tab a different
  outer box, and the host is inside all of them.
- **`<SurfaceOverlay>`** portals into the nearest host and applies
  `absolute inset-0` + a z-layer. Props mirror `<ViewportOverlay>`: `layer`
  (`InTreeLayer`, default `"overlay"`), `className`, and a permissive
  passthrough for `role` / `aria-*` / `onClick` / `style`.

`layer` is an **in-tree** layer, not a portaled one — deliberately. The overlay
must out-stack the pane chrome it covers, but stay under `popover`/`draw`/`max`,
so a dialog or dropdown opened from inside it still paints above it.

## How it differs from its neighbours

| | fills | escapes its parent |
|---|---|---|
| `<Layer>` / `<Overlay>` | its own parent box | no |
| **`<SurfaceOverlay>`** | the app tab's surface | yes, up to the host |
| `<ViewportOverlay>` | the browser window | yes, all the way to `<body>` |

Pick by what the user should still be able to click. A modal scrim or a
fullscreen mode wants the window; anything the user should be able to leave by
switching tabs wants the surface.

## A missing host throws

There is no viewport fallback and no silent no-op. "Covers the surface" and
"covers the window" are different pictures, and a primitive that quietly
delivers the second when the first is unavailable produces a bug that only shows
up in a screenshot. The error names both alternatives, so the fix arrives with
it.

## The container is minted once

React reconciles a portal by the identity of its **container**, so a container
that changes — or a portal put behind a condition — deletes the subtree and
builds a new one: an `<iframe>` inside reloads, an uncommitted edit is gone. So
`<SurfaceOverlay>` mints one `<div style="display: contents">` on first render
and portals into that forever; the host adoption is a plain `appendChild` in a
**layout** effect (before paint, so the overlay never flashes detached).

`display: contents` is load-bearing: the node generates no box, so it is neither
a containing block nor a flex/grid item, and the portaled root's
`absolute inset-0` resolves against the *host's* `relative` box exactly as if it
had been rendered there. The same idiom — and the same reason — as
`primitives/adaptive-bar`'s `PortaledBarItem`; the `no-portal-toggle` rule
(`css/viewport-overlay/lint`) bans the conditional shape.
