# usage-rank

Generic "most-used first" ordering for any set of things named by a
`(namespace, key)` pair — prompt templates, launch prompts, preprompts, command
palette entries. Consumers call `recordUsage(namespace, key)` on use and
`useUsageOrder(namespace, keys, resnapshotKey)` at render; nothing else is
needed, and the primitive knows nothing about what it ranks.

Design: [`research/2026-08-06-global-usage-rank-most-used-ordering.md`](../../../../research/2026-08-06-global-usage-rank-most-used-ordering.md).

## Why a DB table and not config

Usage counts cannot live in config: `forkConfig` copies the config dir into each
new worktree and never syncs back, so counts would fragment across worktrees;
and `listField` treats array position as canonical, so "reordering" in config
means rewriting the authored array. Config stays the AUTHORED order; usage order
is derived at render, and the authored order remains the tie-break for anything
never used.

## Frecency, not counts

Raw counts ossify — a template hammered last year outranks a weekly one forever.
Each use decays the stored score to now and adds 1
(`score * 0.5^(Δt / HALF_LIFE)+ 1`, `HALF_LIFE` = 30 days), and every
comparison decays again to the reader's own `now` (`decayedScore`). Both are
O(1): one row per key, no event log. The whole write is a single
`ON CONFLICT DO UPDATE`, so concurrent uses cannot race.

## The freeze is the feature

`useUsageOrder` snapshots the order exactly ONCE per `(resnapshotKey, key-set)`
— at the first settled read — and ignores every later live push into the same
window. Chips that re-order on their own click are a guessing game; muscle
memory only pays off if the strip holds still while the user works. Habits
surface at the next `resnapshotKey` (the consumer decides what a fresh context
is: a conversation switch, a dialog open).

First paint is seeded from a `persistent-draft` cache keyed by namespace,
because an id-set read cannot be preloaded and hydrates one round-trip after
mount — without the seed the strip would visibly re-sort on every open.

## Bounded by construction

`usageStats` (core) is a `liveCollection` — `{ row: UsageStatSchema, id:
"usageKey" }` plus a small window (`namespace` filterable, `lastUsedAt`
sortable, default limit 20, max 100) — served by `serveCollection(usageStats,
{ from: _usageStats })`. The window exists for `useRecentUsage(namespace,
limit)`: a namespace's most recently used keys, newest first, for a caller with
no candidate set to rank (an emoji picker's Recent row, out of every emoji). `useUsageOrder` reads
it with `useLive(usageStats, { ids })`, one tuple for the whole visible set, and
stamps its frozen window with the same `usageStats.rows.point.encode` the read
subscribes with. A read costs O(subscribed ids) and a write recomputes only the
tuples containing the touched key (the `:rows` point routing).
`usageKey(namespace, key)` is the only place the two halves are joined — a
composite PK is not an option, since the collection's id must be one column.

Growth is bounded by a nightly `defineRetention` sweep on `lastUsedAt` older
than a year: nothing else deletes the row for a template the user removed, since
the ranked things are config entries with no parent row to cascade from.

- Description: Frecency usage ranking for any (namespace, key) set: recordUsage() fires one atomic decay-and-increment, useUsageOrder() returns the most-used-first order — one coalesced id-set subscription, frozen per context so chips never move under the cursor, seeded from a local cache so the first paint does not re-sort — and useRecentUsage() lists a namespace's most recently used keys (a bounded window), for a Recent row with no candidate set to rank.
