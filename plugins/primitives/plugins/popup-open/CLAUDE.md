# popup-open

A typed **"is a popup open inside me"** signal. A region wraps itself in
`PopupOpenScope` and gets a boolean; every popup opened under it publishes
through `useReportPopupOpen`.

```tsx
<PopupOpenScope>
  {(popupOpen) => (
    <Stack className={cn(revealClasses, popupOpen && "opacity-100 pointer-events-auto")}>
      {actions}
    </Stack>
  )}
</PopupOpenScope>
```

First consumer: `row-actions`, whose hover-revealed cluster must stay revealed
while its own dropdown is open — the trigger is the open menu's anchor.

## Why a signal, not a CSS `:has()` rule

The held state used to be a Tailwind selector naming a popup library's attribute
contract (`has-[[data-popup-open]]`; before that the Radix spelling
`has-data-[state=open]`, which base-ui never sets — so it never fired and nobody
noticed for months). A selector naming another library's attribute is
unverifiable by any type system: it fails silently the day the library renames
it. ui-kit is the one place that knows base-ui's open state; the boolean crossing
that boundary is typed.

## Why it imports nothing

`ui-kit` imports this plugin and sits at the bottom of the DAG, so this plugin
must import **only `react`** — not `cn`, nothing — or the `ui-kit → popup-open`
edge closes a cycle `plugin-boundaries` rejects (type-only imports count as
edges). Same precedent as `overlay-boundary`.

## Semantics

- **Counted, not latched.** Two popups open under one scope hold it until *both*
  close.
- **Release on unmount.** Registration is an effect subscription, release is its
  cleanup — so closing and unmounting-while-open take the same path. An unmount
  that skipped the release would latch its scope open forever.
- **Innermost scope wins.** A popup reports to its nearest scope only.
- **No Provider ⇒ no-op** (the `sync-status` tolerance), so a popup outside any
  scope neither throws nor reports.
- **Tooltips are excluded**, deliberately: a tooltip holding a row's cluster open
  is noise, not intent. Only `DropdownMenu`, `Popover` and `Select` publish.
