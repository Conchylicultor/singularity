# announce

Say something to a screen reader from anywhere:

```ts
import { announce } from "@plugins/primitives/plugins/announce/web";

announce("All 9 blocks selected");
announce("Delete failed", { assertive: true });
```

`announce` is a plain function, not a hook — callable from an event handler, a
store, a reducer, anywhere. The two live regions it writes into are mounted once
at `Core.Root` by this plugin's `AnnouncerHost`. With no host mounted the call is
a silent no-op and never throws, the same degradation contract `showToast` has.

## The one rule: announce a state change with NO native carrier

An announcement is for a change the user can otherwise only perceive by looking
at it — a highlight, a count, a colour. If the control already carries the state
in its own semantics, the screen reader **already says it**, and announcing it
too means the user hears it twice:

| Don't announce | Because the control already says it |
| --- | --- |
| "Checked" after a checkbox toggle | the checkbox's own checked state |
| "Pressed" after a toggle button | `aria-pressed` |
| "Expanded" after a disclosure | `aria-expanded` |
| "Selected" on a `role="option"` row | `aria-selected` |
| Anything a focus move already reads | the newly focused element's name and role |

Reach for `announce` only after establishing that no native carrier exists. The
first consumer is the page editor's block selection: its rows contain
`contenteditable` editing hosts, so no role that supports `aria-selected` can be
stamped on them, and selection is therefore conveyed by colour alone. That is
the shape that earns an announcement.

Before adding a call, ask in this order:

1. Can the state live on the control as a native ARIA property? Do that instead.
2. Is the change already narrated by a focus move? Then say nothing.
3. Otherwise announce it — once, at the one place the state actually changes.

Announce at the mutation site, never in render: a render-time announcement fires
again on every unrelated re-render and will repeat itself into the user's ear.

## Polite vs assertive

Default to polite. `{ assertive: true }` interrupts whatever the screen reader
is currently reading, including the user's own navigation — reserve it for
failures and destructive outcomes. Two channels, two regions, independent: an
interruption never clears the polite text.

## Why an identical message re-fires without a timer

A live region speaks when its **text changes**. Selecting the same block twice
yields the same sentence, and an unchanged region is silent — exactly when the
user asked for confirmation.

The usual workaround is to blank the region on a timer and rewrite it. This
plugin does not, and not only because the repo bans timers: a write of the text
already there lands as that text plus a **trailing space**, and the write after
that drops the space again. The rendered string differs every time, the spoken
string never does (trailing whitespace is not read aloud), and nothing is
scheduled.

## Why the host is permanently mounted and empty

A live region must be in the DOM *before* its content changes for assistive tech
to notice at all. A region that arrives in the same commit as its first message
presents no change and is silently skipped — the single most common reason an
`aria-live` "does not work". Both regions are at `Core.Root`, in the document
from first paint, so every write is a change.

The host renders nothing visible: two `sr-only` divs, which are
`position: absolute` and clipped, so they occupy no space and perturb no rect
that layout, drag or marquee code measures.

## Why the store is page-global

A screen reader has one speech queue for the document, so per-surface announcers
would not isolate anything — they would both talk. One host, one queue, the same
shape as the toast stack.
