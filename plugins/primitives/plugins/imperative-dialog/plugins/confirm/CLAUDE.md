# confirm

`confirmDialog(opts)` — the destructive-confirm helper. A thin policy layer over
`openDialog`: it opens the body at `{ size: "sm" }` so it inherits the unified
panel + padding from the host's `DialogContent`, and the body is a bare
`<Stack gap="md">` (title + description + optional `children` + inline error +
Cancel/Confirm row) with **no `Surface`/width of its own**. That the panel chrome
lives in `DialogContent` is the whole reason this can be a ~30-line helper.

## Fire-and-forget — `void confirmDialog(...)`, never `await` in an onClick

`confirmDialog` returns `Promise<boolean>` that resolves when the dialog closes
(`true` iff `onConfirm` completed, `false` on Cancel / Escape / backdrop). Call
it fire-and-forget: `void confirmDialog({ ... })`. Do **not** `await` it inside a
`Button`'s `onClick` — `Button` auto-pends off any thenable its handler returns,
so awaiting the confirm would leave the *launching* button spinning for the
entire lifetime of the dialog. The boolean return exists for the rare caller that
genuinely needs to branch after the fact, not for the common path.

## `onConfirm` owns the follow-up

The destructive action AND anything that must happen only on success go inside
`onConfirm`. It runs once, and only if the user confirms; on Cancel/Escape it
never fires. So navigate-away / toast-success / refetch belong in `onConfirm`,
not after the `confirmDialog` call — code after the call runs on cancel too.

## Error policy — stay open, show inline, retry

If `onConfirm` rejects, the dialog stays **open**, renders
`getEndpointErrorMessage(err)` inline via `<Text tone="destructive">`, and
re-enables the confirm button — so the visible message *is* the retry affordance.
The body owns this `try/catch` because `Button` cannot: `Button` attaches only
`.finally()` to the thenable it auto-pends on, so a rejection handed back to it
would escape as an unhandled rejection. `runConfirm` therefore always resolves.

Two decisions key on different things, deliberately:

- **Stay-open** keys on *any* failure — every error keeps the dialog up so the
  user sees it and can retry. It does not care what kind of error it is.
- **Re-filing the crash** keys on `EndpointError`: a non-`EndpointError` is
  re-thrown via `void Promise.reject(err)` to reach the crash reporter, but an
  `EndpointError` was already reported to `endpointErrorSink` by `fetchEndpoint`,
  so it is only *shown* here, never double-filed.

## No `destructive` flag — the affirmative is the danger

The confirm button is always `variant="destructive"`. Every imperative confirm in
this repo guards a destructive/irreversible action; there is no neutral
"Save changes?" case. A genuinely neutral confirm belongs to an inline `<Dialog>`
with a primary button, not this helper. Add a flag only when a real neutral case
appears (YAGNI).
