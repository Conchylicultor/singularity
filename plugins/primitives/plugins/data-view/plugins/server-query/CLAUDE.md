# server-query

The server half of a **server-delegated DataView** over the one filter language
(`network/live/plugins/filter`, design
`research/2026-09-25-global-unified-filter-language.md`). Names no field type
and consults no field registry: the DataView host lowers the view's filter AND
its search box into one canonical `Filter` in the browser, and this plugin only
decodes and compiles it.

## One declaration, three readers

A source declares what its server can filter ONCE, in its own `core/`:

```ts
// core/ — column → filter-language domain; the searchable text columns
export const THINGS_FILTERABLE = { title: liveText(), createdAt: liveInstant() };
export const THINGS_SEARCHABLE = ["title"] as const;
```

1. **web** — `dataSource={{ filterable: THINGS_FILTERABLE, searchable:
   THINGS_SEARCHABLE, … }}`: the Filter control offers exactly these fields
   (and only when the field's operator set lowers over the declared domain).
2. **server column map** — `bindColumns(THINGS_FILTERABLE, { title: { col:
   t.title }, … })`: every declared column must be bound (`tsc`), and each
   binding's `domain` is COPIED from the declaration, so the two cannot drift.
3. **handler decode** — `decodeFilterBody(body.filter, filterable)` (or
   `augmentServerQuery`, which decodes against the base map plus every
   augmentor's offered columns): STRICT, so an unknown column, a wrong-domain op,
   a bad operand, an over-bound tree or a non-canonical spelling is a **400**
   naming the problem. Nothing is dropped fail-soft anymore.

`compileWhere(filter, columnMap)` then compiles through the language's
`filterSql`; a column the map does not bind throws (the decode already refused
it, so reaching that is a bug).

## A filter op is handed a target, never a column

`compileWhere` hands the language's `filterSql` each column **rendered as a plain
`SQL` expression** — `` sql`${binding.col}` `` — rather than the column object.

That is not a formality. A drizzle column IS a `DriverValueEncoder`, so every
operand bound against one (`eq`, `inArray`, …) is run through the column's
write-side schema. On a decoded column (`database/sql-column`) that schema is
real: a strict one throws `SqlColumnError` and takes the whole list down, and a
**tolerant** one silently rewrites the operand — `model is-any-of ["typo"]`
normalizes to the default model and returns every row that holds it, as if the
user had asked for them. A comparison operand is not a stored value; the
language binds each operand as a param cast to its DOMAIN's SQL type
(`$1::text`, `$1::float8`, `$1::text[]` …), never through an encoder.

A `text`-domain target is relabelled `(col)::text`, so a text op reads the same
over a `uuid`, `varchar` or Postgres-enum column as over `text` (`uuid = text`
has no operator). On a `text` column the relabel is a no-op the planner sees
through. `ColumnBinding.col` keeps the real column for the keyset seek and
`ORDER BY`, which only ever interpolate it.

Design: `research/2026-08-27-global-filter-operand-domain.md`.

## Query augmentors (custom columns)

`DataViewServer.QueryAugmentor` is the server twin of the web global
`DataViewSlots.FieldExtension` slot. An augmentor OFFERS columns — each an
`AugmentedColumn` (`binding` with its domain + the `join` that materializes it);
`augmentServerQuery` decodes the filter against base ∪ offered, then joins and
binds only the offered columns the filter or sort names, and projects the
augmented sort keys for the keyset cursor. The web side offers a global
field-extension field for filtering on a server-delegated source for the same
reason: its server twin binds it.
