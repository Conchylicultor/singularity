# server-query

## A filter builder is handed a target, never a column

`compileWhere` resolves each rule to a `(fieldType, operator)` SQL builder and
hands it **the field's column rendered as a plain `SQL` expression** —
`` sql`${binding.col}` `` — rather than the column object.

That is not a formality. A drizzle column IS a `DriverValueEncoder`, so every
operand bound against one (`eq`, `inArray`, …) is run through the column's
write-side schema. On a decoded column (`database/sql-column`) that schema is
real: a strict one throws `SqlColumnError` and takes the whole list down, and a
**tolerant** one silently rewrites the operand — `model is-any-of ["typo"]`
normalizes to the default model and returns every row that holds it, as if the
user had asked for them.

A comparison operand is not a stored value. The encoder exists to protect what a
column *holds*; comparing a column against a value it can never hold is how you
say "nothing matches". So the operand never meets the encoder, because the
builder never receives one — `tsc` enforces it, since `inArray(target, …)` does
not accept an `SQL`.

Nothing else changes. An `SQL` chunk flattens inside a `sql` template before
drizzle's parenthesising `isSQLWrapper` branch is reached, so the rendered
statement, its `$n` params and its plan are **textually identical** to
interpolating the column itself. Only the param encoder differs.

Consequences for a builder: bind your own operands (never interpolate them), and
do not reach for column metadata — `col.name` / `col.enumValues` are not there.
`ColumnBinding.col` keeps the real column for the keyset seek and `ORDER BY`,
which only ever interpolate it.
