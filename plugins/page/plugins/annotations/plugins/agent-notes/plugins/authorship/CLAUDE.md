# authorship

**Which conversations wrote this agent-notes card**, and the popover that shows
them.

A sub-plugin of [`agent-notes`](../../CLAUDE.md) rather than part of the MCP tool
that first writes these cards, because the record is about the CARD, not about
MCP: a second writer (a job filing a summary, an in-app "ask an agent about this
page") stamps through `recordAgentNotesAuthor` instead of inventing a second
provenance store. The tool layer owns only *which* conversation id — it is the
only place that knows one.

Design: [`research/2026-08-05-page-agent-notes-mcp-access.md`](../../../../../../../../research/2026-08-05-page-agent-notes-mcp-access.md),
Delta 4.

## A link table, not an id array on a 1:1 extension

The design sketch proposed `defineExtension(_blocks, "agent_authors",
{ conversationIds: text().array() })`. This ships
`page_blocks_agent_authors(block_id, conversation_id, created_at)` keyed on the
pair instead. **The reason is concurrency, not taste**: an array append is a
read-modify-write, so two conversations appending to one card in the same window
both read the pre-write array and the second silently drops the first's id —
losing exactly the fact the record exists to keep. A child table makes it
`INSERT … ON CONFLICT DO NOTHING`: dedupe is the primary key, so
`recordAgentNotesAuthor` cannot be called wrongly. (Secondarily, the relation is
1:N and `entity-extensions` is a 1:1 primitive — a set is not a field.)

**`conversation_id` carries no foreign key**, the same call
[`page/prompt/link`](../../../../../prompt/plugins/link/CLAUDE.md) makes for its
`blockId`: the row says *an agent wrote this card*, which stays true after the
conversation is deleted. A CASCADE would erase it and leave the card
indistinguishable from human prose. The cost is a possibly-dangling id.

Growth is bounded by the `block_id` FK cascade — `markCascadeBounded` asserts it
at module eval (boot-fatal). It sits in its own module because a barrel may hold
no statements and `tables.ts` must stay importable by drizzle-kit's schema
loader, which cannot pull in retention's `db`/`jobs` closure.

## The read is point-membership, so only an open card pays

`agentNotesAuthorsResource` is keyed by `{ blockId }` — a FULL load is one card's
handful of authors — copying `page-block-doc`, not the legacy unbounded
`queryResource` collection form.

`identityTable` scopes recompute but delivers **no per-row scoped refill**: the
change-feed attributes affected ids only for a single-column PK, and this key is
composite, so a stamp arrives as FULL-for-table. Correct, and cheap (one indexed
single-block query, written once per agent note). A surrogate `id` would buy the
scoping back at the price of a meaningless key plus a separate unique index to
keep `ON CONFLICT` working. Hence no `ctx.affectedIds` branch — there is never
one to serve.

`useAgentNotesAuthors` re-sorts client-side: a keyed resource merges deltas by
key, so array order after a live update is the merge's, not the loader's
`ORDER BY`.

## The popover, and the one thing it cannot know

`AgentNotesAuthors` renders one row per contributing conversation, each opening
`conversationPane` (no cycle: nothing under `plugins/conversations/` imports
`@plugins/page/`). Transient chrome, not a DataView — a handful of rows off a
`size-5` glyph with no search/sort/filter to earn.

`useConversationById` returns `null` both while its fetch for an older
conversation is in flight and when the conversation is genuinely gone, and those
are **indistinguishable** from here. So an unresolved row falls back to the raw
id and stays clickable rather than claiming "deleted" for what is usually one
frame of loading. Consequence: clicking a truly-deleted conversation opens a pane
that spins forever — `ConversationView` has no not-found state, a pre-existing
gap in that plugin.
