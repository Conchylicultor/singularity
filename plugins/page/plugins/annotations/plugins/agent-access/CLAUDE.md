# agent-access

The **agent-facing surface of a page**: four MCP tools over
[`page/markdown-apply`](../../../markdown-apply/CLAUDE.md)'s engine.

```
read_page(blockId)                                   → subtree markdown, human-audience subtrees pruned
append_agent_notes(blockId, markdown)                → mints an <agent-notes> card, returns its id
write_agent_notes(noteId, markdown)                  → merge-apply within that card
edit_agent_notes(noteId, oldString, newString, …)    → same, localized (the Edit-tool contract)
```

It lives under `annotations` because it is the filter over THIS family: both
"withhold `/private`" and "own `<agent-notes>`" are statements about the
audience-scoped family, not about markdown. The engine stays audience-agnostic —
it takes a root and a row filter and never learns what an audience is.

## Addressing is the authorization

Writes are not restricted by validating the patch they produce. They are
restricted by what an agent can **name**: a write tool accepts only a block whose
type is `agent-notes`, and the engine is scoped to that block's subtree. An agent
cannot rewrite a paragraph because there is no tool that takes a paragraph's id.

That is also what makes redaction a **read-only** concern. The trap it avoids:
strip a private card on read, and a write that diffs the edited document against
the FULL stored forest reads every stripped card as a deletion, so each one would
need its rank re-derived from surviving neighbours after planning. A private card
cannot legitimately live inside an agent-notes card, so the write scope never
contains redacted content — and the one residual case (a user drags a private
card in) is a loud refusal in `assertWritableNote`, never a silent destruction.

The four rules are stated once, in `server/internal/policy.ts`. All of them
enumerate the family generically off `Editor.BlockData` (`audience === "human"`)
and never name a type, so a fifth annotation costs this plugin zero edits. The
set is read at CALL time: a snapshot taken before `collectContributions` degrades
to "redact nothing", and that failure is silent and unrecoverable.

## `append_agent_notes` does not go through the planner

It builds the patch directly — one create for the card, one per parsed child,
ranked after `blockId`'s last child, through `applyPageBlockPatch`. **Creates-only
is structurally incapable of touching anything else**, which a diff-based append
would need a guard to promise. It still parses with the engine's own
`serverMarkdownContext()`, so what an agent writes and what it reads back are one
dialect.

Two ranks from the same floor collide at the `(parent_id, rank)` unique index —
loud, at the DB, which is the right answer for two concurrent appends.

## `write_page` / `edit_page` are gone

Whole-page markdown editing shipped with the engine and is deliberately removed:
no agent-reachable tool writes a page's prose. Recorded so the loss reads as a
decision rather than a regression. The engine is untouched, so they could return
behind a per-page, human-set opt-in.

## Stated bounds

- **Absence is visible.** A read shows a gap where a private card was — no
  marker, by choice — so an agent may re-derive something the author already
  noted privately. `read_page`'s description says so, which is the mitigation.
- **A human's edits inside a notes card can be overwritten** by the next
  `write_agent_notes`. Write semantics; `edit_agent_notes` is the mitigation.
- `read_page` loads the scope twice (once to decide about the id, once inside the
  engine to serialize it). Deliberate: the policy question must be answered
  before the id is handed over as a root.
