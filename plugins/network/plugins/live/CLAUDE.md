# live

The unified live-resource API — design in
`research/2026-09-25-global-unified-live-resource-api.md`. **The default for a new
DB-backed collection.**

## Usage

```ts
// core/ (browser-safe) — declare once
export const eventSources = liveCollection("events.sources", {
  row: EventSourceSchema,
  id: "id",
  filterable: { status: z.enum(SOURCE_STATUSES), enabled: z.boolean() },
  sortable: ["createdAt", "name"],
  default: { orderBy: [["createdAt", "desc"]], limit: 100 },
  maxLimit: 500,
});

// server/ — serve it; spread both Resource.Declare entries
export const eventSourcesServed = serveCollection(eventSources, { from: _eventSources });
// contributions: [...eventSourcesServed.declare]

// web/ — read it
useLive(eventSources);                                                // default window
useLive(eventSources, { where: { enabled: true }, orderBy: [["name", "asc"]], limit: 50 });
useLive(eventSources, { ids: visibleIds });                           // point set
useLiveRow(eventSources, sourceId);                                   // one row
```

- **Declare.** The key is a positional string literal (the build scanners read it).
  One declaration mints two resources — `key` (window) and `key:rows` (point) —
  and both show in the docs. Bounded by construction: `default.limit` and
  `maxLimit` are required, and there is no unbounded spelling.
- **Serve.** `serveCollection(c, { from })` binds every filterable / sortable
  name (and `id`) to a column of `from` (a `PgTable` or an Entity) BY PROPERTY
  NAME — type-checked: a name that is not a column fails in `tsc` until it is
  given in `columns: { name: table.col }`. It compiles both resources through
  `windowQueryResource`: the window decodes `where` / `order` per subscription
  tuple (filters through the op table's SQL half, over the column RENDERED as
  SQL, never the column object) with every sortable column in the order
  signature; the point sibling is `point: { by: <id column> }`, no filter.
  `compileCollection` is the same derivation without registering (for tests).
  Hand-written loaders are out of scope for now — keep those on
  `windowQueryResource` / `defineResource`.
- **Read — `useLive(c, query?)`.** A window query returns `ResourceResult<Row[]>`
  whose settled arm adds `canGrow` (`rows.length === limit && limit < maxLimit`),
  `growing` and `loadMore()` (grow by one default page, clamped to `maxLimit`).
  While a grown window loads the hook stays SETTLED on the previous rows
  (`growing: true`) — the previous tuple stays subscribed only for that moment —
  so `if (pending)` never flashes over a list that already rendered. Each grow
  step is a new tuple; that is fine up to `maxLimit`. An `{ ids }` query reads
  the point sibling: `ResourceResult<Row[]>`, no paging fields. The query is
  identified by its canonical encoding, so inline object literals are fine.
- **Read — `useLiveRow(c, id)`.** `{ pending: true; error; stale? } |
  { pending: false; found: true; row } | { pending: false; found: false }`.
  A point read: it ignores every filter and window bound, so `found: false`
  means the row does not exist — never "outside the window". A nullable id is
  not supported yet (it needs an `enabled` option on `useResource`).
- `useLive` is on `live-state/no-pending-data-collapse`'s watched list;
  `useLiveRow` has no `data` to collapse.

## Internals

- `core/` (browser-safe): `liveCollection(key, { row, id, filterable, sortable, default, maxLimit })`
  mints two resources from one declaration — `key` (window membership) and
  `` `${key}:rows` `` (point membership). The window descriptor carries the query
  codec: `window.encode(query)` → wire params, `window.decode(params)` →
  `{ limit, where, orderBy }`.
- The filter language (`LiveWhere`) is AND across declared columns; each column
  takes a plain value (= `eq`) or exactly one of `eq ne in notIn gt gte lt lte isNull`.
  No OR, no time-relative ops, `in`/`notIn` capped at 100.
- The op table is split by runtime but paired by type: `core/` holds each op's
  operand kind and in-memory `test`, `server/` holds its `sql(target, operand)`
  keyed by the same `LiveOpId` (a missing or extra op is a tsc error). Null
  semantics are Postgres's: a NULL value fails every op but `isNull`.
  `server/internal/op-parity.test.ts` runs every op both ways against a real
  Postgres and asserts identical answers.
- String ordering is code-point order in memory; in SQL it is the cluster's
  collation, which is `C` (initdb `--no-locale`) — the parity suite pins it.

## Wire params

`{ limit: string; where?: string; order?: string }` — `where` / `order` are
canonical JSON present only when they differ from the default, so the default
window stays byte-identical `{ limit: "100" }`. Decode is STRICT: it re-encodes
and throws unless the input was already canonical, so one logical query can
never name two subscriptions.
