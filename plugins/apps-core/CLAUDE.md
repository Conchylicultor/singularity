# apps-core

## An app is authored once, and `Apps.App` takes it whole

An app's id, base path, display name and icon key live in exactly one place:
`defineApp({ … })` in that app's shell `core/app.ts`. The web barrel hands the
resulting `AppRef` over whole:

```ts
Apps.App({ app: pagesApp, icon: mdAppIcon(MdDescription), component: PagesLayout })
```

The contribution restates **nothing**: there is no `id`, `path` or `tooltip`
prop, so drift has no spelling. `Apps.App` is a hand-declared callable (not a
bare `defineRenderSlot`) purely so it can derive the framework-required
contribution id from `app.id`. Consumers read `entry.app.name` /
`entry.app.basePath`; a lower layer that needs an app's name reads it off the
`AppRef` it already holds, never by looking into `apps-core`.

## `apps-core` is the desktop — a meta-app with one data dir

The frame every app renders inside (rail, tab bar, surface modes, the floating
desktop's wallpaper) is itself treated as an app: the **desktop**. It has no
`Apps.App` entry and no route, so its identity is a plain
`desktopApp = { id: "desktop" }` (`core/app.ts`), not a `defineApp` `AppRef`.

What the identity buys is the same data rule every app follows: the desktop owns
exactly ONE data dir, `apps/desktop`, declared here in `data-dirs/index.ts`
(`desktopDir = defineAppDataDir(desktopApp, { owner: "apps-core", … })`).
`apps-core` is registered as the desktop's root in the paths plugin's closed
meta-app table, which is what lets `paths:app-data-dirs` accept an `apps/*` dir
declared outside `plugins/apps/`. A sub-plugin with durable files takes an area
inside it — the wallpaper store is `desktopDir.subdir("wallpaper")` — and never
declares an `apps/*` dir of its own. The wallpaper used to be exactly that
(`apps/wallpaper`); `desktopDir`'s `movedFrom` entry moves it to
`apps/desktop/wallpaper/` the first time main (the host's singleton process)
resolves the path, and leaves a symlink at the old name; every other process
keeps reading the old location until then.
