# serve-app

`./singularity serve-app --web <dist>` — boot a packaged app's whole runtime
(gateway + embedded Postgres + the app's own backend) in one process, under an
isolated data root, and stay up serving it.

This is a **release** entry point, not a development one. It refuses to run
without `SINGULARITY_DIR` set in its environment, because that variable re-roots
the entire install: unset, `dataRoot()` answers with the developer's
`~/.singularity` and the command would quietly pour a release cluster, spec and
registry into it. `--web` is required for the same reason — every derivable dist
path resolves inside the isolated root, which holds no dist because nothing ever
built into it.

## The one detachable command

`bin/index.ts` arms the orphan guard on every invocation: a CLI process exits
140 shortly after the shell that launched it dies, so an op can never sit on a
host lock with nobody watching. `serve-app` is the exception the mechanism was
given an opt-out for — `nohup ./singularity serve-app … &` is how a packaged app
is actually started, and outliving the shell is the point. It declares
`detachable: true`, and the mapper (`bin/register-commands.ts`) disarms the
guard as the action begins.

Nothing else in the repo declares it. If a second command wants it, the question
to answer first is whether it really needs to outlive its invoker, or whether it
just takes a long time — the guard is fine with slow.

## Why `--repo-root` has no commander default

Its default is `REPO_ROOT`, which lives behind `@plugins/infra/plugins/paths/server`
— a server barrel. A command's *declaration* is loaded on every single
`./singularity` invocation, so it may reach no npm package and no `web`/`server`
barrel (`cli:command-declarations-light`). The default therefore lives in
`cli/run.ts` as `opts.repoRoot ?? REPO_ROOT`, and the option's help text says
"(default: the repo root)" so `serve-app --help` still tells the truth.
