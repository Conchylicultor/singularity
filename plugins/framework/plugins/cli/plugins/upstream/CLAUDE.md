# upstream

`./singularity upstream status|merge` — the repo this checkout was cloned from.
A command GROUP: it routes, and the declaration union makes "also runs"
unspellable, so bare `upstream` prints its subcommand help by construction.

Both verbs read `fetchUpstreamStatus` from `@plugins/upstream/core`, which is
also what main's daily detection job calls. That is the point of the shared
core: the command a user runs by hand and the report that wakes them up can
never disagree about what "behind" means.

## `status`

Fetches, then prints how many commits upstream has that local `main` does not,
newest first. Read-only. Every arm exits 0 — "no upstream" (this checkout
publishes to its own remote, or has none) and "up to date" are answers.

It fetches on every run. A count measured against the remote-tracking ref
already on disk is as old as the last fetch, which is a number that looks
current and is not.

Not being able to REACH upstream exits 1, in plain words, with no stack and no
CLI crash record — a laptop on a train is not an incident, and `process.exit`
before the throw is what keeps `run-cli`'s crash recorder out of it.

## `merge`

Merges `<upstream>/main` into the branch this worktree is on, leaving conflicts
in the tree. **This is the one sanctioned merge in this repo** — `CLAUDE.md`'s
"always rebase, never merge" carves it out, because rebasing the user's own
trunk onto upstream would replay their entire history on every update and
rewrite `main` under every open worktree.

Three refusals, all before anything moves: the main checkout (same reason
`toolchain upgrade` refuses — main rebuilds itself when its ref moves), a
detached HEAD, and a dirty tree (a conflict resolution could not then be told
apart from the agent's own edits).

On conflicts it exits 1 and names the unmerged paths under
`plugins/database/plugins/migrations/data` separately: a conflicted migration is
the one thing to stop and report on, and `git merge`'s own output cannot say
which of the files it listed matter.

## Why `merge --continue` exists

To conclude the merge, so that resolving a conflict never needs a raw
`git commit`. The repo's rule is that an agent never commits — `push -m` is how
work is committed — and a half-done merge was the one place that rule had no
answer, because `push` would also push, which is exactly what an upstream update
must not do before the user says so. Rather than carve an exception into the
rule, the command that opens the merge closes it.

Order matters inside it: unresolved paths are refused **before** anything is
staged, because staging a conflicted path is how git records "resolved" — doing
that for the user would silently pick a side. Only once nothing is unmerged does
it `git add -u` (post-resolution edits; `-u` not `-A`, so a stray scratch file
stays out) and commit. A staged file still carrying `<<<<<<<` is caught by
`git diff --cached --check`, reading only its conflict-marker lines since that
flag also reports whitespace.

A merge that did NOT conflict needs none of this: git concludes it itself, by
fast-forwarding or by writing the merge commit.
