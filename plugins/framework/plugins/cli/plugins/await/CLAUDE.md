# await

`./singularity await [ops…]` — block until this checkout's running op writes its
verdict, print it, and exit on it.

```bash
./singularity build          # run_in_background: true
./singularity await build    # foreground — returns when the build ends
```

## Why it exists

A subagent that backgrounds a long op is **never woken when it finishes**. The
harness builds the completion notification and files it under the *parent*
session's queue, where nothing delivers it. Measured in `conv-1789736383-4i30`:
two teammates ended their turns on a background `check` and `test`, both exited
0 two minutes later, and neither moved again for nine hours. Upstream
`anthropics/claude-code` #88423, #87689, #85534, #92410 — all open.

So the wake-up stops being something the agent is *told* and becomes the result
of its own tool call. `background-ops` (guards) points subagents here, and the
stop-guard refuses a turn that walks away from a running op.

## It starts nothing, and kills nothing

`await` never spawns the op. That is not a simplification, it is the design:

- **The orphan guard.** `bin/index.ts` arms it for every CLI invocation, so a
  command dies with its invoking shell. An agent's foreground tool call is
  killed at 600 s — if `await` owned the build, the build would die with it.
  Keeping the op in its own harness-owned background task means the wait is
  disposable and the op is not.
- **`detached: true` has one home.** `plugins/infra/plugins/spawn/lint` reserves
  it for the supervised-run supervisor, deliberately. A second CLI-side detacher
  would be the start of the spread that lint rule exists to prevent.

Consequently `await` is **not** `detachable`: dying with its shell is right.

## What it reads

Three records, none of them new:

| question | record |
|---|---|
| is my op still running? | the op's flocked marker `~/.singularity/worktrees/<slug>/ops/<opId>.json` (`infra/worktree`) |
| what did it decide? | the op log's terminal record for that `opId` (`debug/profiling/op-log`) |
| what is it blocked on? | `readOpenWait(opId)` — the same feed the build lock prints from |
| build / test detail | the deploy receipt, and `test-status.json` |

**The op log wins over the marker.** Every writer appends its terminal record
BEFORE it releases its marker, so the verdict is on disk by the time the marker
goes; asking the log first means a marker read a moment late can never outvote
it — `core/decide.ts` encodes the precedence, and a test pins it.

The marker's `opId` is what joins the two, and it is **required** on
`markWorktreeOpStart`. There is one marker per op, held under a kernel `flock`
for the op's life, so two `check`s in one checkout are two markers, and a
SIGKILLed op's marker reads dead the instant the process is gone. Frozen at arm
time, a wait always reports on the runs it armed on. Legacy per-kind
`ops/<kind>.json` markers from an older CLI are still read (pid liveness), and
for those the op's own pid settles "gone" vs "verdict coming".

## The four exits

`core/`'s `AWAIT_EXIT`, because three of them are not "your op failed":

| code | meaning |
|---|---|
| 0 | every awaited op ended successfully |
| 1 | one ended badly — **or died without writing a verdict at all** |
| 70 | the wait hit its own cap; nothing is wrong, call again |
| 3 | there was nothing to await |

`--max-wait` defaults to 480 s, under the 600 s cap an agent's foreground call
has, so the wait always returns something readable rather than being killed
mid-wait. `0` waits forever — for a human, never for an agent.

A **vanished** op (process gone, no terminal record — a SIGKILL, an OOM) is its
own state, not an outcome. Nobody knows what it did; calling that `failed` would
invent a verdict and calling it success would be a lie, so it says so and exits
non-zero.

## Waiting is push-based

`watchForCommand` (file-watcher's CLI barrel) over two directories — the checkout's `ops/` and the op
log's — so the wait settles on a filesystem event, not a tick. The watcher's own
`reconcileMs` is the only timer, and it is a safety net: a missed event must
cost seconds, not the whole wait. Waiting forever on a signal that never arrives
is the exact failure this command was written to remove.

Repeated `await` calls cannot trip the poll-loop guard: `singularity` is in its
`MUTATORS` set, so every invocation classifies as `mutate` and resets the
window.
