# check

`./singularity check` — the repo's verdict.

The **only in-process caller of `runChecks()`**. `build` and `push` each spawn
this command in a subprocess (`op-runtime/cli/check-subprocess.ts`) rather than
re-implementing the pass, so the `checks ✓` all three print is one claim.

`cli/index.ts` is the data-only declaration; `cli/run.ts` is the body, behind the
declaration's lazy `import()`.

## Two commander shapes to copy from here

- **Variadic positional.** `[checks...]` arrives as a `string[]` — empty, never
  `undefined`. That empty array is how "run everything" is spelled:
  `runChecks(checks.length > 0 ? checks : undefined, …)`.
- **Negatable flag.** `--no-cache` binds to a `cache` property that is `true` by
  default, so the body tests `opts.cache === false`. A truthiness test would read
  "cache off" as "cache on".

## Nested vs top-level is ONE fact

Inheriting a parent op's host grant (`inheritedGrant()`) decides all of it: the
worktree op marker, the op-log row, the signal handlers, the broadcast banner,
and whether a grant is acquired at all. A nested check does none of them — the
parent owns all three, and a second set would double-count the time. `--run-id`
is nested-only for the same reason: a top-level check's id also names its op-log
row, its kill line and its `check-<id>.log` transcript, so adopting a parent's
would collide.
