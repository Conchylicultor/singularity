# regen-migrations

`./singularity regen-migrations [--name <slug>]` — throws away this branch's
own migrations and re-runs drizzle-kit generate against the rebased schema.

A branch-local migration is generated as a diff against the schema as it stood
when the branch started. A rebase moves that schema, so replaying the old diff
on top of it produces DDL for a state that no longer exists. Regenerating from
the merged schema is the only correct answer, which is why `push` calls this
right after its rebase.

It is the migration-generation stage of `./singularity build`, reached through
the same `generateMigration` pipeline (`plugins/migrations/cli`) with
`resetMigration: true`. The default slug is `merged_YYYYMMDD_HHMM` in UTC;
`--name` overrides it.

Two refusals come before the regeneration, both because "reset and regenerate"
is destructive in exactly two ways:

- **A hand-edited branch-local migration.** Every migration's filename embeds a
  sha256 prefix of its own SQL, so content that no longer matches the name is
  proof someone edited it — and regenerating would discard those edits without
  a word. Data migrations (the snapshot-less ones) are exempt: their SQL is
  hand-written by design and their hash self-heals on every build.
- **A migration from `main` missing from the working tree.** Migrations that
  have landed are immutable by contract — deployed databases record their
  hashes in `__singularity_migrations` — so a missing one is always an error.
  This assertion is also what keeps the unconditional journal regeneration
  honest: the journal is derived from the `.sql` files on disk, so a deletion
  would otherwise just quietly lose its row.

Both need `origin/main` (or `main`) to compare against, and say so rather than
guessing when neither resolves.
