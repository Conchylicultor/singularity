# bootstrap

The part of the CLI that must work with `node_modules` **absent or stale** —
because it is the part that repairs them.

`bin/index.ts` runs four ordered steps before the CLI proper exists: arm the
orphan guard, `await ensureDeps()`, hand the command to a fresh process if it
installed, then `await import("./cli")`. Everything those steps need lives here.

## The one rule

**This barrel's static import closure must reach no npm package.** Static
imports hoist above every statement in a module, so a single npm specifier
reachable from here resolves against the very `node_modules` that `ensureDeps()`
exists to repair — and a fresh checkout dies on an unresolved module before the
CLI can install anything. `rm -rf node_modules && ./singularity build` becomes
unrecoverable from inside the repo, which is also the fresh-clone path.

Node builtins, relative repo files and `@plugins/*` aliases only.
`cli:bootstrap-package-free` measures this with `Bun.build`, so the check cannot
drift from what actually loads.

## Why these five and nothing else

They are already in the pre-install closure: `ensure-deps → build-lock →
adaptive-timeout`, plus `orphan-guard` and `reexec` which `bin/index.ts` reaches
directly. A module only *some* command needs belongs in `op-runtime`, whose
closure carries no such constraint.

`build-lock` says which span a lock holder is stuck in, and the authority on
that is `op-runtime`'s build-progress reader — which this barrel may not import,
static or dynamic. So it does not: `acquireBuildLock` takes a
`describeHolderActivity` hook and the caller that HAS the progress log
(`app-artifacts`, deep in the build) passes it in.

That inversion replaced a dynamic `import()`. The dynamic edge kept the closure
npm-free, but it made a real cross-plugin dependency invisible to the boundary
system, which is what R9 (`inline-import`) forbids — and the check caught it.
Injecting the diagnostic is the better answer anyway: `bootstrap` now names no
plugin the pre-install path cannot afford, so the constraint holds by
construction rather than by a comment explaining why an exception is safe.

## Why a plugin, not files in `bin/`

Once every command is its own sub-plugin, a sibling cannot reach the host's
`bin/`, and `shared/` is plugin-private (cross-plugin `shared/` imports are
forbidden). A `cli/` barrel is the sanctioned way for one CLI plugin to share
code with another — `push` and `build` both need `ensureDeps`, and `build` needs
the build lock.
