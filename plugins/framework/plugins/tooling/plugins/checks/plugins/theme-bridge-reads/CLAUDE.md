# theme-bridge-reads

Rejects any read of a Tailwind `@theme inline` **bridge** copy
(`--color-input: var(--input)`) outside `@theme` — in plugin CSS (a utility,
a rule) or in a `.ts`/`.tsx` class string (`bg-[var(--color-x)]`,
`[--y:var(--color-x)]`). Read the runtime var it copies (`var(--input)`)
instead.

## The bug it prevents

Tailwind inlines a bridge into its generated utilities (`border-input` →
`var(--input)`), so those re-read the token on each element, inside its own
theme scope. But the bridge property itself is emitted on `:root`, where its
`var()` is substituted once; every element then inherits the desktop theme's
value. A hand-written `var(--color-input)` therefore paints the desktop colour
inside a scoped app theme (`[data-theme-scope]`) — no error, just the wrong
colour. The menu rows and the input focus border both had it.

Only bridges that copy a runtime var count; Tailwind's static palette
(`--color-red-500`) is a literal and is ignored (see `no-hardcoded-colors`).
