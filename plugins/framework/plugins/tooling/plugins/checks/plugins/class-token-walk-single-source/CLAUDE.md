# class-token-walk-single-source

Fails if any lint **rule** file declares its own class-token walk —
`collectTokens`, `baseClass`, `CLASS_ATTRS` or `CLASS_BUILDERS`. There is one
walk, in
[`tooling/plugins/lint/core/class-token-walk.ts`](../../../../lint/core/class-token-walk.ts),
and every class rule is handed it.

## Why an absence, not a byte-comparison

This replaces `class-token-walk-in-sync`, which kept six hand-copied walks
byte-identical. That check could only police the copies named in its `EXPECTED`
list — and **eleven other rule files carried an older, weaker copy** that
resolved no identifiers at all. They sat outside the check and drifted silently,
so `no-adhoc-layout`, `no-adhoc-spacing`, `no-adhoc-surface` and eight more
could not see a class string parked in a `const` or a style map. Keeping N
copies in sync is strictly weaker than having one.

## How a rule takes the walk

Rule files are dual-loaded, under **jiti** (which loads `eslint.config.ts` and
cannot resolve the `@plugins/*` alias) and under **Bun**, so they cannot import
a runtime value from another plugin. jiti *does* erase `import type`, so a rule
takes the type by import and the value by injection:

```ts
import type { LintToolkit } from "@plugins/framework/plugins/tooling/plugins/lint/core";

export default function buildRule({ collectTokens, CLASS_ATTRS }: LintToolkit) {
  return createRule({ /* … */ });
}
```

and its plugin's `lint/index.ts` lists it under `classRules` (not `rules`), which
`buildLintConfig` calls with the shared toolkit.

Use `import type { … }`, never `import { type … }` — `verbatimModuleSyntax` can
preserve the latter as a runtime import, which breaks config loading under jiti.
