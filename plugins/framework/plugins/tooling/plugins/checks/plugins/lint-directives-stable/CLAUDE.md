# lint-directives-stable

Fails if any `eslint-disable-next-line` / `eslint-disable-line` on this branch
would suppress **different code** once its file is formatted.

`eslint-disable-next-line R` binds to a line *number*, not to the code it means.
Prettier reflows lines. The two are structurally incompatible, and the repo has
~1,100 such directives.

Two failure modes, and only one announces itself:

- **narrowed** — the target is split across lines, the directive stops covering
  the violation it was written for, the rule fires. Loud, annoying, safe.
- **widened** — the target is merged with neighbouring code, and the directive
  now suppresses a violation nobody vetted. **Silent, and strictly worse.**
  Nothing else in the build can see it.

The comparison is structural, not textual: two lines are the same target iff the
same sequence of AST nodes *starts* on them — which is what an ESLint directive
actually covers, since a report's line is its node's start line. Quote
normalization, added trailing commas and reindentation change a line's text
without moving code across a line boundary, and are correctly not displacements.

## This check is the second line of defense, not the first

It reads the files **as they are on disk**, so it can only see a displacement
while the file is still unformatted. Once a build has written the formatted
bytes, `formatSource` is the identity and there is nothing to compare — the
check goes green at the exact moment the damage has landed.

So the real enforcement is the **write gate** in
[`tooling/format`](../../../format/CLAUDE.md)'s `formatChangedSources`: it holds
both the pre- and post-format bytes, refuses to write a displacing file, and
throws. This check exists because `push` never builds — it spawns
`check --scope tree` — so a not-yet-formatted branch needs a surface that names
the real problem instead of `format-clean`'s "run `./singularity format`", which
would just hit the gate.

Both surfaces print the identical message, from
`formatDirectiveDisplacementReport`, so they cannot describe the same problem
differently.

## Fixing a hit

A directive prettier can move again is not a fix. Either remove the violation,
or wrap the region in block form, which survives any reflow:

```ts
/* eslint-disable promise-safety/no-bare-catch -- <why> */
…code…
/* eslint-enable promise-safety/no-bare-catch */
```

**In JSX the block form does not exist.** A `disable`/`enable` pair is not
expressible in child or attribute position, so a JSX directive is positional or
nothing. There, either remove the violation (reach for the primitive that owns
the mechanic — that is what makes the suppression unnecessary rather than
merely relocated), or write the target line in prettier's *own* shape, so the
format pass is a no-op there and has nothing left to move.

The ~1,100 existing sites are deliberately **not** migrated: they surface one at
a time, as the files that hold them are touched. 208 of them are the JSX braced
form.
