# check-runner-safety

Contributes the repo-wide `no-adhoc-check-runner` ESLint rule: importing
`runChecks` as a **value** from
`@plugins/framework/plugins/tooling/plugins/checks/core` is banned everywhere
except the one sanctioned in-process caller,
[`cli/plugins/check/cli/run.ts`](../../../../cli/plugins/check/cli/run.ts). Every other
caller spawns that command instead.

## Why

A passing check does not just print a ✓. It writes a durable entry to the
**global** cache at `~/.singularity/check-cache/`, keyed on
`(treeHash, checkId, sha256(signature))` and carrying no provenance — just
`{checkId, treeHash, recordedAt}`. A **later, different** process looks that key
up and returns ✓ without running anything.

So the process that records a verdict must have done nothing else first. `push`
already understands this: it spawns a fresh `bun … check --scope tree` child
precisely so checks cannot read a stale in-process module cache. `build` did the
opposite — it called `runChecks()` in the same process that had already imported
every plugin barrel, run the slot-declaration pass, and warmed the codegen memos.
The two ✓ were not the same claim, and the contaminated one won: push's clean
subprocess found the build's cache entry and skipped the run. The isolation push
paid for was spent on a lookup answered by the process it was isolating itself
from.

That is how commit `fa7e865e0` shipped a `docs/plugins-details.md` only a build
could reproduce: four commits each recorded a passing `plugins-doc-in-sync` from
a build, four pushes hit that cache, and the failure surfaced hours later on an
unrelated branch. `18126884a` fixed that one check at its source — this rule
closes the channel for the next impure one.

The remedy the message names: spawn the check pass through the shared helper at
[`cli/plugins/op-runtime/cli/check-subprocess.ts`](../../../../cli/plugins/op-runtime/cli/check-subprocess.ts),
threading the host grant through `grant.env()` so the child does not re-acquire
host capacity.

## What is and is not banned

The rule keys on the **named specifier**, never the module. `RunChecksOptions`
lives on the same barrel and is deliberately not banned — naming the options
shape costs nothing, only invoking the runner does. `listAllChecks` and `scopeOf`
read the registry without recording anything, and stay valid too. Type-only
imports (`import type`, and inline `type` specifiers) are allowed. A namespace
import followed by `checks.runChecks(…)` is flagged, mirroring
[`no-adhoc-profiler-seam`](../sink-safety/lint/no-adhoc-profiler-seam.ts).

*Owner (in-rule, `OWNER_FILE`):* `plugins/framework/plugins/cli/plugins/check/cli/run.ts`
— a **file**, not a directory: the `check` command's action body and nothing else
in that plugin, since its `cli/index.ts` declaration must stay data-only and a
directory-shaped owner would admit any file dropped beside it. `build` and `push`
are the callers this rule exists to keep out; both spawn the pass instead.

## No test exemption

Contributed rules are off in test and e2e files by default (see the
[lint](../../CLAUDE.md) plugin), because they enforce the app's *composition*,
which a suite observes from outside. This one is opted back in everywhere via
`enforceEverywhere`, alongside `promise-safety`'s bug-catching rules.

A `*.test.ts` that drives `runChecks()` is not observing from outside: it runs in
a process that imported whatever the suite imported, and it writes into the same
global cache a later `push` reads and trusts. A test harness is inside this blast
radius, not outside it. (This plugin's own RuleTester fixtures embed the
specifier in JS strings, so the rule does not self-flag them.)

## Why a lint rule and not a check

A `grepCode` check was rejected: the token appears in ~8 comments inside
`checks/core` itself, an AST-walking check reimplements what ESLint gets from the
parser for free, a check only fires *after* a build has already recorded its
entry, and a new check would itself enter the very cache this change exists to
make trustworthy. Rung 4 is the runtime `isBuildProcess()` throw at the top of
`runChecks()`, which catches the paths lint cannot see.
