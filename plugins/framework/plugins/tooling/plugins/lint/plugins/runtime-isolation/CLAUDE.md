# runtime-isolation

Two repo-wide ESLint rules policing imports **inside a single plugin's own
tree** — edges `plugin-boundaries` never sees, because it only polices
cross-plugin imports.

- **`no-cross-runtime-import`**: `web/` and `core/` never import a sibling
  `server/`, and `server/` never imports a sibling `web/`. The cross-runtime
  channels are `core/` (public) and `shared/` (plugin-private). Type-only
  imports are banned too — a type both runtimes need belongs in `core/` by the
  same argument.
- **`no-deep-own-folder-import`**: a browser-built file (`web/`, `core/`,
  `shared/`, `fixtures/`) reaches a sibling folder only through its barrel —
  `../../core`, never `../../core/merge-group-values`. See below.

Both read the plugin-dir grammar through one helper, `lint/own-tree.ts`.

## Why a lint rule and not `plugin-boundaries`

`plugin-boundaries` owns the CROSS-plugin grammar, but it only resolves alias
specifiers (`@plugins/…`, `@server/…`) through its zone map — see
`ZONE_SPECIFIER_RE` in `boundaries/core/check.ts`. A relative `../server/x`
inside one plugin never reaches it. The rule covers both spellings: relative
paths and the plugin's own `@plugins/<own>/server` self-specifier. Cross-plugin
`@plugins/other/server` imports stay out of scope — the boundary config decides
those.

## The outage

`conversations/core/index.ts` line 1 was
`export { isActiveStatus, hasLiveProcess } from "../server/status"`. The browser
`core` artifact therefore bundled a file out of `server/`, while the artifact's
address hashes only the folders it is meant to inline (`core/`, `shared/`) — so
editing that file left the content-addressed store answering "unchanged" and
serving the stale bundle indefinitely
(`research/2026-08-17-global-artifact-address-covers-content.md`). The fix was to
move the two pure predicates into `core/`, where they always belonged; the rule
is what keeps the next one from being written.

## Why deep own-folder imports are banned in browser-built files

The web-artifact builder turns every import into another own folder into that
folder's barrel artifact (`@plugins/<own>/core`). It cannot inline the file:
the page would then hold a second copy of that file's module state, next to
the one inside the core artifact every other plugin loads. So in the browser
`../../core/merge-group-values` means "the core barrel", while `tsc` reads it
as the file.

That is how `theme-engine/web/components/theme-injector.tsx` shipped: it
imported `mergeGroupValues`, which `core/index.ts` did not export. Type-check,
eslint and plugin-boundaries were all green. `./singularity build` failed about
5 minutes in, at compose: `"@plugins/ui/plugins/theme-engine/core" does not
export "mergeGroupValues"`. Written as the barrel, the import means the same
thing to `tsc` and to the bundler, so the missing export is a type error in the
editor. The autofix rewrites the specifier to the barrel — the module the
browser already loads — and `tsc` then names whatever the barrel still lacks.

Server, `check/`, `cli/` and script files are out of scope: they run under Bun,
which loads the deep file itself, so their deep imports mean what they say. The
builder also throws on a deep path (`web-artifacts` `ownFolderBarrelPlugin`), as
the backstop for what lint cannot see — generated files, disabled lines,
`--skip-checks`.
(`research/2026-09-15-global-own-folder-barrel-imports.md`)
