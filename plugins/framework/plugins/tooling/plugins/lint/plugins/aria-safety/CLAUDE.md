# aria-safety

Contributes the repo-wide `no-orphan-composite-role` ESLint rule: a file may not
declare a composite ARIA container role (`listbox`, `tablist`, `tree`,
`treegrid`, `grid`, `menu`, `menubar`, `radiogroup`) unless it also contains an
element carrying one of the child roles that container requires.

## Why

A composite role is a contract, not a label. `role="listbox"` promises options,
`role="tablist"` promises tabs, `role="grid"` promises rows — and assistive tech
honors the promise: it presents the subtree as that widget and commonly drops
whatever is not one of the required children.

So a container whose children never arrive is **strictly worse than no role at
all**. It announces an empty widget, and it hides the real content behind it.

That is the defect this rule was written from. The page editor's block-selection
container carried `role="listbox" aria-multiselectable aria-label="Page blocks"`
and nothing below it carried `role="option"`. A screen reader therefore read an
empty list of options where a document of headings, lists, quotes and paragraphs
actually lived — an attribute added to help was deleting the page. The honest
role there was `group`, which promises nothing, and the selection state moved to
an announcement channel instead (see
[`plugins/page/plugins/editor/CLAUDE.md`](../../../../../../page/plugins/editor/CLAUDE.md)).

The pairing is knowable statically at the only altitude where it *is* knowable:
the file that declares the container. That is what the rule reads.

## The rule

| Container | Required child role |
|---|---|
| `listbox` | `option` |
| `tablist` | `tab` |
| `tree` | `treeitem` |
| `treegrid`, `grid` | `row` |
| `menu`, `menubar` | `menuitem` / `menuitemcheckbox` / `menuitemradio` |
| `radiogroup` | `radio` |

The verdict is per **file**, not per subtree: children authored above the
container, in a sibling component in the same module, or inside a `.map()` all
count. A `role="…"` value contributes every whitespace-separated token, so an
ARIA fallback list (`role="doc-item option"`) satisfies a container.

Purely syntactic — the rule reads literal `role` strings and nothing else. A
computed `role={x}` is not analyzable and is ignored rather than guessed at.

## The two known blind spots, and why they take a disable

**Cross-file children.** A container and its items legitimately live in
different files when the item is its own component. The rule cannot see that,
and deliberately does not try — a whole-program role graph would be expensive
and still wrong across a `children` prop. Name the pairing instead:

```tsx
// eslint-disable-next-line aria-safety/no-orphan-composite-role -- options are rendered by <ResultRow> in ./result-row.tsx
```

That turns an invisible assumption into a reviewed one, which is the point: the
page-editor bug survived because nobody had ever had to write down where the
options were.

**Native elements with an implicit role.** `<input type="radio">` *is* a `radio`
to the browser, `<tr>` is a `row`, `<option>` is an `option` — none of which
carry a `role` attribute the rule can read. The one instance today is
`primitives/css/radio-group`, whose disable names its native inputs. Don't quiet
such a site by stamping a redundant explicit `role` on the native element; the
comment is the cheaper and truer record.

The third exit is the one the page editor took: if a container genuinely has no
children to promise, it has no composite role — use `group`, which promises
nothing.
