# hook-value

## Why

The React Compiler and `react-hooks/rules-of-hooks` recognise a hook by its
**name** alone. A hook carried as a value — a field, prop, parameter or
variable that holds a hook and is called later — keeps working only as long as
every name it passes through starts with `use`.

Drop the prefix once and the bug is silent. `PaneInternal.resolve` held a hook,
and the resolve guard called it as `resolve(params)`. The compiler saw a pure
function and memoized the call on `(resolve, params)`. On the guard's
render-phase re-render the cache hit, so the resolve hook's own hooks were
skipped, the next `useState` landed on a `useMemo` slot, and React threw #311.
Neither the compiler nor `rules-of-hooks` can catch it, because both trust the
name. Only the **type** knows the value is a hook.

## The brand

```ts
import type { Hook } from "@plugins/framework/plugins/hook-value/core";

interface PaneSpec {
  useResolve: Hook<(params: Params) => ResolveResult>;
}
```

`Hook<F>` is `F & { readonly __hook?: true }`. The brand is **optional**, so any
plain function (a `function useFoo` declaration, an inline arrow) is assignable
with no cast and no mint helper. The declared or inferred type still carries
`__hook`, and that is all the lint reads. The brand survives inference:
`const x = props.useFoo` and `const { useFoo: foo } = p` keep `Hook<…>` in the
type, which is exactly where a rename happens. One exception: because the brand
is optional, `Hook<F> | F` subtype-reduces to plain `F`. So
`props.useFoo ?? plainFn`, a ternary, or a destructuring default loses the
brand. `hook-binding-name` therefore also reads the operands of `??` / `||` /
`&&` / `?:` / `as` / `!`, and the source field of a destructure.

## The two rules

- **`hook-value/use-field-branded`** makes a hook visible. An interface or
  type-literal property named `use*` whose type is a function must be declared
  `Hook<…>`. A union counts when its callable members are branded, so
  `useText: string | Hook<…>` passes. A `use*` **method signature**
  (`useContributions(): T`) is always reported, because a method type cannot
  carry the brand. Function declarations and object literals are out of scope.
  This rule is app-only.
- **`hook-value/hook-binding-name`** makes the name follow the type. Any binding
  whose type (or a union member of it) is `Hook<…>` must be named
  `/^use[A-Z0-9]/`. Bindings are variables, destructured names (a rename reports
  the local name), function parameters, property signatures and class
  properties. Object-literal keys are not checked, because their names come
  from the target type, whose declaration this rule already checks. This rule
  is enforced in test and e2e files too, because a hook renamed there breaks the
  same way.

The two rules together close the set. Declaring a hook field forces the brand,
and the brand then forces every later binding to keep a `use*` name. The risk
only runs one way: a plain function under a `use*` name just costs some
caching, so neither rule judges whether a `use*` name is "really" a hook.

## Fixing a report

- `use-field-branded` on a property: wrap its type as
  `useFoo: Hook<(…) => T>`, and import the type from
  `@plugins/framework/plugins/hook-value/core`.
- `use-field-branded` on a method signature: turn it into a property,
  `useFoo: Hook<() => T>`.
- `hook-binding-name`: rename the binding to `use*`, for example
  `const useDecorate = props.useRowDecoration ?? useNoRowDecoration` or
  `const { useResolve } = spec`. If a fallback is a plain function, rename that
  too (`noRowDecoration` becomes `useNoRowDecoration`). Never silence this rule
  by casting the brand away. The call really is a hook call.

A genuine one-off escapes per site, with the reason next to the code:
`// eslint-disable-next-line hook-value/<rule> -- <reason>`.
