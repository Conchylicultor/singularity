# instructions

The instruction files (CLAUDE.md) the harness loaded.

**Two flavors of the same payload.** At launch it is a snapshot: `files` alone,
each with its path, its harness-assigned `type` ("Project", "AutoMem"), and its
content. On a re-read it is a delta instead — `reason` says why it re-read
(`session_start`), `removed` lists paths that were loaded before and are gone
now, `changed` says whether it found a difference.

`files` can legitimately be **empty** on a re-read whose only news is a removal.
That case is real — it crashed this card once — so only the snapshot flavor
treats an empty `files` as a broken payload and throws; a delta with nothing in
it says "No changes." the way the other delta cards do.

**Deliberately the twin of `nested-memory`.** That sibling renders the same
idea for ONE file picked up mid-session; this is the plural form. Same card,
same `FilePath`, same capped pre-wrapped body — keep them looking alike, so the
reader sees one family instead of two unrelated rows. Removals wear the `−` in
`text-destructive` + strikethrough grammar of `mcp-instructions-delta` and
`agent-listing-delta`, and are plain text rather than `FilePath`: the file is
gone, so offering to open it would promise something that is not there.

**A card, collapsed.** The content is long and standing context; the collapsed
line answers "which files, how many" and the body waits. With exactly one file
and nothing removed the path moves to the `aside` (it identifies the row) and
the body drops it, so the card never restates its own header. A removal is the
row's actual news, so it keeps the header for the count instead.
