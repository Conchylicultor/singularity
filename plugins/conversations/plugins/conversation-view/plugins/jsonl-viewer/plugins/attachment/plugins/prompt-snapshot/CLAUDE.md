# prompt-snapshot

The exact system prompt an agent was handed, captured into the transcript. It is
what you read when you are trying to work out why an agent behaved the way it
did — and it is enormous: fifteen sections of prose plus a full tool table.

So this row is **always collapsed**, and the collapsed line has to be worth
trusting on its own:

```
System prompt   · 14 sections · 14 tools
```

Those two numbers are what a reader actually decides on. The section count says
how much prompt there was; the tool count says whether the agent had tools at
all (half the payloads carry no `tools` key, and that clause then disappears
rather than reading `· 0 tools`).

## Two things the payload gets wrong if you render it literally

**`__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__` is not prompt text.** It is a marker
sitting at index 1, separating the static prompt from the part assembled per
session. Printing it as a section would put a fake instruction in the middle of
the prompt, so it is excluded from the count and rendered as a muted rule
labelled `Dynamic` — a bare rule would leave the reader wondering why the prompt
breaks in two.

**Tools appear by NAME only.** Each `tools` entry is `{ name, description,
schema }`, and the description is a whole tool manual. A reader scanning a
prompt wants to know which tools were on the table, not to re-read their specs.
The names go in a wrapping monospace cluster at the foot of the body; the full
entries stay one click away on the row's raw-JSON action.

The body is capped at `max-h-96` and scrolls inside itself, so opening this row
never pushes the rest of the conversation off the screen.
