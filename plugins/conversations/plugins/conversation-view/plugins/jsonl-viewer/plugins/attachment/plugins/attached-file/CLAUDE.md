# attached-file

A file the user attached to their message. Nine of ten are pasted screenshots;
the rest are text files.

The collapsed line has to answer one question — *is this worth opening* — and
the answer differs by kind:

- **an image** — how big the picture is: `Attached image · 862×154 · 19 KB`.
  It opens by **default**. A pasted image is visible inline everywhere else in
  this transcript (see the `user-image` row), and an image hidden behind a
  chevron is an image the reader never sees. Inside, it is the same
  `ViewerThumbnail` every transcript image uses: capped inline, and a click
  opens the full-window viewer.
- **a text file** — which file, and how much of it: `Attached file · 39 lines`,
  with the path as the interactive `aside`. Collapsed, like every other content
  card.

**The image row deliberately shows no path.** An attached image lives at
`~/.singularity/apps/attachments/<uuid>.png` — every one of the 60 in the
sample — so its name identifies nothing a reader can use, and the path is not
reachable from the file-peek pane either. The picture is its own identity. The
raw payload is one click away on the row action strip for anyone who wants the
blob name.

## The text content is raw

This payload carries raw file text, not `cat -n` output, so it renders through
`code-listing`'s `CodeListing` (not `CatNListing`), passing `startLine` to
restore the true line numbers when the attachment is a window.

The two content kinds are a closed union on `content.type`. A third kind is a
harness change nobody has read yet, so it throws onto its own row rather than
rendering a card with an empty body.
