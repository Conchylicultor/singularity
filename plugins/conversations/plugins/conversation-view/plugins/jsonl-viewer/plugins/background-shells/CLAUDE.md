# background-shells

Which background shells a conversation has launched, how each one is going, and
its live output.

When an agent runs `Bash` with `run_in_background: true`, Claude Code records:

| Moment     | Where                                                   | Content |
| ---------- | ------------------------------------------------------- | ------- |
| launch     | the `Bash` tool-call, `input.run_in_background: true`   | `command`, `description` |
| launch ack | that call's `tool_result`                               | `Command running in background with ID: <shellId>. Output is being written to: <path>. …` |
| output     | `<path>` = `<tmp>/claude-<uid>/<cwd-slug>/<sessionId>/tasks/<shellId>.output` | a plain file, appended while it runs; `\r` progress frames included |
| end        | a `<task-notification>` in the transcript               | `task-id` = shellId, `status` ∈ completed / failed / killed, summary `… (exit code N)` |

## Discovery is a fold, not a read

`backgroundShellsOf({ events, conversationStatus })` (core) is a pure fold over
the `jsonl-events` value the conversation view already subscribes to — no new
server read. A launch is a background `Bash` call whose result parses as the
acknowledgement; a result that does not is a failed launch, never a shell. The
end joins the `task-notification` by `taskId === shellId` (fallback: the
notification's `toolUseId`). A shell the agent stopped itself with a
successful `TaskStop` (`{ task_id }`) is `killed` at that call's result time —
Claude Code writes no notification for it, so without this it would read
`running` for the conversation's whole life. With neither, the conversation's own
liveness (`hasLiveProcess`, the same evidence `subagentRunState` uses) decides
`running` vs `ended-without-reporting` — Claude Code kills its shells on exit.
There is deliberately no staleness timeout. A notification with a status this
build does not know is `ended-unrecognized` (it ended; nothing says how), never
folded into `failed`.

`useConversationShells(conversationId)` gates the fold exactly as
`useConversationSubagents` does: `pending` until both the transcript and the
conversation row have arrived, `failed` when either read failed.

## The output tail: the server finds the file

`shellOutput` (`background-shell-output`, params `{ id, shellId }`) is served on
the external arm. **The browser never sends a path.** The server resolves
`(conversationId, shellId)` itself — the conversation's anchored chain
(`resolveConversationTranscriptPaths` → `readJsonlEventsFromChain`) folded
through the same core `shellLaunchesIn` — and `assertShellOutputPath` throws
unless it is exactly `<tmp root>/claude-<uid>/<x>/<y>/tasks/<shellId>.output`.
The tmp roots are every spelling this process can see (`/tmp`, `/private/tmp`,
`os.tmpdir()` and its realpath) — on macOS the transcript records
`/private/tmp/…`.

Each read is one `stat` and one bounded read of the last 64 KB, cut at the first
line boundary inside the window (`truncated: true`). A missing file is `gone`; a
shell the transcript does not record is `unknown-shell`.

While subscribed, an instance of the `background-shells.output` file watcher
(`defineFileWatcher`) on the file's `tasks/` directory
(`writesWhileOpen: true`, 150 ms debounce) notifies on writes to that one file.
`writesWhileOpen` is required: the shell holds its output file open, and macOS
FSEvents reports only on close. A resolved path is kept for the room's lifetime
so the chain is read once per subscription, not once per push.

## Surfaces

- `ShellStateChip` — the one rendering of a shell's state (dot + label + a
  ticking or frozen clock), shared by the band row, the `Bash` card and the pane.
- `shellOutputPane` (`shell/:shellId`) — a conversation-scoped satellite like
  `agentReportPane`: header (`$ command`, state chip, output path with copy),
  and a sticky-bottom `<pre>` of the tail, rendered through `terminalText`
  (ANSI stripped, each line's last `\r` frame). Loading, `gone` and
  `unknown-shell` are rendered states.
- `lastOutputLine(tail)` — the latest non-blank line (splitting on `\r` too),
  `null` before any output, for a one-line "what is it doing" summary.

v1 is view-only: there is no Stop (only the agent can call `TaskStop`, which the fold reads as `killed`).
