# page

The Singularity pages a conversation wrote, changed or read — one of the kinds
in the conversation's Artifacts popover.

## What counts as a sighting

The three page tools, matched on their **suffix** the way their transcript
renderers match them (`/edit_page$/`, `/write_agent_note$/`, `/read_page$/`):
an MCP tool arrives named for its server too, and the prefix is not ours to
predict.

| The call | The relation |
| --- | --- |
| `write_agent_note` / `edit_page` | the page it wrote into: **edited** |
| …whose report lists `created_page_ids` | each of those new sub-pages: **created** |
| `read_page` | **referenced** |

A write that mints an `<agent-page>` yields two rows: the page it wrote into
(edited) and the new sub-page (created). The new page's id comes only from the
report, since it does not exist before the write lands — so a mint still in
flight shows just the edited parent, and the created row appears when the call
returns.

## Which page a row is

The apply report's `page_id` first, because `block_id` names the **scope** of
the write, which is usually a card inside a page rather than the page itself.
The report only exists once the call returned and succeeded; a write in flight
or refused falls back to the block id, which is then the only name the row has.
`parsePageApplyReport` is page-tools' — the report shape has one reader.

Known seam: a read is keyed by whatever `block_id` it was given, so reading one
card of a page and then editing that page lists two rows: the page, and the
card. Both open.

## Resolving a row

Each row resolves its key through page-tree's `useBlockTarget` — the same
resolver the transcript's `block-…` chips use. A page id is answered from
`pagesResource` for free; anything else costs one `getBlockPage` lookup.

- **a page** — titled with the page's title, opens the page beside the chat.
- **a block inside a page** — titled "<page title> › <block type label>"
  ("Plugin system › TODO"), opens the block view (`blockDetailPane`): that
  block and its nested lines, editable, beside the chat.

Two states are not a title and do not pretend to be one:

- **not resolved yet** — a skeleton row. The count is known from the transcript
  alone; a title is not.
- **not in this instance** — greyed and inert, showing the id. Not an error: the
  page tools write to the SHARED instance while this view reads whichever one
  served it, so a worktree's stale DB fork routinely has no row for a block
  that exists. Only this truly-missing case is inert; a failed lookup is inert
  too, but says why.
