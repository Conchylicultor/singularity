# commits-graph

Toolbar chip showing how many commits the conversation's worktree branch is ahead of (and behind) `main`. Clicking opens a side pane that draws the chain of commits between the merge-base and HEAD as a single colored rail (VSCode-Git-Graph style, single-branch scope).

## The standing belongs to `tasks/attempt-work`

This plugin does not own "where does this attempt stand relative to `main`?" — the server-side exit-drop guard needs the same fact, so it lives in [`tasks/attempt-work`](../../../../../tasks/plugins/attempt-work/CLAUDE.md). Here:

- The **chip** subscribes `attemptWorkResource` and nothing else. `↑ahead ↓behind` come from `pending`'s `measured` arm; the push count is `landedPushes || ledgerPushes` (git-measured, with the ledger as corroboration — a `pushes` row proves a push happened, its absence proves nothing, and pre-trailer-era commits are visible only to the ledger).
- The **pane** owns only the commit *rows*, behind `commits-graph.graph`. Its landed shas come from `readLandedShas(attemptId)`; the pending-side git helpers (`readBranch`, `readMergeBase`, `probeHeadMain`) are imported from `attempt-work/server`, not re-implemented.

**The landed set is git-measured** — `main`'s commits carrying this attempt's `Singularity-Conversation` trailers — never read off the `pushes` ledger, which lags behind a background ingest job (`research/2026-08-17-global-attempt-work-git-derived-standing.md`). Two consequences worth keeping: the graph resource depends on `refHeadResource` **alone** (a commit joins the landed set only by landing on `main`, so a ref advance is the complete refresh signal), and `graphEtag` folds in only `(headSha, mainSha)` for the same reason. It tracks its subscribed attempts via `onFirstSubscribe`/`onLastUnsubscribe`, so a ref advance fans out only to the panes on screen.

## Unresolved payloads (worktree gone)

The graph payload is wrapped in `Resolvable`: the resolved arm carries the measured graph, the unresolved arm a `reason`. An attempt outlives its worktree, so "no worktree" and "worktree reaped mid-compute" are the SAME determinate state, collapsed onto `unresolved("worktree unavailable")` by `onWorktree` (`server/internal/resources.ts`). Loader value and `revalidate` ETag come from the same `onWorktree` branch, so they can never disagree (`research/2026-07-09-global-etag-value-coproduction.md`). Every *other* git failure throws — including `readLandedShas`, which throws rather than returning a `[]` indistinguishable from "landed nothing". It is unmeasurable only when the attempt row is gone, which `onWorktree` just excluded, so that throw means a delete raced the compute: it propagates, and the error gate keeps the client on its last vouched-for value.

The pane is deliberately stricter than the chip: `attempt-work` can still measure a reaped attempt through its surviving branch ref, but the pane needs a checkout to run its commit logs in.

The chip renders a muted `—` (reason as tooltip) both for an unresolved payload and for `pending.kind === "no-branch"`; the pane renders a `Placeholder` with the reason.
