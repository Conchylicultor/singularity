# rewind

On each of your own messages in the transcript, a small history button offers
two ways to go back to just before that message:

- **Rewind to here** — this conversation continues from that point. Everything
  after it is removed from the conversation.
- **Fork from here** — a new conversation on the same worktree starts from that
  point. The original is untouched.

Either way the message's text lands in the prompt editor, ready to be rewritten.

Design, and the CLI experiments behind every claim below:
[`research/2026-09-18-conversations-rewind-conversation.md`](../../../../../../research/2026-09-18-conversations-rewind-conversation.md).

## How it works

Neither path talks to the running CLI. The CLI's own `/rewind` sits behind an
interactive menu, and its hidden `--resume-session-at` flag is honoured in print
mode only. So both paths **cut the transcript file and start a plain
`claude --resume` on it** — the CLI only ever sees an ordinary resume, and the
kept history is byte-identical, so the prompt cache hits in full.

- **Rewind** moves the live session file into the backup folder, writes the
  shortened transcript in its place, and respawns the pane on the **same session
  id**. Same id means the session chain, the CLI's file checkpoints and the cost
  index need no change. The move (rather than a copy) is deliberate: the CLI
  being killed still holds the old file open, so anything it appends on its way
  down follows the moved file instead of landing after the cut.
- **Fork** writes the shortened transcript under a fresh session id in the same
  `~/.claude/projects/<dir>/` and plain-resumes it. This is NOT the `fork-session`
  plugin's mechanism: that one asks the CLI to copy the *whole* history
  (`--fork-session`); the CLI has no way to copy part of one.

The cut itself — which lines stay, and what is lost — is one pure function,
`cutTranscriptAt` in `conversations/server`. The Stop button's "give me my
prompt back" is the same function cutting at the last unanswered prompt. The
preview endpoint and the real action both call it, so the dialog cannot describe
a different cut than the one that happens.

A row offers the action only when its `user-text` event carries a `uuid`, and
the parser sets that with the same predicate the cut validates with
(`userPromptText`, `transcript-watcher/core`).

## What cannot be brought back (and why there is a dialog)

Background work lives in the CLI process, not in the transcript:

- A background agent's report is delivered **once**, into the conversation as it
  stood then. Cut before the delivery and the report is gone for good — this is
  true of the CLI's native `/rewind` too.
- Restarting the pane kills subagents and background shells still running.
- On the next resume the CLI sees a launch with no result, prints that the work
  "didn't finish before the previous session ended", and **runs one model turn
  by itself** to say so. The conversation simply reads as `working` for that
  turn; nothing waits on a user message first.

So the action asks the server what the cut loses, and confirms first whenever
there is something to say. With nothing lost, it goes straight through.

Files in the worktree are never touched.

## Refusals

A refusal is a normal answer (`ok: false` + a sentence to show), decided before
anything is changed: the first message (nothing left to resume), a message no
longer in the transcript, a conversation whose worktree is gone, and — rewind
only — a message that predates an earlier fork (it lives in an ancestor session
file; fork from it instead).

## Backups

`~/.singularity/state/conversation-rewinds/<conversationId>.<epochMs>.jsonl` is
the full transcript as it stood before each rewind — the only copy of what the
rewind dropped. A nightly job deletes files older than 30 days. The folder must
share a filesystem with `~/.claude` (the move is a rename); a cross-device
rename throws before anything has changed.

## Known rough edge

A turn sent moments before a rewind that cuts it away can later show as "didn't
land" in the pending-turn card: that store confirms a send by finding its text
in the transcript, and the rewind removed it. Dismissing the card is correct.
