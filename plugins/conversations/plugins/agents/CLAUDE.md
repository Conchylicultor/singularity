# agents

## Tree collapse is not an agent field

There is deliberately no `expanded` column. Expand/collapse of the agents tree is
per-`(surface, view-instance, row)` device-local render state owned by the
data-view primitive, so a collapse costs no DB write and never stamps the row's
`updatedAt`. The column, its patch field, and the "auto-expand the parent when a
child is filed under it" blocks in `handle-update.ts` / `handle-create.ts` were
removed together — that reveal is now the tree primitive's generic add-child /
drag-reparent behavior. Do not reintroduce it; see
`plugins/primitives/plugins/data-view/CLAUDE.md` § State split and
`research/2026-07-28-global-tree-collapse-state-as-view-state.md`.

## The roster is an `all` collection over the `agents` table

`agentRows` (`shared/resources.ts`, key `"agents.roster"`, `preload: "boot"`)
is the whole ordered roster (`rank`, then `createdAt`), served by
`serveCollection(agentRows, agentRowsServeOptions)`
(`server/internal/agent-rows.ts`, the one spelling the server and the tests
compile) over the `agents` TABLE — never `agents_v`: every row field binds to
its column by name, and `isFolder` is an `expr` of `prompt IS NULL`, the
definition `agents_v.is_folder` spells. The sidebar and the avatars' lookups
read it whole with `useLive(agentRows)`; a pane that names one agent reads
`useLiveRow(agentRows, id)` (`:rows`).

- **What a write costs.** A rename, a prompt / model / avatar edit or a
  reparent is that row's refill; a rank move the refill and one `orderOf`; an
  insert an entrant, a delete an exit; a write to any other table (launches,
  the task tree) nothing. Pinned by
  `server/internal/agents-roster-oracle.test.ts` on tasks-core's tree oracle,
  which also holds the compiled set equal to `agents_v` row for row and in
  order (the five REST handlers still read the view).
- **The key was renamed** from the value `agents`: a tab on an older bundle
  subscribing `agents` gets `unknown-key` (the skew / Reload prompt) instead of
  keyed deltas its non-keyed read cannot apply, and the old key's L2 row is
  swept as unusable. The same oracle file pins the `unknown-key`.

## Launches are an `all` collection over a rollup

`agentLaunchRows` (`shared/resources.ts`, key `"agent-launches"`,
`preload: "boot"`) is the whole ordered set of launches, each carrying the
latest non-system conversation of its task (`latestConversation`, and its
status flat as `latestConversationStatus`). Served by
`serveCollection(agentLaunchRows, agentLaunchRowsServeOptions)`
(`server/internal/agent-launch-rows.ts`, the one spelling the server and the
tests compile): `agent_launches` LEFT-joined to the `task_latest_conversation`
rollup (`server/internal/rollup-spec.ts`) on the launch's `task_id`. Read with
`useLive(agentLaunchRows)`.

- **The rollup has two sources.** `conversations` (through the `attempts` hop,
  reading `kind`, `title`, `status`, `created_at`) and `attempts` itself
  (carrying `task_id`, update + delete). The hop is read at trigger time, so
  without the second source an attempt deleted (its conversations cascade and
  resolve no task) or moved between tasks left the task's row stale until the
  next boot reconcile (W8). The second source is also what query-resource's
  A35 requires of any reader joining the rollup.
- **What a write costs.** A launch insert is an entrant, its delete an exit; a
  conversation write the rollup reads refills the launches of its task; an
  attempt insert, move or delete those of its task(s); the poller's
  `waiting_for` / `last_viewed_at`, pushes, task and edge writes reach nothing.
  Pinned by `server/internal/agent-launches-oracle.test.ts` on tasks-core's
  tree oracle, which also checks the rollup against its aggregate after every
  step (W8) and the C39 old-bundle row.
- **The wire row is frozen** (`AgentLaunchWithStatus`, under the legacy key): a
  change to it must rename the key.
- `GET /api/agents/:id/launches` (`handle-list-launches.ts`) still derives the
  same row from `listConversationsForDisplay` — a known duplicate (P8 v3 D30).
