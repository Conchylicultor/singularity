# tags / storage

The **tags** type's storage capability: contributes `Fields.Storage({ type,
decode })` (server runtime), so it is handed the FIELD's own schema and builds
the `jsonb` column from it — a JSON array of strings that really decodes.
Resolved by exact token through `resolveFieldStorage("tags")`.

This file used to be **the one storage contribution in the repo that asserted
rather than derived**: `jsonb(name)` hands back `unknown` while the `tags` token
declares `string[]`, and the gap was closed with a cast. It is a decoder now
(`parsedJson`, `plugins/database/plugins/sql-column`), and the cast and the
paragraph explaining it are gone.

Unlike its `json` sibling there is no `z.unknown()` branch, and there is nothing
to decide: the token declares `string[]`, which a `ZodUnknown` cannot produce, so
every tags column narrows and every tags column decodes.

`tagsField` still has no `defineEntity` call site — it is used in config_v2
surfaces only (the salsanueva source config), never in a table — so nothing is
guarded by this today. What changed is that putting a `tagsField` in a table no
longer means inheriting an assertion.

Without this contribution, `defineEntity` throws on any `tags`-typed field —
this is what makes `tags` usable in an entity at all.

Design: `research/2026-08-26-global-decoded-jsonb-entity-columns.md`.
