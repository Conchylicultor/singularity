# tags / storage

The **tags** type's storage capability: contributes `Fields.Storage` (server
runtime) mapping the `tags` field token to a Postgres `jsonb` column via
`build(name) => jsonb(name)` — a JSON array of strings. Resolved by exact token
through `resolveFieldStorage("tags")`.

The builder is byte-identical to `fields/json/plugins/storage` on purpose: the
bare runtime column for both is `jsonb`.

**`string[]` here is an ASSERTION, not a decoded type**, and it is written as one
— a cast, with the reason beside it. Postgres really decodes the JSON, so a jsonb
column honestly hands back `unknown` and only the *element shape* was ever
claimed. That is the same weaker tier `jsonField<T>` sits in, and an open
follow-up (`research/2026-08-25-global-decoded-entity-columns.md` §7).

The difference from `json` is where the claim lands: `json`'s token declares
`unknown` and lets `jsonField<T>` do the narrowing, while the `tags` token bakes
`string[]` in, so this contribution is what has to state it. The storage contract
surfaced the disagreement as a `tsc` error instead of losing it, which is the
contract working.

`.$type<string[]>()` is NOT the honest spelling of that, and does not compile:
drizzle's `$Type` writes `_.$type` and never `_.data`, which is what the
signature reads (and `$type()` is `return this` — it runs nothing either).

This is **the one storage contribution that asserts rather than derives** — do
not copy it as the pattern. It also guards nothing today: `tagsField` has no
`defineEntity` call site, only config_v2 surfaces. Putting a `tagsField` in a
table is what would change that, and it should get a real jsonb decoder then
rather than inherit the cast.

Without this contribution, `defineEntity` throws on any `tags`-typed field —
this is what makes `tags` usable in an entity at all.
