# tags / config

The **tags** type's config capability: the `tagsField` factory + `TagsFieldDef`
shape (core) and the `TagsRenderer` contributed to `config-v2.fields.renderer`
(web). The multi-valued sibling of `enum/config` — same two halves, same
dispatch by type id.

## The value is `string[]`, not `z.enum(options)[]`

`options` is what the user can **pick**, not what the stored value must **be**.

The types that want a multi-select are the ones whose option set is a snapshot of
a live catalogue someone re-copies each season (a school's dance styles, levels,
teachers). Pinning the schema to that snapshot means the day someone updates the
list, every stored value it dropped stops parsing — a config that loaded
yesterday failing today, with the user's own selection as the casualty.

So the schema is `z.array(z.string())`, and the renderer shows a selected value
the menu no longer offers as a trailing `label ?` chip: kept, visible, and
de-selectable. A value that is still filtering must never be one the form cannot
show.

This is a deliberate weakening of the type rung for this one type, so the
strength has to come back from the consumer: whether a selected value still
matches anything is knowable only where the data is, and the consumer is
expected to say so out loud (`sources/salsanueva` reports it in the run's
caveats).

## What "empty" means is the consumer's word

Nothing here decides whether an empty selection means "none" or "all" — that is a
property of the thing being filtered. Say it in the field's `description`.
