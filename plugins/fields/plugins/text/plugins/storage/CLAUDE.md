# text / storage

The **text** type's storage capability, and the repo's only **decoding** storage
arm: it contributes `Fields.Storage({ type, decode })` rather than `{ build }`,
so it is handed the FIELD's own schema and builds the column from it. Resolved by
exact token through `resolveFieldStorage("text")`.

That is what makes `enumTextField(...)` true rather than asserted. The field-record
analogue of `text("x").$type<Union>()` used to be exactly as empty as the
original: `$type` runs nothing, so the union was a claim about rows nobody
checked. Now the schema that declares the union is the schema that decodes the
column — on every read and every write (`parsedText`,
`plugins/database/plugins/sql-column`).

## The one discrimination

```ts
valueSchema instanceof ZodString ? text(name) : parsedText(name, valueSchema)
```

A plain `textField()` (or one refined with `.min(1)` — still a `ZodString`) keeps
a bare `text` column and pays nothing. Anything else gets a real decoder.

The branch is on the schema the author actually wrote, not a heuristic about
intent — and it is not an optimisation detail: decoding a column that is NOT
narrowed costs the **same** as decoding one that is (345 ns vs 322 ns per value)
for zero guarantee, so decoding every text column would spend roughly 10× more
than decoding only the narrowed ones. `internal/storage.test.ts` pins both
branches.

`getSQLType()` is `"text"` either way, so adopting the decoder generates no
migration (see `sql-column/CLAUDE.md`).

## The decoder runs on writes and on bound params too

One schema, both directions. Besides INSERT `.values()` and UPDATE `.set()`, the
encoder runs on every **bound comparison param** — `eq`, `inArray`, and the rest
route through `bindIfParam` → `Param(value, column)`. So a DataView filter
operand against a decoded column is now checked as well: a stale saved view
holding a value the set no longer contains throws instead of silently matching
nothing. That is a pre-existing hole in filter-operand validation becoming
visible, not a new one — and the columns with real legacy values are tolerant, so
they normalize.
