# investigate-failure

A failed run in a deployment's [History](../../CLAUDE.md) gets one hover action:
**Investigate failure**, which opens the standard launch popover and starts an
agent briefed on that run.

## Why it is a plugin and not a button in the row

The History section owns no writes and no state — the ledger belongs to the
[`deployments`](../../../deployments/CLAUDE.md) sibling. What a reader wants
*after* learning a run failed is an open set (investigate it, re-run it, open its
transcript), so the section owns a row-action slot and each answer is its own
folder. Remove this plugin and the action simply disappears.

## What the agent is told

Everything the row already holds, and nothing it does not:

- **the CLI's message verbatim** — a refusal in this domain is always the CLI's,
  written for a human, and the brief quotes it rather than summarising it. Same
  rule the row follows;
- **the run's identity** — the `deploy_runs` id, the deployment, the server, the
  composition, the verb and the leg it died on;
- **the honest exit-code sentence** — a null exit code is not "exit 0". For a
  multi-leg `update` the phase is what happened, and only a phase-less run
  "never started";
- **absent facts stay absent** — no pinned release run and no commit sha are
  real answers (a converge ships nothing; a bare `ship` resolves the bundle
  inside the CLI's own process), so the brief says so instead of substituting a
  plausible one;
- **where to dig** — the `deploy` log channel, the ledger row, and the fact that
  `./singularity deploy` is the engine, so a wrong verdict is a CLI or host-state
  bug rather than a UI one.

## Why `running` rows are not offered it

The gate is `status === "failed"`, not "not succeeded". A row can be `running`
forever — the backend that would have stamped its outcome went away — and the
ledger deliberately does not invent a terminal status nobody observed. Briefing
an agent that a failure happened there would invent exactly that.
