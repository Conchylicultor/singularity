# deploy-history

**History** — every run ever launched for this deployment. Design:
[`research/2026-08-05-global-deploy-pane-test-locally-and-one-button-deploy.md`](../../../../../../research/2026-08-05-global-deploy-pane-test-locally-and-one-button-deploy.md)
(Phase C).

One contribution: `DeploymentDetail.Section` "History", a server-delegated
`DataView` over `POST /api/deploy/deployments/:id/runs/query`. It owns no state
and no writes — the ledger is the [`deployments`](../deployments/CLAUDE.md)
sibling's `deploy_runs` table, written by the same two functions that write the
live `deploy.runs` map.

## What this section is for

`deploy.runs` is in-memory, so a backend restart empties it — which is correct
for a *live* view (the spawned CLI is not detached; after a restart nothing is
running) and useless as a record. Before this section the pane simply could not
answer *"what is live on this box, and what happened before"* after a reboot, and
the four-step UI it replaced used to say so in a step note. **The point of this
section is to make that caveat false, not to restate it.**

## Reading the row

- **the outcome names the leg** — `Failed on build` rather than `Failed`, because
  which of `converge` / `build` / `ship` died is the first thing anyone asks and
  the row already knows;
- **the message is verbatim** — it is the CLI's own refusal, carried from
  `deploy_runs.message` with nothing rewritten around it. That is also why the
  list view goes through `renderRow`: the field-driven default joins every
  non-primary field into one truncated subtitle, which would clip exactly the
  sentence this section exists to preserve. The field schema still drives sort /
  filter / search and the whole table view;
- **the commit can be absent, and that is an answer.** It is filled from the
  pinned bundle's own manifest, so an `update` has one and a converge does not;
  a bare `ship` lets the CLI follow `latest-<platform>` inside its own process,
  so this app never saw which bundle went out. HEAD is never substituted — the
  sha of this checkout is not the sha of the bytes on the box;
- **`Running` is readable and can be permanent.** A backend that died mid-run
  left it, because the process that would have stamped the outcome is the process
  that went away. No sweep invents a terminal status nobody observed.

## Why a row does not open the release run it names

The plan wanted the release run id to open Studio's run detail. It cannot, and
the blocker is structural rather than an omission here: `releaseDetailPane`'s
segment is `rel/:runId` under `comp/:id`, and its declared params are `{ runId }`
only. `openPane` fills an ancestor's params from the *current route*, so from
outside the composition pane the `:id` segment has no value to take — the caller
is not allowed to supply one (stray keys are rejected by design). Opening it from
the deploy pane would need either that pane to declare its composition param, or
this section to hand-write another app's URL.

So the row shows the full release run id and does not pretend to be a link.
