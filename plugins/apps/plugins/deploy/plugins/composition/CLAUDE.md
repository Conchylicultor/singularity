# composition

The **Composition** section of the deployment pane: *what* this deployment
builds. Every other section is about *where* it lands — and all of them are
downstream of a composition name the pane never stated (`overview` shows the
install paths derived from it, `remote-deploy` the bundle built for it,
`deploy-history` the runs of it).

## It links, it does not edit

`compositionId` is create-only on the row, and the composition's membership lives
in the `compositions` config, which Studio owns. So this section names the
composition and hands off to `compositionDetailRoute.link(studioApp, { id })`.

- **The route lives in Studio's `core/`**, and the pane is defined from it
  (`Pane.define({ route })`) — so the link can't drift from its destination and
  deploy never imports Studio's web barrel (the `build` ← `debug` precedent).
- **The lookup is by name.** Deploy is composition-NAME-keyed end to end (row,
  install dir, unit, `release --composition`); `comp/:id` is keyed by the config
  item's uuid. `useManifestItemByName()` is the one place that crossing happens,
  shared with `local-serve`.

A name that no longer resolves is an expected state (validated on write, nothing
stops a later rename) and renders as a destructive placeholder, not a dead chip.

## No closure computation here

Category / entry points / `extends` / contributor count are read straight off the
stored manifest item — one config read. Plugin counts and membership need the
server-shipped `EdgeGraph` and are what Studio's composition detail is for; a
bundle-size summary here would be a second place to keep right, one click from
the first.
