# local-serve

**Test locally** — where you look at the app before putting it on a box. Design:
[`research/2026-08-05-global-deploy-pane-test-locally-and-one-button-deploy.md`](../../../../../../research/2026-08-05-global-deploy-pane-test-locally-and-one-button-deploy.md)
(Phase B).

Two contributions, both driven by the same capability:

- **`DeploymentDetail.Section` "Test locally"** — the serve panel for this
  deployment's composition, above `remote-deploy`'s "Deploy to server". Reading
  order is the working order: rehearse, then ship.
- **`DeploymentItemActions` "serve"** — one button on the deployments row that
  *opens* the local namespace when it is live and *starts serving it* when it is
  not, because from a list row there is only ever one thing anyone wants.

It owns no serve logic. `ServeTargetPanel` / `useServeComposition` /
`useServeStatus` all come from
[`build/serve-composition`](../../../../../build/plugins/serve-composition/CLAUDE.md),
which is where the capability lives now precisely so this plugin could consume it
without an `apps/deploy → apps/studio` edge.

## Name in, id out

`deployment.compositionId` is a composition **name** — it is what
`release --composition` takes, what the install dir and systemd unit carry, and
what `assert-known-composition.ts` validates on write. The served namespace is
the manifest item's **`id`**, which is the same string for config-authored
compositions and a uuid for UI-created ones. So both surfaces look the item up by
`name` and hand its `id` onward, and a name with no matching item renders as an
error rather than a dead link — a deployment can outlive a rename.

## What the section claims, and what it does not

The caption is load-bearing, not decoration. The local serve is the **dev build
of the same closure** on the shared gateway with its own empty database: it
proves composition membership and closure completeness — the app boots with
exactly these plugins. It does not exercise packaging, config vendoring or
first-boot migrations, because those only exist in the packed artifact, and a
`linux-x64` binary cannot run on the host anyway. The first thing that runs them
is `ship`'s remote health gate.

## The main-only refusal comes first

`compose-serve` reads MAIN's config inside MAIN's build, so on a worktree backend
the toggle writes an intent nothing local will act on and the immediate build is
refused with a 400. The section leads with that sentence, from the `canServe`
field of the serve-status read — server truth, not a hostname the client sniffs —
rather than letting the user find out by pressing. The panel itself deliberately
does not render it: it is a fact about the backend, so where it belongs is the
host surface's call.
