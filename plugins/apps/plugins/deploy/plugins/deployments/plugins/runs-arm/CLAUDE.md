# runs-arm (deploy)

The deploy arm of the unified run space: `deploy_runs` bound into the
[`runs`](../../../../../../runs/CLAUDE.md) union, its own columns, and the list
row. It lives under `deployments` because `deploy_runs` is that plugin's table;
`runs` names no kind.

The per-deployment history DataView is untouched — that one is *scoped*, this
one is global. They read the same table through different queries.

## `namespace` reads `null`

A deploy targets a **remote server**, not a worktree. The worktree whose backend
launched the CLI is a fact about who pressed the button, not about where the
software went.

## Deliberately **unscoped**

The build and release arms carry an always-on `where namespace = currentWorktreeName()`,
because a worktree DB is forked from main and inherits main's rows. This arm must
not, and the symmetry is a trap: `deploy_runs` has no namespace — a deploy targets
a remote server — so the predicate would not narrow the arm, it would delete every
deploy from the view. `null = 'att-…'` is `NULL`, not `false`, and the symptom is
an empty section reading as "nothing deployed yet".

## `trigger` is the verb

A deploy records no separate initiator, and `converge` / `ship` / `update` is the
closest thing to "how did this start". It is *also* `deploy.verb`, so the same
fact is filterable precisely (closed enum, chips) as well as generically.

## `message` is rendered verbatim

The CLI owns every refusal; this app only spawns `./singularity deploy` and
streams its output. The row prints the message untruncated and unclamped, as the
existing deploy pane does — a paraphrase of "the command refused, and this is
what it said" is the one thing that must not happen to it.

## No row activation, and what it would take

The row carries both ids `deploymentDetailPane` needs, but that pane is a legacy
segment-form pane: its typed params are its own only, so `openPane` cannot be
handed the `serverId` its `serverDetailPane` ancestor needs, and an open from
anywhere but the server page lands on a "server not found" column. Converting it
to `Pane.define({ route })` types the parent params and mints the `.link` a real
cross-app hand-off needs; `open` is then two lines in `web/index.ts`.

## `deploy.releaseRunId` is a plain chip

It points at a `release_runs.id` and clicking through would be useful, but
importing the release plugin here would couple two arms — the thing the registry
exists to prevent. The cross-link belongs in `runs`, as a way for one arm to ask
another to open a row it names.

## The label reads the server's name

`server_id` is a mint-time string (`srv-1712…-ab12cd`): a fine dimension,
useless as a label. The label subquery reads `deploy_servers.name` and
`coalesce`s back to the id, because `server_id` is copied onto the run rather
than joined — the server row can be gone while the record remains, and `label`
is non-nullable.
