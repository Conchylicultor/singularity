# page-outline

The right-edge outline of the open page: one dash per heading, the dash for the
section you are reading brighter and wider, hover (or Tab) to expand it into an
indented list you can click to jump. All of that chrome — the dashes, the
disclosure, which entry is current, the scroll-to on click — belongs to
`primitives/outline/rail`. This plugin is the **adapter**: it answers only
*which entries a page has* and *how an entry id maps to a DOM node*, which is
exactly the part that differs between a page and a conversation transcript.

## A heading is a block type that says it is one

The outline never names `heading-1` / `heading-2` / `heading-3`, and must not
start to. It reads `handle.semantics` — the block API's own
`{ role: "heading", level }` declaration — off every `Editor.Block`
contribution. So:

- a `heading-4` plugin added tomorrow appears in the outline, correctly nested,
  with **zero edits here**;
- a block that merely *renders large* never does. `textVariant` is a font-size
  role and `semantics` is a structural claim; the editor keeps them apart
  deliberately (see `page/editor/core/block-semantics.ts`), and deriving one
  from the other is how a big paragraph starts announcing itself as a heading.

`depth` is `level - 1`, so an H1 sits at the rail's top level. The label comes
from the handle's own **text lens** (`handle.text(data)`), not from reading
`data.text` by hand — the lens is typed against that block type's own payload,
so a field rename is a compile error in the owning plugin rather than a silently
blank row here. A heading whose text is empty is skipped: it has nothing to name
it, and a blank outline row is worse than a missing one.

## Document order, not visible order

Entries are ordered with `inDocumentOrder`, **not** `flattenVisible`. An outline
is a map of the document, so a heading nested inside a collapsed toggle is still
one of its sections — it just has no DOM row yet, and `resolve` returns `null`
for it, which the rail already reads as "not on screen". Ordering by what is
visible would make the outline change shape every time the reader folds
something.

## Accepted caveat: a heading you are typing lags ~1s

`block.data.text` is a **~1 s-debounced projection** of the block's live `Y.Doc`
— the editor's per-block CRDT owns the text, and the row is downstream of it
(see `page/editor`'s *Text is doc-owned*). So a heading being actively typed
shows its previous text in the outline for about a second, then catches up.

That is the editor's existing contract and this plugin does **not** work around
it. The two ways it could — reading the live Lexical editor, or shortening the
debounce — are both worse than the lag: a mounted editor is a *view* that can
silently fall behind the doc (and a collapsed heading has no editor at all), and
the debounce is what keeps every keystroke burst from re-running the row write
path for search, backlinks and history.

## `resolve` asks THIS pane's editor

`resolve` reads `blockContentScope` (`page/editor`) — the block grid the editor
this rail belongs to published — and never `document`. The rail renders beside
the pane's scroller, outside the editor's subtree, so it can neither ref that
grid nor walk up to it; the scope is how a sibling asks.
