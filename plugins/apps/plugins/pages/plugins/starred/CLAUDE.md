# starred

Favorites/starred pages, as a **presence-only marker** — not a bespoke sidebar.

- `page_blocks_ext_starred` is a pure presence side-table (one row per starred
  page, no columns of its own beyond the synthesized `parentId`/timestamps).
  Presence = starred; there is no rank/order column.
- The plugin contributes a single `starred` bool `FieldDef<PageRow>` into the
  page-tree's `PageTree.Fields` field-extension seam (`StarredField` closes the
  field's `value` over the starred id set). That makes `starred` a filter
  dimension of the one `pages-sidebar` DataView.
- **One read serves everything.** `useStarredPageIds()`
  (`web/internal/use-starred-ids.ts`) is the only consumer of
  `starredPagesResource`; the field and both toggles go through it, so they
  cannot disagree and every mount shares one subscription tuple.
- **Favorites is a filtered `list` view instance** of the `pages-sidebar`
  DataView (authored in `page-tree`'s config, filtering on `starred = true`) —
  not a separate `Pages.Sidebar` contribution. The DataView's view switcher is
  the sidebar chrome.
- The Favorites **row order belongs to the view** (`data-view/view-order`, keyed
  by `(dataViewId, viewId)`), not to this table. Consequently there is no rank
  column and no reorder endpoint.
- `starredPagesResource` is a **bounded window** (desc `createdAt`, default 500 /
  max 1000), not a point resource: `StarredField` needs `starred` for every row
  the DataView filters over, so a point set would have to name every page id —
  O(pages), which bounds nothing. What is bounded is the favorites set. Star and
  unstar are membership entry/exit and ship incremental deltas. The boundary is
  real: past `maxLimit` favorites the oldest-starred page reads as unstarred.
  Same shape as the sibling `agent-origin` plugin.
- The two star toggles stay: `PageTree.RowActions` (row hover) and
  `PageDetail.HeaderActions` (page header), both flipping `PUT /api/pages/:pageId/starred`.
