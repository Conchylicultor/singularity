# pitch-layout

**How pitch is laid across the screen**, and the app's single choice of keyboard
layout. One switch (`pitchLayoutConfig` — `piano` / `janko`) and one closed
geometry table behind one entry point (`pitchGeometry`), which the falling notes,
the grid rules, the keys under the roll and the chord/key readout chips all lay
themselves out from — instead of each calling a piano formula.

**Everything is a fraction, never a pixel** — X of the axis width, Y of the
keybed height — so one plane serves a two-octave chip and an 88-key roll alike.
The only pixels are `heights`, how tall a keybed or chip a layout WANTS, because
no ratio derives that: four rows of Jankó pads need more room than one row of
piano keys.

**Pads and note columns are two declared outputs, not one.** `keys` are what a
player presses; `columns` are the X bands a pitch's falling notes occupy. They
coincide on the piano and deliberately do not on Jankó, where a pad is two
strides wide (overlapping each neighbour by half, so the keybed has no dead zone)
while a column is the single non-overlapping stride — at pad width a chromatic
run smears into one block. Declaring both is what makes "a note lands on its key"
a property (every pad's center IS its pitch's column center) instead of a
coincidence between two formulas.

**A plane is branded, so a hand-built one does not compile.** `PitchPlane` in
`score/core` carries a module-private `unique symbol`; `markLaidOut` is its only
producer and `pitchGeometry()` is `markLaidOut`'s only caller. Nobody can
assemble "just the pads I need here" with columns that disagree with them. Same
class of guardrail as `PageForestTx` in the page editor.

**`snapRange` is a request/answer, not a validation.** A surface hands over the
range it wants and reads `plane.low`/`plane.high` back for the range it got — so
iterate the plane's range, never your own request. Piano widens outward off an
accidental so its naturals tile flush; Jankó returns the identity. It must be
idempotent and may only widen, or a plane's range would drift on every recompute.

**A neutral leaf owns it**, like `look`, because neither consumer can: if
`piano-roll` owned it the keyboard primitive would import a display plugin
(dragging the roll into the readout chips and the website vignette); if the
keyboard owned it the roll would import the keyboard for its own columns and
grid. The TYPES live one level lower, in `score/core` — the zero-import waist,
which must not drag `config_v2` in. This plugin owns the formulas; the waist owns
the shape, so `Projection` can publish a `pitchPlane` with no display depending
on this plugin.

**Closed record, no slot.** A third layout is a tsc error until it has geometry
here, a label in `config.ts`, and chrome in the keyboard primitive. Per the root
`CLAUDE.md` rule, a set you can enumerate today is plain data.

**Jankó v1 is four rows** — the physical two-row pattern duplicated, so every
pitch has two pads. Read top→bottom the row parities are odd, even, odd, even,
which puts the C row (C D E F♯ G♯ A♯) nearest the player, as on a real Jankó.
`ROWS` is not a knob: `rowsForParity` is written for four.
