## Keyboard transport (per-player, focus-scoped)

Sonata's keyboard transport is **per-player and focus-scoped** — there is no
module-level command bus. Each key goes where its effect is visible:

- **Every shown player** — a `SonataPlayer.Effect`, mounted once per player
  scope while a `PlayerDisplay` is on screen: the Sonata app's player pane and a
  file preview alike, never the library's now-playing bar.
  - **`PlayPauseShortcut`** (`components/play-pause-shortcut.tsx`) — Space
    toggles play/pause via `useSurfaceShortcuts`: eligible only while ITS
    surface is the focused one, its handler closing over THAT player's session.
  - **`SeekHoldController`** (`seek-hold-controller.tsx`) — owns ←/→ via a raw
    window listener (it needs keyup + OS auto-repeat to tell a *tap* — jump one
    bar — from a *press-and-hold* — accelerating bar-by-bar scrub). Being
    outside the shortcut registry, it enforces focus itself
    (`getFocusedSurfaceId() === thisSurface`), yields to a key an element
    already handled (`defaultPrevented` — a file tree walking its rows) and to
    text fields (`targetClaimsKey`).
- **The Sonata app only** — a `Sonata.Effect`, gated on a song being open
  (`currentSongId != null`):
  - **`TempoShortcuts`** (`components/tempo-shortcuts.tsx`) — ↑ / ↓ speed up /
    slow down by `TEMPO_STEP` (`shortcuts.ts`). App-only because the tempo
    control and readout live in Sonata's transport bar; in a preview the keys
    would change the speed invisibly.

Two players inside ONE surface would both register Space (the first registered
wins) and both seek on ←/→; no host does that today. If one does, the
tie-break belongs in the player (focus-within its own root), not here.
