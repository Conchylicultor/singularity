# sample-loader

`sharedSampleLoader(ctx)` — the one `SampleLoader` every smplr instrument built
against an `AudioContext` should be handed as its `loader` option.

## Why

The engine builds one voice manager per **track**, not per instrument. A
two-hand piano score — the most common shape in this app — therefore creates two
`SplendidGrandPiano` instances. Each smplr instrument that is not given a loader
builds a private one and fetches and decodes the whole sample set for itself, so
that score would pay for the grand piano twice.

smplr's loader caches decoded `AudioBuffer`s by resolved sample URL, and an
instrument uses an injected `loader` verbatim in place of the private one it
would have built (`loader` sits in smplr's own `SMPLR_OPTION_KEYS`, so every
instrument factory takes it even though it is not spelled out in that
instrument's own config type). One loader per context is therefore all it takes
to collapse N downloads and N decodes back into one.

Only the **loader** is shared. Each instrument keeps its own **scheduler**,
because silencing a track flushes its scheduler queue and a shared one would
flush every other track's queued notes with it.

## Keyed weakly on the context

The engine builds a fresh `AudioContext` per mount, and React StrictMode builds
two. A module-level singleton would be wrong in both directions: a decoded
`AudioBuffer` belongs to the context that decoded it and cannot be played
through another one, and a loader holding megabytes of samples would keep every
context that ever existed alive. A `WeakMap<BaseAudioContext, …>` gives each
context its own loader and lets the pair go together.

What is cached is the **promise**, not the resolved loader, so callers racing to
create the first loader for a context join one in-flight dynamic import.

## Joining loads that are already in flight

The URL cache inside smplr's loader holds decoded buffers, written only once a
fetch has settled — there is no in-flight entry to hit. That is enough when the
instruments are built at different times, and useless in exactly the case this
plugin exists for: the engine creates every track's channel in a single
reconcile pass, so two piano instances call `load()` in the same tick, both miss
the still-empty cache, and both fetch and decode everything.

So the returned loader wraps smplr's and joins identical concurrent loads onto
one, fanning the single progress stream back out to everyone waiting. The entry
is dropped once the load settles — afterwards the URL cache serves any repeat
instantly, and a failed load must be retryable rather than remembered forever.
A rejection is never swallowed; it reaches every joined caller, and the engine
already renders it as a load error.

Two loads are joined only when the preset **alone** determines the result — that
is, when neither caller injects pre-decoded buffers. That exclusion is
load-bearing. smplr's `Soundfont` decodes its samples itself and passes them in
as `buffers`, under a preset whose `baseUrl` is empty and whose sample names are
bare note names, so two different patches covering the same note range describe
themselves identically; joining them would give one patch the other's sound.

## Which instruments actually benefit

- **Piano** (`SplendidGrandPiano`) — fully. It hands the loader a preset and
  nothing else, so every sample goes through the URL cache. This is the case
  worth the plugin.
- **Soundfont** — not today. It fetches its `<patch>-mp3.js` file and
  base64-decodes every note itself, then passes the finished buffers to smplr,
  which means the loader never sees a URL to cache. Passing the shared loader is
  still correct and costs nothing, and it starts paying the day smplr routes
  soundfont samples through the loader — but a second track on the same
  soundfont patch still decodes that patch a second time. Deduplicating that
  needs a cache of our own, above smplr, and is not part of this plugin.
