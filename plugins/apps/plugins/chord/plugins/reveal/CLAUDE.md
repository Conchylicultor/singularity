# reveal

How much of a chord the trainer shows besides its Roman numeral. Design:
`research/2026-09-20-apps-chord-trainer-reveal.md` (Part 1); the look is the
prototype `proto-1789461303-updb` at `reveal=keyboard`.

## Three values, one axis

| | `off` | `names` | `keyboard` |
|---|---|---|---|
| Song card | — | a key tag: `G major` | same |
| Answer box | numeral | numeral + the chord's name under it | same |
| Chord button | "dominant" | the chord's name | same |
| Below the buttons | — | — | a card: the name, the numeral, and a piano with the chord's notes lit |

`off` ⊂ `names` ⊂ `keyboard`: each value shows everything the one before it
shows. That is **one three-valued choice, not two switches**. A pair of
booleans ("name the chords" / "show the keyboard") would have a fourth
combination — a keyboard with no names — that nobody wants, and would then need
a rule somewhere to suppress it. One axis leaves that combination with no
spelling at all. `core/mode.ts` is the single list the type, the config's
options and the panel's switch are all derived from; the same reasoning, at
length, is in `sonata/plugins/look/core/config.ts`.

It is a `config_v2` enum (`shared/config.ts`, default `off`), so it persists and
appears in Settings → Config. `useReveal()` reads it with plain `useConfig`, not
`useConfigResult`: the document is boot-hydrated and resident, and reveal is a
display preference that makes no claim about the learner's data — a default read
for one frame cannot say anything false about them. The read is narrowed through
`asRevealMode`, which throws on an unknown id (`enumField` types as `string`).

**The switch lives in the side panel**, as its own first row above *Today*
(`<RevealSwitch/>`, rendered by the trainer's `ProgressPanel`). It reads and
writes the config itself, so the panel hands it nothing. It sits there rather
than beside the round because it is a setting about how the learner wants to
practise, and because it must stay reachable whatever the round is doing — the
panel's stats can still be loading behind it.

## The keyboard card

`<RevealKeyboardCard token songKey tonicPc/>` borrows Sonata's keyboard whole,
the way the trainer already borrows Sonata's piano:

- **The plane** — `pitchGeometry("piano", low, high)`. The layout is passed
  explicitly rather than read through `usePitchGeometry()`: that hook reads
  Sonata's own piano/Jankó setting, and the Chord app is not Sonata.
- **The window** (`web/internal/keyboard-window.ts`) — C3–C6, widened OUTWARD by
  whole octaves while a note falls outside, never shifted. `chordVoicing`
  already pins every chord's bass near middle C, so the default fits nearly
  everything and the window stays put: changing chord re-lights keys instead of
  re-laying the keyboard out. Pure and total, with a unit test.
- **The colour** — the card's body is `.chord-tone` carrying
  `chordToneStyle(token)`, the lit map is `pitch → var(--fn-bg)` and the labels
  are `var(--fn-ink)`. That is the one tile-and-ink pair a filled answer box
  already wears, so a lit key reads as the same object as the box above it.
- **The labels** — `noteName(pitch)` on lit keys only, spelled by the song's key
  (`A♭` in E♭, never `G♯`). An unlit key says nothing.

Two invariants worth stating, because both are what stop this card lying:

1. **The lit keys are `chordVoicing`'s own output** — the very call `usePiano`
   plays. One expression feeds the picture and the sound, so they cannot
   disagree about which notes the chord is. (The mockup also draws a greyed root
   an octave below; we do not, because the app never plays that note.)
2. **Nothing is lit before the check.** The card is handed `null`, by
   construction: the trainer's `shownChord` is null until the round is checked,
   so there is no guard here that could be forgotten. With `null` the card draws
   the same keyboard unlit, with a line saying what it is waiting for, rather
   than collapsing — the panel below would otherwise jump every time the
   playhead crossed a rest.

## e2e

`trainer/e2e/trainer-verify.ts` checks the values (the lit `data-pitch` set
against `chordVoicing` computed in the script). `e2e/reveal-shot.ts` checks the
*look*: it fills and checks a round, clicks a chord, and photographs the card
with its keys actually lit — the one thing a value check cannot tell you.

## What lives elsewhere

The naming itself is `vocabulary` (`songVocabulary`, `songKeyLabel`), where the
numeral already lives — this plugin owns the *setting*, the switch and the card,
and nothing pure. Only `trainer` imports it, and nothing imports `trainer`, so
there is no cycle.
