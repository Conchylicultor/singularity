# compare-component

The **Component** stage of the prototype detail pane: the prototype mock on the
left, the real app component it says it mocks on the right, both live, both
interactive, and both at **one width** the reader changes.

It is a separate plugin because it is the only thing in the Prototypes app that
reaches into app internals — the layout-harness fixture catalog. The gallery's
stage set is a slot precisely so that weight lives in one folder.

## The pairing is declarative, and only the prototype declares it

A prototype names its counterpart in its own document:

```html
<meta name="mocks" content="control-panel/setting-rail" />
```

The value is a **layout-harness fixture id** (the ids in Debug → Layout Lab).
Nothing here offers a picker: the prototype is always the source of the pairing.

**The lookup can only be a runtime one.** Prototypes are host-global and shared
by every worktree; fixtures are per-worktree code on a branch. A prototype
naming a fixture that does not exist here is *ordinary* — it may exist on
another branch — so the stage says which id it asked for rather than treating it
as a fault.

## The three states

1. **No `mocks` tag** — the common case. The copy explains how to add the tag.
2. **Declared, unresolvable** — nothing here has that id, *or* it is a **region
   fixture** (`control-panel/region`, `control-panel/pane-region`,
   `section-card/region`, `ui-kit/overlay-panel-region`). A region fixture takes
   the children the harness supplies and has no rendering of its own to put
   beside a mock; those children come from `expandRegionFixtures`, harness
   internals we do not widen the barrel for. Reported as "not renderable here";
   making regions comparable is a deliberate follow-up.
3. **Found** — the side-by-side.

While the catalog loads, a loading state — never state 1's copy, which is a
claim about the user's own file that would then reverse itself.

## Shared width is the whole affordance

One control moves both halves. Not a draggable divider — that trades room
*between* the two, so every reading is a different question.

The widths offered are the matched fixture's own `widths` (fallback
`360 / 640 / 960`), and it opens at whichever is closest to the prototype's
declared viewport width — the width the mock was drawn at, so the one it is
certain to have something to say about.

## Why the mock frame is not `ScaledIframe`

`ScaledIframe` mounts a prototype at its declared viewport and `scale()`s it to
fit, so a 320px box shows the 1280px layout shrunk. Next to a component that
genuinely reflows at 320px, that compares nothing.

So this stage mounts a plain iframe **at** the chosen width, and the prototype's
own media queries run. A prototype authored at one fixed width then crops and
scrolls instead of rearranging — that *is* the answer ("the mock has nothing to
say about this width"), not a defect to paper over with a scale factor. Height
is the prototype's declared viewport height, since an iframe never sizes to its
content.

Sandbox posture is unchanged from every other prototype frame:
`allow-scripts allow-same-origin`, which also keeps cross-document measurement
(the later measured-gap table) reachable from this surface.

`fixture.render()` runs inside a `PluginErrorBoundary`, as in the Layout Lab —
the slot middleware's boundary is the whole pane, which would take the mock down
with it and leave nothing to compare against.
