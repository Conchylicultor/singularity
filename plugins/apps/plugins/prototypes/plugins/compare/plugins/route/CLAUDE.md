# route

Two kinds of counterpart for the prototype canvas's Real app frame, both the **running
app itself** framed at an in-app path. They differ only in how much of the app
the frame shows:

```html
<meta name="mocks" content="route:/agents/c/123" />  <!-- the screen alone -->
<meta name="mocks" content="app:/agents" />          <!-- the whole app, chrome included -->
```

| Kind | Heading | Frame |
| --- | --- | --- |
| `route:` | App screen | chromeless (`?embed=1`): only the surface for that route |
| `app:` | Whole app | with its chrome (`?embed=chrome`): the app rail, the tab bar and the action bar around that route |

Use `app:` when the mock is of the chrome itself (the tab strip, the rail, the
action cluster), or of how a theme reads across chrome and surface together.
Everything else about the two — resolution, widths, framing rules — is one code
path, parameterized by the embed mode.

A whole screen cannot be a fixture: a fixture is a real component with
hand-written props and no routing, live data or pane chrome, so a fixture of a
full screen would be a second implementation that drifts from the real one —
and drift is the very thing the side-by-side exists to catch. So the reference
for a screen is the app as this branch renders it, in an iframe on this
deploy's own origin.

## Chromeless, or with chrome

A `route:` frame loads `embedUrl(target, "chromeless")` — the path with
`?embed=1` — so the document inside renders **no app rail and no tab bar**, only
the surface for that route. An `app:` frame loads `embedUrl(target, "chrome")`
— `?embed=chrome` — so it renders the rail, the tab bar (one tab, booted from
the path) and the action bar, exactly as a fresh browser tab at that path would.
The flag and its readers are `primitives/embed`'s; see that plugin's `CLAUDE.md`
for why it is read once at boot and for the sessionStorage guards that stop the
framed document — in either mode — from touching the host tab's own persisted
tabs.

## Two unresolved answers, one loading one

Both kinds' components are synchronous over the registries the app already holds:

1. The target must start with `/` — a root-relative in-app path.
2. `resolveAppForPath` (apps-core) finds the app owning the path's prefix. None
   → "no app in this worktree owns `<path>`".
3. `parseUrl` (pane) matches the app-local remainder against the registered
   panes. Unmatched **while the deferred plugin tier is still loading** →
   `loading` (the registry fills in as plugins arrive, so "no pane" would be a
   claim that reverses itself a moment later); unmatched once loading settled →
   "`<app>` owns that prefix, but this worktree has no pane at `<path>`".

A query or hash on the target rides along to the frame untouched; only the
pathname decides which pane answers.

## Widths

`480 / 768 / 1024 / 1280 / 1600`, merged with the prototype's declared viewport
width, deduped, ascending. The declared width is always offered — it is the
width the mock was drawn at — and it is where the stage opens; the standard
breakpoints are what make the real app's own responsive behaviour legible
beside it. Height is the prototype's declared viewport height, the same box the
mock half gets.

## No `sandbox`, no `?v=`

**No `sandbox` attribute.** On a same-origin frame `allow-same-origin` makes the
sandbox a no-op as a boundary — the frame can reach the parent and lift its own
restrictions — while it silently withholds modals, popups, downloads and forms,
so a route that opens a file picker would break only inside this stage, the
worst place to discover it. Storage, `BroadcastChannel` and Web Locks are
origin-keyed, so live-state's cross-tab election treats the frame as one more
document either way. Nothing is gained and something is lost.

**No cache-bust.** The counterpart is the live app, not a file on disk; a
prototype edit bumps the version and must not reboot the app beside it. Width
changes are CSS on the frame, so they do not remount it either — the app boots
once per prototype.

## Self-framing terminates

A prototype can declare `route:/prototypes/proto/<its own id>`. The bare path
opens the detail pane on its **first** stage (Focus), so that frame shows the
mock and stops.

But a canvas can hold a Real app frame — and a canvas opened inside a framed
app screen could too — so a path that leads back to a prototype canvas, its
own or another's, could frame the app again, with no floor. So both kinds refuse to frame from inside a framed
document, in either embed mode: when `isEmbeddedDocument()` is true they answer
`unresolved` with a notice, and the recursion stops at depth one whatever path
the prototype wrote.
