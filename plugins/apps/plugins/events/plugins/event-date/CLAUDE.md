# event-date

The **date format** for the Events app: what an extractor says about *when* an
event happens, and everything that reads that statement back. A leaf — `core/`
only, `zod` and nothing else, so `events-core` can import it.

Five files that move together or not at all: the schema (`event-date.ts`), what
it **means** (`expand.ts`), the human sentence and the projection onto the
`events` columns (`describe.ts`), what makes two dates the same event
(`identity.ts`), and how it is explained to the model (`prompt-spec.ts`). Split
across plugins each pair drifts silently: a prompt documenting a key the schema
rejects is a terminal failure on a real page; a schema key the prompt never names
is a key no model fills. One folder is what makes the format *customizable*
without a four-plugin audit.

## One row per series — so identity is the rule, not the anchor

A recurring event is ONE row carrying a rule, never N materialized occurrences.
That makes `eventDateIdentityKey` load-bearing (`events` is unique on
`(source_id, external_id)`, so identity IS idempotence):

- **`once` → the UTC day key of `startsAt`**, byte-identical to the engine's
  pre-recurrence `startsAtDateKey`. Keep it that way: the equality is what stops
  a deploy re-minting every existing one-off row's identity.
- **`recurring` → a canonical signature of the RULE, independent of the anchor.**
  The anchor moves — next week's extraction reports next week's Thursday — so
  anything derived from it mints a new row every refresh. Members are sorted and
  de-duplicated (listing order must not change identity); `until`/`count` are IN
  the signature, because a series that ends is a different series.

## Two arms, and a third deliberately absent

`once` and `recurring`. An irregular published date list ("Aug 13, Aug 20,
Sep 3") is **not** a third arm — it is exactly what the extraction flag channel
exists to report. `EVENT_DATE_PROMPT_SPEC` says so to the model: when a schedule
cannot be expressed exactly, emit the next occurrence as a `once` and add one
entry to the response's global `flags`. Never approximate, never one row per date.

## Purity and termination

`expandEventDate`/`nextOccurrence` read no clock and mutate no input.
`nextOccurrence` is on the **write path** (the engine normalizes a model's anchor
through it), so a non-deterministic result would rewrite the same row every run.
It returns `{found:false, reason:"exhausted"}`, never `null` — a spent series is
a legitimate answer the engine acts on, not an absorbable failure. A rule that
can never fire (`daily` every 7 days filtered to a weekday the anchor's phase
never hits) also reports `exhausted` rather than spinning.

## Documented limitation: no timezone database

**All calendar arithmetic is UTC** — also why the same series expands, and the
same identity derives, on whichever machine runs it. `startsAt` is an instant
carrying the page's own offset and the expander advances it in whole UTC days, so
a weekly 23:00 event crossing a DST boundary **shifts by an hour on the read
side**. One row per series keeps that out of storage entirely: the stored anchor
is always an exact published instant, so only a derived far-future occurrence can
be off, and re-reading the page re-anchors the series anyway.
