# entry-points

The composition detail pane's entry-point editor: the roots the closure is
resolved from, as removable chips plus an add-search over every known plugin id.

Entry points are the composition's *seed*, not a preference — everything the
Summary counts and the Closure section tints is reachable from this list. An
empty entry-point list resolves to an empty bundle, which is why a new
composition looks inert until one is added.

`allIds` (the searchable candidate set) comes from `useCompositionData()` — the
full registry, not the current closure, since the point of the control is to
reach plugins the draft does not yet include.

## Two rows are read-only

Main's row and `base-exclusions` render their entry points as plain chips: no
remove button, an inert Add, and a note naming
`plugins/plugin-meta/plugins/composition/core/config.ts`. Those two decide what
the app SHIPS, and codegen emits the registries and the docs from the committed
config — so an edit stored in the user layer would look like a change and never
reach a generated file. `isCommittedSourceComposition(id)` is the predicate, the
same one `useManifestActions().save` throws on, so the inert control and the
boundary beneath it cannot disagree about which rows they mean.

Inert rather than hidden, following `serve-target-panel`'s non-servable
composition: reading those entry points is exactly why someone opens the row.
