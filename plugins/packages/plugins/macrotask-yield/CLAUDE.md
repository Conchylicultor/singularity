# macrotask-yield

`yieldMacrotask()` resolves on a later event-loop turn: `scheduler.yield()`
where the runtime has it, else `setImmediate`, else `setTimeout(0)`. Timers and
I/O callbacks that are waiting run before the caller continues.

`await Promise.resolve()` does not do that. A microtask runs before the loop
moves on, so a due timer keeps waiting through any number of microtask yields —
a loop written that way looks cooperative and still holds the thread.

Use it to cut a long synchronous loop into slices on a thread that other work
shares: yield every ~10 ms of work. The server warm-up drain and the corpus
index yield between units with it; check code yields with it in any CPU loop
over thousands of items (every check in a pass shares one thread — see
`tooling/checks/CLAUDE.md`).

## Concurrent callers: `createTurnQueue()`

Callers that yield at the same moment resume together: the runtime runs every
callback queued for a turn before it looks at its timers again. So N tasks that
each `await yieldMacrotask()` and then work run their slices back to back. The
yield separated each task from its own past, not from its peers. For a loop's
periodic breath that is fine — one round costs N × one slice. It is wrong when
every task's next slice is long.

`createTurnQueue()` returns a function whose every call resolves on its own
turn, in call order. A call's yield is queued only once the previous call's
turn has arrived, so a full loop turn (timers, I/O) separates consecutive
callers. The check runner starts every check through one: ~100 checks'
synchronous start-ups used to run as one block before any timer fired.

The browser-only `yieldToMain` (`primitives/perfs/plugins/scheduler/web`) is a
separate helper with a `postTask` tier for the deferred plugin boot; this one is
runtime-neutral `core`.
