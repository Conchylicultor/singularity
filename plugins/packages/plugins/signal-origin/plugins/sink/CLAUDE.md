# sink

The **contract** for `~/.singularity/signal-origin.jsonl` — the host-global
record of who killed a `./singularity build|check|push`: the path, the line
shape, and the bounded read. One JSONL line per catchable fatal signal, plus one
when the native tap could not be armed.

The append itself stays in the CLI (`bin/signal-origin-log.ts`), the only writer,
on a death path where nothing may be awaited.

## Why the contract is here and not in the CLI

`bin/` is unreachable across plugin boundaries, so a backend answering "who
killed build X?" would otherwise have to re-derive the path and re-type the
lines — one record with two independent definitions, drifting silently (a
renamed field makes the reader return nothing, and fails no build). Declared
here, a change is a `tsc` error at the other end.

It is a **sub-plugin** rather than part of `signal-origin/core` because that
barrel is the FFI-free *and web-safe* half (`build-info` imports
`formatSignalOrigin` from it), while this one reaches `node:path` /
`SINGULARITY_DIR`. Same split as `infra/file-sink/core`.

## Reading

`readSignalOriginLines()` goes through the file-sink primitive's bounded reader
with `includeRotated: true` — unlike a live tail, every question asked of this
file is about ONE past run, and a busy host rotates past it. A torn last line is
the normal case here (the writer is a process mid-death) and is skipped. A
missing file folds to `[]` at the call site: no op on this host has ever caught a
fatal signal, which is a legitimately empty history, not a failure.
