# zod-parser

`ZodParser<T> = z.ZodType<T, z.ZodTypeDef, unknown>` — the type of a schema that
parses **untrusted input** into a `T`. Use it at every parse boundary.

**Why not `z.ZodType<T>`.** In zod v3 the type is `ZodType<Output, Def, Input>`
and `Input` defaults to `Output`, so `z.ZodType<T>` asserts the value going *in*
is already a `T`. At a parse boundary — a jsonb column, a request body, a
WebSocket payload — that is false, and it excludes exactly the combinators that
bridge the gap: `.default()`, `.catch()`, `.coerce()`, `.transform()`,
`.preprocess()`.

The quiet failure is the one to know about: where a type infers *through*
`ZodType<infer U>` instead of taking it as a parameter, a wide-input schema does
not error — it silently resolves `U` to the schema's **input** type, so the
consumer gets a row type that disagrees with `.parse()`. `ZodParser<infer U>`
recovers the output type.

Costs nothing on `Output` (still pinned to `T` exactly) or at runtime. `Input`
goes opaque only on values *annotated* `ZodParser<T>`; concrete schemas keep
`z.input<S>` and the `.default()` argument check at their definition site.

**`lint/no-narrow-zodtype`** bans the one-argument `ZodType<T>` repo-wide. Zero
arguments (a bare `z.ZodType` constraint) and three (`z.ZodType<T, z.ZodTypeDef, T>`)
both pass — a site where input genuinely *is* output can still say so, explicitly
rather than by accident. The rule file is deliberately self-contained (plain
`@typescript-eslint/utils`, no `@plugins/*`): jiti loads it in the ESLint config
and cannot resolve those aliases.

**Why `packages/`.** It must be importable from `fields/core`,
`resource-runtime/core`, `endpoints/core` and `live-state/core` with no cycle
risk. It imports nothing but `zod` types, so `resource-runtime`'s stated policy
of depending on "only the `packages/…` leaves" still holds.
