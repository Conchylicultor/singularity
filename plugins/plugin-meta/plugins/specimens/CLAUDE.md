# specimens

A place for a plugin to exhibit one of its **real** components on its own, so
another surface can render it standalone — inside the running app, with real
slot contributions, config and data. The first consumer is the Prototypes
Compare stage's `component:` kind, which puts a specimen beside a mock.

## Registering one

In the plugin that owns the component (never anywhere else — a specimen is how
the owner exhibits its own private component, so nothing needs a deep import):

```ts
Specimens.Specimen({
  match: "task-draft/composer",  // the id: `<plugin>/<name>`, globally unique
  label: "Task composer (Improve)",
  widths: [360, 480, 640, 900],  // optional: where it changes shape
  component: ComposerSpecimen,   // ComponentType<SpecimenProps> (gets its id)
})
```

## The contract a specimen meets

- **Standalone.** Renders at any width with no ancestor but the app itself.
- **Self-contained state.** Holds what it needs locally (text, toggles), seeded
  from the same defaults the real host uses.
- **An exhibit, not a working copy.** Never submits, navigates, or writes to
  the database. Typing into it is fine; filing a task from it is not.

## Looking one up

`useSpecimen(id)` → `found { specimen }` | `missing` | `ambiguous { specimens }`
— metadata only. Render with `<Specimens.Specimen.Dispatch id={id}/>`, which
isolates it in the slot's error boundary like any contribution. Two
plugins claiming one id is reported, never resolved by registration order.
`missing` is ordinary for a consumer whose ids come from outside the repo (a
prototype naming a specimen that exists only on another branch).

A dispatch slot keyed on the id, not a render slot: a consumer picks one entry,
so there is no list order to curate.
