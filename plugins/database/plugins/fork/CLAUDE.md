# fork

Durable, self-healing per-worktree database forks.

`createConversation` (in `conversations`) enqueues the `database.fork` job
instead of calling `forkDatabase` fire-and-forget. The job is a
`defineSupervisedJob` with a `run` body: the fork (`pg_dump | pg_restore`) runs
in a detached `./singularity supervised-exec database.fork` child, so **a backend
restart or deploy no longer interrupts a fork** — the child keeps going and
whichever backend is alive when it exits records the outcome.

- **In-flight lock:** the built-in ledger's open `supervised_job_runs` row keyed
  by `lock: target`. A second enqueue for the same target loses its claim while
  a fork runs.
- **Retries:** `runAttempts: 5`, with a durable backoff (~3, 7, 20, 55 s) between
  attempts. A `ForkPlanError` is deterministic, so it becomes a
  `NonRetryableError` and dead-letters at once (after its bell).
- **Where failures show:** the `DB fork failed` bell, a dead `database.fork` in
  Debug → Queue carrying the child's error, and the transcript in the
  `database-fork` log channel (`logs/database-fork.jsonl` of the supervising
  backend — main in practice). Both notifications are written from the child.

The fork itself (`forkDatabase` in `database/admin`) is idempotent and
atomic-publish (populate a unique `f_*__forking` temp, rename to the canonical
name as the last step), which is the precondition that makes retry safe.

This lives in its own plugin rather than `database/admin` because
`infra/jobs` already imports `connectionString` from `database/admin`; a
job consumer back in `admin` would close an import cycle
(`database/admin → infra/jobs → database/admin`). Extracting the jobs here
keeps the graph a DAG: `database/fork → {infra/jobs, database/admin}`.

`database.fork-temp-sweep` is a scheduled (every 15 min, main-runtime-only)
reaper for orphaned `*__forking` temp DBs left by a failed or killed fork. It
skips any temp with active connections, so a fork whose detached `pg_restore` is
still running is never dropped out from under it.
