# migrations

## Two kinds of migration

Migrations live in `data/` as `<ts>_<sha8>__<slug>.sql`. The runner
(`server/internal/runner.ts`) applies them in timestamp order (a phased schema migration pulls the data
migrations it claims into its own group — see **Phased schema migrations**) and tracks applied
state by the **filename `sha8` hash** — it never reads drizzle snapshots, nor
`meta/_journal.json`. The `sha8` MUST equal the hash of the file's content, or
the runner's identity drifts from what it executes.

`meta/_journal.json` is derived from those filenames and regenerated
unconditionally by `generateMigration` (`framework/cli/plugins/migrations/cli/migrations.ts`) — so
`./singularity build` is the fix for any journal/`.sql` mismatch. It stays
tracked in git for a non-obvious reason: it is the merge sentinel that triggers
post-rebase migration normalization. See `framework/cli/CLAUDE.md` before
touching it.

- **Schema migration** — generated by drizzle from `schema.ts`
  (`./singularity build --migration-name <slug>`). Carries a sibling
  `meta/<tag>_snapshot.json`. The snapshot links into the snapshot DAG enforced by
  the `snapshot-chain-intact` check (a single chain, except where a merge node
  joins two — see **Merge nodes**). Never hand-edit the SQL: it must match the
  snapshot's DDL, and the push-time hand-edit detector aborts if it doesn't.

- **Data / backfill migration** — DML only (UPDATE/INSERT/DELETE), created freely
  with `./singularity build --custom-migration --migration-name <slug>`. No human
  approval gate: two automated checks back it up instead —
  `data-migration-dml-only` (proves it contains no schema changes) and
  `migration-applies-clean` (a transactional dry-run against main, rolled back,
  that proves it applies before push — see **Pre-push verification** below). It has
  **no snapshot**: a backfill changes no schema, so it is deliberately kept out of
  the snapshot chain. Why this matters:
  - It can never Y-fork against a schema migration main adds concurrently, so it is
    **push-safe** regardless of main movement (no "quiet window" needed).
  - drizzle bases the next schema migration on the last *schema* snapshot, which is
    correct since the backfill has zero schema delta.
  - You **hand-edit** the generated empty SQL to add the backfill. It is re-hashed
    on every build (`rehashBranchLocalDataMigrations` in `cli/plugins/migrations/cli/migrations.ts`)
    so the filename hash always tracks the content — editing it re-applies once per
    DB (with a loud drift warning for the old hash), never a silent skip.
  - It is enforced **DML-only** by the `data-migration-dml-only` check, so it cannot
    smuggle schema changes past `schema.ts`. To change the schema, edit `schema.ts`
    and generate a schema migration instead.

## Published migrations

A migration is **published** once it exists on any `main` this checkout knows
of: local `main`, or any `refs/remotes/<remote>/main`
(`core/internal/published.ts`). For the author that is `main` + `origin/main`;
in a clone, local `main` holds the user's own migrations and `origin/main` (or
`upstream/main`) the author's; in a fork, `origin/main` + `upstream/main`. The
union needs no remote classification, so it is offline and side-effect free.
Everything in `data/` that is not published is **branch-local** — the only
files the generator may reset (`--reset-migration`, push's `regen-migrations`),
re-hash, or claim. Every consumer (the CLI generate pipeline, `regen-migrations`,
`migration-phases-valid`, `migration-hashes-unique`) reads the set through
`publishedMigrationBasenames`, and a check whose verdict depends on it folds
`publishedMigrationRefsSignature` into its cache signature. No local `main` is a
loud error, never an empty set.

**A published migration is immutable.** Its sha8 is in deployed ledgers and its
snapshot is a link of someone's chain, so it is never edited, deleted or
renamed — change the schema with a new migration. The
`published-migrations-immutable` check (`check/published-immutable.ts`, logic in
`core/internal/published-immutable.ts`) enforces it: for every published ref R,
every `.sql` and `meta/*_snapshot.json` present at `merge-base(HEAD, R)` must be
in the working tree byte-identical (so a branch merely behind R passes), and
each such `.sql`'s filename sha8 must be its content hash (a closed list of 15
pre-invariant files excepted). `_journal.json` (regenerated) and the
`_*_answers.json` sidecars (read by neither the runner nor drizzle) are not
covered. `regen-migrations` asserts the same function before push's reset.

## Merge nodes

Merging another `main` (an upstream update, `./singularity upstream merge`)
forks the snapshot chain at the merge base: user A→U1→U2, upstream A→P1→P2.
Both sides are published, so the fork is **joined**, never rebased. After
`--reset-migration` and before drizzle-kit, `generateMigration` runs
`joinSnapshotTips` (`framework/cli/plugins/migrations/cli/snapshot-join.ts`):

- 0–1 tips: nothing to do.
- Several tips, one of them branch-local: a rebase Y-fork — refused with the
  `--reset-migration` hint.
- Several published tips: it writes a **merge node**, a phased migration with
  empty sections behind one header line (grammar: `core/internal/phases.ts`):

  ```sql
  -- singularity:merge-snapshot parents=<snapshotIdA>,<snapshotIdB>
  -- singularity:phase expand
  -- singularity:phase contract
  -- singularity:claims
  ```

  Its snapshot is the **3-way merge** of the tips against their nearest common
  ancestor (`snapshot-merge.ts`: plain objects by key, arrays and scalars as
  leaves; `id` / `prevId` / `_meta` excluded), with `prevId` = the parent that
  sorts last. Its SQL does nothing because each side's own migrations already
  apply that side's DDL — on the user's DB (their side applied, upstream's
  pending) and on a fresh one (everything in timestamp order) alike. drizzle-kit
  then diffs `schema.ts` against the merge node, so it emits only what the merge
  resolution itself changed. The runner plans it as an empty group: a ledger row
  and nothing else.
- Both sides changed the same path differently (one drops a table the other
  alters; both add `note` with different types): the build fails listing each
  path — `tables.public.foo.columns.note.type: ours=text theirs=integer
  base=<absent>` — and writes nothing. Which side wins is the user's call;
  never resolve it by editing a published migration.

The node is a pure function of its parents: the snapshot id is derived from the
parent ids, the timestamp is one second after the latest migration on disk
(and `renameMigrations` never stamps at or before an existing one). Push's
normalize resets it as branch-local and writes it back byte-identical.

**drizzle-kit never reads `data/` directly.** Its `prepareMigrationFolder` exits
0, writing nothing, whenever two snapshots share a `prevId` — which every
merged history has, forever. `stageDrizzleOut` (`core/internal/drizzle-stage.ts`)
gives it a throwaway out-dir holding only the journal and the DAG's single tip;
the CLI moves what it emits back into `data/`, and `migrations-in-sync` reads
it in place. The DAG itself (edges = `prevId` + merge-header parents; one root,
one tip, every node reachable, no duplicate ids, every parent present) is
`core/internal/snapshot-dag.ts`, shared by the join and `snapshot-chain-intact`.

## Phased schema migrations

A real change often needs **add schema → move data → remove schema** in one
push. Filename timestamps cannot express that (a push re-stamps its schema
migration to push time, after every data migration), so the ordering is
declared in the schema migration itself. At generation — in `generateMigration`
(`framework/cli/plugins/migrations/cli/migrations.ts`), before the content is
hashed — every freshly generated schema migration is rewritten into marked
sections (grammar: `core/internal/phases.ts`):

```sql
-- singularity:phase expand
ALTER TABLE "agents" ADD COLUMN "icon" text;
-- singularity:phase contract
ALTER TABLE "agents" ALTER COLUMN "icon" SET NOT NULL;
ALTER TABLE "agents" DROP COLUMN IF EXISTS "icon_svg_nodes";
-- singularity:claims
-- 20260927_182347__remap_saved_icons_to_symbols
```

The runner applies one push as one group: **expand → the claimed data
migrations (timestamp order) → contract**. So a data migration sees the schema
**after expand and before contract**: every new table and column exists, and
nothing the push drops or tightens has been dropped or tightened yet. Files
without the markers (everything written before this, and every data migration)
are legacy and apply whole at their own timestamp.

### What is expand and what is contract

The split is a closed statement table (`core/internal/classify.ts`), not a
judgement per migration:

- **expand** — existing rows and the code already deployed stay valid:
  `CREATE TABLE`, non-unique `CREATE INDEX`, `CREATE SEQUENCE` / `DOMAIN`,
  `ADD COLUMN` that is nullable or has a `DEFAULT`, `SET DEFAULT` /
  `DROP DEFAULT`, `DROP NOT NULL`, `DROP CONSTRAINT`, `DROP INDEX`,
  `ENABLE` / `DISABLE ROW LEVEL SECURITY`, and **renames** (`RENAME COLUMN`,
  `RENAME TO`) — so a data migration reads and writes the NEW names.
- **contract** — restrictive or data-destroying: `DROP TABLE`, `DROP COLUMN`,
  `DROP SEQUENCE` / `TYPE`, `SET NOT NULL`, `SET DATA TYPE`, `ADD CONSTRAINT`
  (drizzle's `DO $$ … ADD CONSTRAINT … FOREIGN KEY … EXCEPTION … $$` form
  included), `CREATE UNIQUE INDEX`.
- **auto-split** — `ADD COLUMN c T NOT NULL` with no `DEFAULT` becomes expand
  `ADD COLUMN c T` plus contract `ALTER COLUMN c SET NOT NULL`. A new required
  column plus the backfill that fills it is therefore one push.
- **rejected** — `CREATE` / `DROP VIEW` (views are derived code, see
  `derived-views`), `ALTER TYPE … ADD VALUE` (a new enum value is unusable in
  the transaction that adds it, and the boot schema layer is one transaction),
  and DML (it belongs in a data migration).

Anything the table does not recognise **fails generation**, naming the
statement, and the generated file is discarded. Extend the table when the
statement is legitimate; never hand-edit the generated SQL.

### Claims

A new schema migration claims every **branch-local** data migration (snapshot-
less, not published — see **Published migrations**) that no other branch-local schema migration
already claims. A claim is `<timestamp>__<slug>` — the filename minus its hash,
which re-hashing changes. After push's `regen-migrations` the single `merged_*`
file claims all of the branch's data migrations, so a push is one explicit
group. A data migration nothing claims (a data-only push) runs at its own
timestamp, as before.

So the recipe for "move data into a new shape and drop the old one" is one
push, in any order: change `schema.ts` (add the new shape, remove the old),
write the backfill with `--custom-migration`, build. Make the backfill
idempotent (`ON CONFLICT DO NOTHING`, guarded `UPDATE … WHERE`): it is re-hashed
and re-applied whenever its content changes.

The `migration-phases-valid` check (`check/migration-phases-valid.ts`) fails the
build when a branch-local schema migration is not phased, when a statement no
longer classifies into the section it sits in, or when the runner's own
`planSchemaSteps` refuses the files on disk (a claim resolving to no data
migration, to one sorting after its claimer, or to one already claimed) — so a
claim error fails the build, not the boot.

## Views never block a migration

Plain views are derived code (`database/derived-views`), rebuilt from source at
the end of the one boot schema-layer transaction. When any migration is pending,
that transaction first drops every live `public` view (`dropDerivedViews`), so a
migration that drops or retypes a column a view reads just works, and the
previous backend never reads a missing view during a hot-swap. Never hand-add
a `DROP VIEW` to a schema migration: push regenerates schema migrations and
refuses hand-edited ones.

## Pre-push verification

The only way a migration "breaks main" is by erroring during boot
(`onReadyBlocking` → `applySchemaLayer`), so the server never comes up. The
`migration-applies-clean` check (`check/index.ts`) catches that automatically
before push:

- **Fast path** — if this branch changes no file under `data/` vs local `main`
  (the ref the main DB runs) there are no pending migrations, so it passes instantly with **no DB
  connection** (the ~99% case).
- **Slow path** — otherwise it opens a direct connection to the live **main** DB
  and calls `dryRunPendingMigrations` (`server/internal/runner.ts`), which is
  `applySchemaLayer(…, { commit: false })`: the very function boot runs (drop the
  live views, the phased steps, derived updatedAt, derived tables, rebuild the
  views, all in one transaction) ending in a sentinel throw that **always rolls
  back**. The check process never boots, so it hands the layer its inputs itself
  — views, derived tables and updatedAt specs read from main's server barrels
  (`check/internal/declared-schema-inputs.ts`); registry reads would come back
  empty there. Applying against main's real schema + data reproduces the boot
  failure exactly, while the rollback leaves main untouched. A real apply error
  is surfaced with the offending filename + the pg error.
- `SET LOCAL statement_timeout = '60s'` is the load-bearing bound on how long the
  dry-run can hold locks on live main; `lock_timeout = '1s'` bounds lock
  acquisition so it can never queue behind live traffic. Postgres DDL+DML are both
  transactional and `LISTEN/NOTIFY` only fires on commit, so a rolled-back apply
  is side-effect-free.
- Caveat: a rolled-back `INSERT` still advances serial/identity **sequences**
  (`nextval` is non-transactional), so a dry-run can leave harmless ID gaps. No
  data changes; nothing to fix.

The check runs uniformly in `./singularity build`, `./singularity check`, and the
push checks step — which runs after rebase + migration normalization, i.e. when
the branch-local migration set is final and local `main` is fresh.

## Checks run BEFORE migrations apply

In `./singularity build` the checks pass runs before the restart that applies
pending migrations, so the live DB is at the *previous* boot's schema. A check
comparing live schema against the head drizzle snapshot must therefore gate on
"the DB applied every migration on disk" (read `__singularity_migrations`) and
decline while behind — otherwise a `DROP TABLE` migration wedges the build
permanently: checks abort it before the restart that would make them pass.
`orphaned-db-tables` does this; `fork-schema-drift` asks an order-independent
question and needs no such gate.

Every direct (non-pgbouncer) DB connection a check opens goes through
`withDirectDb` (`check/internal/direct-db.ts`) — never a hand-built `Pool`. It
owns the one connect timeout (60 s): the timer counts wall-clock on the check
process's own thread, which a full pass keeps busy for 8–16 s, so a shorter
bound fails against a healthy Postgres. And it returns "could not connect" as a
typed arm (`unreachable` / `no-database`, decided by a probe connect before the
callback runs, so the callback's own errors are never reclassified) — each check
must decide explicitly what "cannot look" means for its verdict. See
`research/2026-09-11-global-check-db-connect-timeout-aborts-run.md`.

## Schema files must be synchronously loadable

Schema-glob files (`server/**/internal/{tables,tables-*,schema,schema-*}.ts`) must
be leaf modules that are synchronously `require()`-able: drizzle-kit loads each via
a sync `require()`, so an async-only import (top-level await, e.g.
`lexical`/`@lexical/yjs` reached transitively through a plugin barrel) anywhere in
their import graph makes drizzle-kit throw-but-exit-0 and **silently drop the
table** from migration generation. Keep these files importing only synchronous
modules; the `schema-files-loadable` check enforces this invariant.

## Which files are schema files

The glob set is declared **once**, in `core/internal/schema-glob-patterns.ts`
(`SCHEMA_GLOBS`), repo-root-relative. Two independent consumers read it and must
agree:

1. `core/drizzle.config.ts` builds its `schema:` array from it, re-anchoring each
   pattern with `REPO_ROOT_FROM_MIGRATIONS_DIR` — drizzle-kit resolves a relative
   glob against its **CWD** (this plugin's dir), not against the config file.
2. `schemaGlobFiles(root)` (`core/internal/schema-glob.ts`) expands the same
   patterns with `Bun.Glob`; this is how the `schema-files-loadable` and
   `table-defs-in-schema-glob` checks enumerate their scan surface.

Their agreement is **proved**, not asserted: the
`database-migrations:drizzle-config-schema-globs` check imports the real config,
set-diffs its evaluated `schema:` against `SCHEMA_GLOBS`, and separately asserts
that the hop back to the repo root lands exactly there. This replaces a
text/regex parse of `drizzle.config.ts` that could silently return a **subset**
(a `schema: [` occurring in prose, a `]` inside a glob character class, a
non-literal array element) — which would have made both checks inspect fewer
files than migration generation does and keep passing while a table silently
vanished.

Two consequences when editing:

- **Never inline a literal array into `drizzle.config.ts`'s `schema:`** — add or
  change the pattern in `SCHEMA_GLOBS`.
- **`schema-glob-patterns.ts` must stay import-free.** drizzle-kit loads
  `drizzle.config.ts` through a synchronous `require()`, so anything that module
  pulls in (`fs`, `Bun.Glob`, a plugin barrel) becomes subject to the same
  sync-loadability constraint as a schema file.

## How drizzle-kit is invoked

Never by hand. `drizzleGenerateArgv({custom, name, configPath})` (`core` barrel,
declared in `core/internal/drizzle-cli.ts`) is the only argv builder: it welds the
binary name to `generate` and takes typed flags, so no caller can express another
subcommand. `generate` is the only one that works — every other (`push`, `migrate`,
`studio`, `pull`) dials `drizzle.config.ts`'s deliberately non-resolving `.invalid`
credentials. It also owns the `bunx --bun` preamble: without it Node honours
drizzle-kit's `#!/usr/bin/env node` shebang and the child dies on `Bun.which()` with
exit 0 and no migration written. The `drizzle-cli-safety/no-adhoc-drizzle-cli` lint
rule (`lint/`) catches a hand-written argv; naming the binary as *data* is not an
invocation and is not flagged. It always passes `--config=core/drizzle.config.ts`
(`DRIZZLE_CONFIG_PATH`, or the caller's `configPath`): the config lives in `core/`
because a plugin has no loose root files, and drizzle-kit only finds a config on its
own when it sits in the cwd.

## Where drizzle-kit runs from

`MIGRATIONS_PLUGIN_DIR` lives in the same module as `SCHEMA_GLOBS` and is **exported
from the `core` barrel** — it is the one declaration of this plugin's repo-relative
dir, and every sanctioned invocation uses it as the child's `cwd`:

- `check/internal/schema-files-loadable.ts` — the require-probe's cwd (a probe, not
  a drizzle-kit invocation).
- `framework/tooling/.../checks/plugins/migrations-in-sync` — the check that proves
  the committed migrations match `schema.ts`.
- `framework/cli/plugins/migrations/cli/migrations.ts` — the real `./singularity build` path.

The cwd is **load-bearing, not incidental**. drizzle-kit resolves every relative path
in `core/drizzle.config.ts` against its CWD rather than against the config file — both the
`schema:` globs (re-anchored with `REPO_ROOT_FROM_MIGRATIONS_DIR`) and `out: "./data"`.
Run generation from the wrong directory and the globs expand to **nothing**: drizzle-kit
exits 0 having discovered no tables and writes no migration. A silent DROP, not an
error. That is why the three call sites share one constant instead of each carrying a
copy of the literal — a copy that drifted would fail exactly this way.

The constant is the repo-relative **dev-tree source location**. It is deliberately NOT
the runtime migrations dir: the runner reads
`SINGULARITY_MIGRATIONS_DIR ?? <runner dir>/../../data` (`server/internal/runner.ts`),
and a released bundle points that env var at `<bundle>/migrations/data`. No runtime
path reads `MIGRATIONS_PLUGIN_DIR`.

`SCHEMA_GLOBS` and `REPO_ROOT_FROM_MIGRATIONS_DIR` stay **internal** — they have no
cross-plugin consumer, and the `drizzle-config-schema-globs` check already proves the
only agreement that matters.

> Known remaining duplication: the derived `data/` path
> (`plugins/database/plugins/migrations/data`) is still hand-written in ~11 places
> across `cli/`, `checks/` and this plugin's own `check/`. Three of those use it as a
> **git pathspec** (`git diff -- <path>`, `git ls-tree -- <path>`), where a wrong path
> exits 0 with empty output rather than erroring — the same silent class as above. See
> `research/2026-07-29-global-migrations-plugin-dir-single-source.md`.
