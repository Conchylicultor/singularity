# sweep

The backstop half of `createTestDb`'s lifetime. `drop()` runs in the suite's
`afterAll`, so it reclaims the throwaway on every path the test process survives
— and on no other. A killed run (Ctrl+C, crash, OOM, SIGKILL) leaves a
fully-migrated database on the shared cluster; this hourly job reclaims it.

**A hook is not a lifetime.** The lifetime has to be legible to a later process
that never saw the mint, so the name carries both facts
(`<prefix>_<pid>_<base36 mintedAt>__testdb`, minted and read back by
`db-test-fixture/core`) and this job reads them off the catalog.

A candidate needs BOTH conditions — neither is sufficient alone:

- **Past the TTL** (6h). A fresh mint is briefly connection-less between
  `ensureDatabase` and the pool opening, so connections alone would let the sweep
  delete a database out from under the run that just created it.
- **Zero active connections.** A suite paused under a debugger is old but alive.

A `__testdb` name that does not parse **throws** rather than being skipped:
nothing else mints that suffix, so a non-conforming body means the grammar has
torn.

**Every drop files a `test-database-leaked` report.** A sweep that deletes
quietly is indistinguishable from data going missing, and the facts worth
keeping (which suite, which pid) live in the name the drop destroys — so the
report is both the receipt and the only surviving evidence. Deduped per suite
prefix, since "this suite's runs keep being killed" is the unit anyone acts on.

Main-runtime only and `singleton` — databases are a global cluster resource, so
one sweep covers every worktree (same shape as `database.fork-temp-sweep`).

**Why a child plugin, not a file on `db-test-fixture`:** the fixture must stay
jobs-free — `infra/jobs`' own test suite imports it, so a fixture importing jobs
would close an import cycle. Same split, same reason, as its sibling
`worktree-db`.
