# worktree-db

`worktreeDbScenario(body)` opens a transaction on the REAL worktree database,
runs `body(tx)`, and always rolls it back — nothing is ever committed, so a
suite leaves behind no rows, no emissions, no enqueued jobs. It also installs
the `graphile_worker` schema once per process first (excluded from the worktree
DB fork by design, so a never-booted worktree has none, and any mutation that
emits a status change enqueues on the caller's transaction).

Use it ONLY when a `createTestDb` throwaway genuinely cannot reproduce what is
under test — today that means reading the derived VIEW layer (`tasks_v` /
`task_blocking_v`), which is rebuilt from source on every boot rather than being
migration schema. For anything table-only prefer the parent fixture: a throwaway
is isolated and can hold two concurrent COMMITTED transactions, which a
rolled-back scenario cannot.

**Every failure inside a scenario must be a JS-level `throw`.** Bodies keep
reading from the same `tx` after an asserted rejection; a *Postgres* error
aborts the transaction and every later statement fails with "current transaction
is aborted". A case failing on a constraint violation or a bad cast needs its
own savepoint.

**Why a child plugin, not a function on `db-test-fixture`:** the fixture must
stay jobs-free — `infra/jobs`' own test suite imports it, so a fixture importing
jobs would close an import cycle. Parent and child are independent plugin ids,
so `worktree-db → infra/jobs` and `infra/jobs (test) → db-test-fixture` coexist
acyclically.
