# supervised-task

An out-of-process body that is **not a command line**.

`supervised-run` supervises an argv. Build, release and deploy each have one; a
backup does not — it is ~11 contributed `BackupSource`s staged into a directory,
one `tar`, and ~2 contributed `BackupTarget`s. That is why backup was the last
durable job whose work still died with its backend. A task is the argv that
stands for such a body:

```
./singularity supervised-exec <taskId> <payloadJson>
```

```ts
export const backupTask = defineSupervisedTask({ id, payload: zodSchema, run });
export default { register: [backupTask, backupJob] } satisfies ServerPluginDefinition;

defineSupervisedJob({ …, task: (input, runId) => backupTask.invoke({ runId, … }) });
```

Detach, pid, transcript, exit marker, boot reconcile, suspend and resume are
unchanged. A task changes **what** is spawned, never how it is supervised.

## `exec` is the whole trick

The child runs `server-core`'s `exec` boot mode, which is the same sequence
`serve` runs, stopped after `onReadyBlocking`. So the body sees the contributions
it needs, the config registry and its parent's database — and none of the
machinery a short-lived process must not start: no socket, no graphile runners,
no cron, no git watcher, and above all **no supervised-run reconciler**, which in
a child would adopt and write off the very run that spawned it.

Read `server-core`'s "Boot modes" before adding to `onReadyBlocking` or moving
main-only work earlier: `isMain()` is env-derived, so in a child of main's backend
it is **true**, and nothing misbehaves today only because every main-only side
effect hangs off a phase `exec` skips.

## What the child inherits

Nothing is plumbed — `startSupervisedRun` spawns with `{ ...process.env }`:

- **`SINGULARITY_WORKTREE`** resolves both the per-worktree database and, through
  that namespace's `spec.json`, the composition registry. Same app, same DB as the
  parent, with no argument saying so.
- **`PATH`** — `tar`, `gzip`, `pg_dump` resolve exactly as in the backend.
- **cwd** is `REPO_ROOT`, because `./singularity` is a path.

A task that needs anything else puts it in the payload, not the environment.
Keep payloads small: they are JSON on a command line.

`supervised-exec` declares `detachable: true`. A supervised child is meant to
outlive the backend that started it, and the orphan guard — armed for every
`./singularity` invocation — would otherwise be free to kill it.

## Failure is loud

An unknown id throws, naming the id and listing the registered ones. Returning
quietly would exit 0, the shim would write a `0 -` marker, and the ledger would
record a successful run that did nothing at all. Malformed payload JSON throws
the same way; `execute` parses and runs in one call, so a value the schema
refused can never reach the body.

All of it exits 1, which the shim records and the supervising job reads. A failed
task is a failed RUN, not a failed job — see `supervised-job`.

## Why `invoke()` rather than a hand-written argv

`defineSupervisedJob`'s `task` arm takes a `SupervisedTaskInvocation`, and the
only producer of one is `SupervisedTask.invoke(payload)`. So the id is a
registered id by construction and the payload is checked against that task's own
schema at the call site that knows both — a job and the task it spawns cannot
drift apart without a tsc error. That is what makes the arm more than a second
spelling of `argv`.
