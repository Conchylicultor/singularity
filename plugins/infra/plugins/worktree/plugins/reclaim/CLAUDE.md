# reclaim

Gives back what a namespace took: its Postgres database, its config dir, its
gateway registry dir (spec + dist + marker), and the gitignored filtered
registries in whatever checkout composed it.

## The trigger is ownership, never intent

A namespace is reclaimed when the thing that OWNS it disappears — never because
someone stopped serving it. Deactivating a composition (`autoBuild: false`) is
deliberately not a trigger: the dist, spec and database stay live.

Ownership is recorded at mint time in the `composition.json` marker; this plugin
only reads it. `checkout: "att-X"` → that checkout. `checkout: null` → main.
`checkout` absent (legacy marker) → **unknown**, and never a target.

`namespacesOwnedByCheckout` matches on an exact string so `null` and `undefined`
fail it structurally. Guessing an owner here drops a database.

## Ask, do not enumerate

Callers do not name the kinds of namespace a checkout might have left behind —
they ask `namespacesOwnedByCheckout(id)` and reclaim the answer, so a namespace
kind invented later needs no edit to the reaper. Same one level down: the
filtered registries come from `listNamedCompositionRegistries`, not from
spelling `server.composition.<id>.generated.ts`, so `web` and `prewarm` are
reclaimed too.

## Why a sub-plugin and not part of `infra/worktree`

Five CLI command files import the parent barrel, so anything added to it joins
the CLI **process**'s import closure. Reclaiming reaches `database/admin` and
`database/zero/…/cache-service`, and through them `infra/jobs` and the DB pool —
exactly the surface `cli:codegen-manifests-not-frozen` guards.

## Order is load-bearing

Zero replication artifacts before the database (`DROP DATABASE WITH (FORCE)`
does not drop replication slots, and a leftover slot fails the drop); both DB
steps guarded on `databaseExists` (otherwise the reclaim aborts before the
registry step and the gateway registration is anchored forever); filtered
registries after the spec (the spec is what stops the backend, and the backend
reads its registry at spawn).

No separate "dist" step: `removeWorktreeSpec` `rm -rf`s the whole namespace dir,
so dist and marker go with the step that deregisters.
