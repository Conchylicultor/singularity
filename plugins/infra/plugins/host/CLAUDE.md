# host

Around sixteen worktree backends run on this one machine at a time, and they all
share its cores, its memory, its disk, and one embedded Postgres. Nothing here is
per-worktree. Everything under this umbrella answers **how much of the shared
machine may I take right now, and is the box still healthy enough to be asked?**

Reach for:

| You want | Use |
|---|---|
| A bounded slot before doing heavy work, counted across every backend on the box | `host-admission` |
| One slot for a heavy git-subprocess or filesystem read | `host-read-pool` |
| How loaded the box is at this instant — load average, cores, Postgres backends | `contention` |
| Whether the box is in trouble, and how to shed durable writes while it is | `duress` |
| To read that "in trouble" signal from a process with no backend around it | `duress/latch` |

`host-admission` is the floor the others stand on. It is the only plugin allowed
to bring a cross-process pool into existence, and `host-read-pool` is one pool
declared through it plus the policy that names, sizes and instruments it.

`contention` and `duress` bound nothing. They describe the state of the box, and
each caller decides what to do about it.

`duress/latch` is a sub-plugin of its own so that it stays importable by a
process with no database, no config and no worktree identity — the CLI's build
admission valve has to read the signal before any backend exists.

Not here: the mechanisms these policies are built from. The cross-process flock
slot broker is `packages/host-semaphore`, its in-process counterpart is
`packages/semaphore`, and the sentinel that trips and clears the duress latch is
`debug/sentinel`. This umbrella owns which pools exist, how big they are, and
when writes get shed — not how a slot is taken.

## Plugin reference

- Description: How much of the shared host machine may I take right now, and is the box still healthy? — the host-wide admission pools (host-admission), the heavy git/filesystem read budget declared through them (host-read-pool), the box's load snapshot (contention), and the 'the box is in trouble' latch plus the shed engine that rides it (duress).
- Sub-plugins:
  - **`contention`** — Cached, cluster-wide system-contention snapshot (OS load average + Postgres backend counts) stamped onto slow ops.
  - **`duress`** — Duress web presence: registers the shed-engine config (enabled, persist-first-N, buffer caps, flush delay) for Settings → Config. Host-global duress latch (a mtime-leased latch file the cluster sentinel sets while the box is in trouble; backends gate observability writes on the cheap synchronous isUnderDuress()) plus the shed engine: createShedBuffer routes durable observability writes through per-episode first-N persistence, a bounded in-memory buffer, and a flush-on-clear replay.
  - **`host-admission`** — Host-admission registry: one place a host-wide concurrency pool comes into existence, wrapping createHostSemaphore with a summed CPU/RAM ceiling and true host occupancy.
  - **`host-read-pool`** — Shared host-wide budget for CPU/IO-heavy git/filesystem reads: withHeavyReadSlot admits at most a few heavy reads at once across all worktree servers.
