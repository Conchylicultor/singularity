# audio-analysis

YouTube `videoId` → cached **beat features** (contract 1 of
`research/2026-09-29-apps-sonata-ug-sheet-alignment.md`), computed out of
process on the on-demand `audio-python` dependency (`infra/deps`). Plan and
measurements: `research/2026-09-30-infra-audio-analysis-beat-features.md`.

## Using it

- **Off the event loop** (a chain job's `run` body, a CLI command — both hold
  an `ExecContext`): `ensureBeatFeatures(videoId, exec, { log, force?, settings?, device? })`
  → `BeatFeatures`. Fetches the audio (`youtube/audio-fetch`), installs the dep,
  analyses, caches.
- **From a request**: `requestBeatFeatures(videoId, { force? })` enqueues the
  `audio-analysis.beat-features` supervised job (lock = settings key + videoId, 2 attempts)
  unless the features are ready, running, or failed permanently, and returns
  the state. `readBeatFeatures(videoId)` is the state from files alone.
- HTTP: `GET` / `POST /api/audio-analysis/beat-features/:videoId`.
- CLI: `./singularity audio features <videoId…> [--force] [--clicks <dir>] [--device auto|cpu|mps] [--beat-model small0|final0] [--chroma fast|full]`
  — each flag overrides its setting for the run; `--clicks` writes `<videoId>-clicks.wav` (clicks over the audio, accented
  downbeats) to check a grid by ear.

## Settings (user config)

`audioAnalysisConfig` (`shared/config.ts`, Settings → Config), read on the
server by `configuredAnalysis()` — an in-memory read, fine on a request path.
The defaults are the fast options, except the beat model: `small0` misplaced
downbeats on sparse songs (Let It Be: 64% of bars 4 beats, against 83% with
`final0`), and downbeats feed the aligner, so `final0` is the default.

- `device`: `auto` (MPS when torch can use it, else CPU) | `cpu` | `mps`.
- `beatModel`: `final0` | `small0` (Beat This! checkpoints, both sha256-pinned).
- `chroma`: `fast` | `full` (frame hop 46 vs 23 ms, tuning from a quarter of
  the STFT frames vs all; both keep HPSS, tuning and the bass chroma).

`beatModel` and `chroma` change the output, so they are the cache key
(`settingsKey` → `final0-fastchroma`) and are recorded in
`source.settings`; `device` does not (CPU and MPS give identical features),
so it is only recorded, resolved, in `source.device`. Every read, ensure and
request uses the configured settings unless given others; the job carries the
settings it was requested with, so it computes the entry the request read.

## State lives in files, not the DB

Host-wide, shared by every worktree (the per-worktree `supervised_job_runs`
ledger cannot say "another worktree is analysing this"):
`cache/beat-features/v<ANALYSIS_VERSION>/<settingsKey>/<videoId>.json` (validated, then
renamed in: present ⇒ ready), `.running.json` (counts only while
`<videoId>.lock`'s flock is held — a killed run reads as absent), and
`.failed.json` (`permanent` = the error was non-retryable). Bumping
`ANALYSIS_VERSION` makes every video absent again; cached audio survives. The
lock, the markers and the job's lock are per settings key too, so two settings
of one video are independent entries.

## The extractor (`python/singularity_audio`)

- Decode: PyAV frames at their native rate, one soxr HQ resample of the whole
  signal to mono 22.05 kHz (no system ffmpeg). PyAV's per-frame resampler cost
  ≈0.5 s more per song.
- Two processes: importing torch (≈1.5 s) and librosa's scipy/numba (≈2 s)
  costs more than using them, so the chroma runs in a spawned child that
  imports while the parent decodes, then the parent imports torch and tracks
  beats. A child failure is raised in the parent with its traceback.
- Beats: Beat This! `small0` or `final0` (MIT, code and weights), minimal
  post-processing, no DBN. Checkpoints are sha256-pinned in `beat_features.py`
  and land in `cache/audio-models` (`TORCH_HOME`) on first use.
- Chroma: one tuning-compensated CQT (MIDI 28–95) → HPSS by median filtering
  **on the CQT magnitude** (`librosa.effects.harmonic` on the waveform took
  ≈30 s per song) → log-compress → treble (48–95) and bass (28–52) folded to 12
  pitch classes → beat-synchronous median → max-normalised.
