# caret-flight

The report kind for **an abandoned caret landing in the page editor** — see the
"The caret authority (input follows the model, not the DOM)" section of
`plugins/page/plugins/editor/CLAUDE.md` and
`research/2026-07-31-page-caret-authority.md`.

The authority holds one authoritative caret location. When the caret moves into a
block whose editor has not mounted yet (the block an Enter just created), it takes
the keyboard and buffers what the user types until that block's caret is ready.
An **abort** means the landing never happened, so the buffer had to go somewhere
else: back into the origin block, or — if even that has no host — nowhere.

## Signal source and threshold

The page editor must not import `reports`, so the authority emits a neutral
`CaretFlightAbortReport` into `caretFlightReportSink` (exported from
`@plugins/page/plugins/editor/web`) and `CaretFlightCollector` (mounted via
`Core.Root`) maps it to a report — the same inversion `reports/crash` uses for
`error-boundary`'s `boundaryReportSink`.

**There is deliberately no threshold in the collector**, unlike
`live-state-stale-drop`. The authority already suppresses the benign case at the
source: an abort with an EMPTY buffer is an ordinary cancellation (the user
clicked away before the landing) and never reaches the sink. Every body that
arrives therefore represents keystrokes that had to be rescued or were lost —
one report each.

## Fingerprint

`sha256("caret-flight" + reason + recovered|lost)`, first 16 hex chars.

The block ids are **excluded**: they are fresh uuids on every occurrence, so
including either would open a new `_reports` row per keystroke burst. `buffered`
is excluded for the same reason. `recovered` vs `lost` IS kept — a buffer nothing
could take is data loss, a materially worse bug than one that landed in the
previous block, and it deserves its own row (and its own `destructive` badge).
