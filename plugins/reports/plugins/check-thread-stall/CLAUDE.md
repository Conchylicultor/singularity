# check-thread-stall

The report a `./singularity check` run files when its shared JS thread stalls
past the "Check pass speed" track's targets. The stall watch itself lives in
the check runner (`plugins/framework/plugins/tooling/plugins/checks`, section
"The check thread is shared, and a run reports when it stalls"). This plugin
owns the kind: its payload, fingerprint, task and summary line.

## Two triggers, one kind

| trigger | files when | fingerprint | one row per |
| --- | --- | --- | --- |
| `stall` | one stall's `lateMs ≥ STALL_REPORT_MS` (2 s) | `check-thread-stall:<top owner>` | owner (`check <plugin>`, `shared <fn @ path>`, `import`, `native <leaf>`) |
| `total` | a run's `stalledMs ≥ TOTAL_REPORT_MS` (20 s) | `check-thread-stall:total` | — |

The thresholds are the track's **targets**, not today's measurements, so both
fire on most full passes until the remaining stalls are fixed. After that, a
report is a new regression.

Warning variant, bell re-alerts at most every 6 h per row: a slow check is a
chronic cost, not an outage. The row keeps the latest example — worktree, run
id, transcript path, the top 3 owners with their stacks, the waiting-vs-working
split and CPU.

## How it is filed

The check runner is a CLI process with no server, so it files through the
report outbox (`plugins/reports/plugins/outbox`). The payload's worktree lives
in `data`, not in the row's `worktree` column — main records every outbox
entry. The outbox's staleness rule drops a report when main has changed a file
on the stall's stacks since the writer's branch point.

`core/` is imported by the check runner (`checks/core/stall-report.ts`), so it
stays zod-only: no React, no server code.
