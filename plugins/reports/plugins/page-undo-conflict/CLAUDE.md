# page-undo-conflict

The report kind for **a text undo entry that met a second writer** in the page
editor — see the undo section of `plugins/page/plugins/editor/CLAUDE.md` and §5
/ §6 of `research/2026-09-09-page-data-based-text-undo-entries-v2.md`.

A text undo entry records a block's runs before and after a typing run and
replays by writing the recorded side back. That is lossless only while the block
has ONE writer between record and replay. A second writer — a server push, an
agent's `edit_page`, another client — is what both arms of this report describe,
and the policy differs per arm, which is why they are reported apart.

## The two reasons are two different policies

- **`stale-entry`** — the replay compared the block's current runs to what the
  entry recorded (`after` on undo, `before` on redo) and they differed. Under
  single-writer LIFO they always match, so the mismatch is a genuine second
  writer. The entry is applied **anyway** — the user asked for their undo — and
  the second writer's text is clobbered. This report is what makes that clobber
  measurable instead of silent; the upgrade path when it stops being rare is a
  runs-level 3-way merge at replay.
- **`run-aborted`** — a remote apply landed inside an open typing run. Closing
  the run would have recorded an entry carrying the remote text as if the user
  had typed it, and undoing it would destroy that text. So the run is dropped:
  one undo step lost at a genuinely concurrent moment, never a destructive
  entry. The same guard covers the hydration window.

Both are fingerprinted on the reason ALONE. The block id is a fresh uuid per
occurrence, the direction is whichever key the user pressed, and the two lengths
are however much text the block held, so including any of them would split one
situation into a row per keystroke.

## Signal source

The page editor must not import `reports`, so it emits a neutral
`UndoConflictReport` into `undoConflictReportSink` (exported from
`@plugins/page/plugins/editor/web`) and `PageUndoConflictCollector` (mounted via
`Core.Root`) maps it to a report — the same inversion `reports/collab-hydration`
and `reports/caret-flight` use.

**Neither arm is a crash.** Each is the residual the design accepts under a
stated policy, and this report is the measurement that keeps the policy honest:
a rising count is the signal to take the upgrade path, not a bug in the
collector.
