# collab-hydration

The report kind for **a block whose text stopped rendering** in the page editor —
see the "Per-block CRDT text" section of `plugins/page/plugins/editor/CLAUDE.md`
and `research/2026-07-23-page-collab-binding-replicas.md`.

A block's text has exactly ONE owner: its per-block `Y.Doc`. Everything else is a
view of it — the Lexical editor the user types into, and the ~1s
`page_blocks.data.text` projection. Neither view can be trusted to notice when it
falls behind, because `@lexical/yjs` has **no read-the-doc operation**: a binding
ingests its doc solely through the update events fired AFTER it attaches, and the
doc itself is hydrated solely by the `page-block-doc` live-state push. So there
are two ways to end up showing an empty block whose content is safe on the
server, and this report is how either becomes visible.

## The two reasons are two different bugs

- **`blind-binding`** — the editor rendered less than its own doc holds. The
  binding never received its post-attach events (it attached to an
  already-populated doc, or missed events while detached). `BindingReplica`'s
  construction invariant is supposed to make the first case impossible, so this
  arm firing means that invariant has a hole.
- **`starved-doc`** — the doc itself is behind the server: the row projection
  holds text this client never typed, so the push that should have hydrated the
  doc never arrived. Note the standing evidence that this happens — `reports`
  carries `live-state wedged: missed-updates — page-block-doc` occurrences.

Both are fingerprinted on the reason ALONE. The block id is a fresh uuid per
occurrence and the three lengths are however much text the user had, so including
any of them would split one defect into a row per keystroke burst.

## Signal source

The page editor must not import `reports`, so its hydration guard emits a neutral
`CollabHydrationReport` into `collabHydrationReportSink` (exported from
`@plugins/page/plugins/editor/web`) and `CollabHydrationCollector` (mounted via
`Core.Root`) maps it to a report — the same inversion `reports/caret-flight` and
`reports/crash` use.

**The editor recovers before it reports** (re-read the authoritative state,
re-attach the binding to a fresh replica) and suppresses the projection so the
emptiness is never written to the row. A report therefore describes a defect the
user saw and the app survived — not data loss. Treat it as a defect anyway: the
recovery is a safety net, and the structural fix is tracked separately.
