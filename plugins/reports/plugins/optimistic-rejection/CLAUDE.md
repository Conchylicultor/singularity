# optimistic-rejection

The report kind — and the user-facing toast — for **a write the server permanently
rejected**, so the user's edit was lost.

`useOptimisticResource` (`primitives/optimistic-mutation`) classifies every HTTP failure
with `classifyRejection`: a 4xx other than 401 / 408 / 429 is a **final verdict** (the
server will answer the same way however often the op is re-sent). Such an op is dropped
from the overlay at once — the surface renders server truth again and the newer ops
parked behind it can confirm — and its neutral `OptimisticRejectionReport` is emitted
into `optimisticRejectionSink`. A detached write (`enqueueDetachedWrite`: no overlay, no
Retry surface) emits the same body for any `EndpointError`. Transient failures (5xx,
401, 408, 429, network) never reach this plugin: the op stays rendered under
never-revert, with the sync cloud's Retry.

Design: `research/2026-10-08-global-rejected-optimistic-ops.md`.

## What the collector does

`OptimisticRejectionCollector` (mounted via `Core.Root`) drains the sink — the primitive
may import neither `reports` nor `shell` — and, per rejection:

- **toasts** `Couldn't save <label> edit` with the server's reason, so the user knows the
  edit on screen was not kept (before this, the only signal was the cloud's tooltip, and a
  reload threw the edit away silently);
- **reports** `kind: "optimistic-rejection"`, source `client-optimistic-rejection`.

## Fingerprint

`resourceKey + label + status + opSummary + normalized message`. `params` is excluded
(the same wrong prediction is rejected on every page it happens on), and uuids, block ids
and numbers are normalized out of the message for the same reason. The notification
re-arms every 6h, like `optimistic-divergence`.
