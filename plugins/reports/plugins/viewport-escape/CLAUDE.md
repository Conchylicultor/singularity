# viewport-escape

The report kind for **a `fixed inset-0` box that is not actually measured
against the viewport** — the runtime auditor in
[`plugins/primitives/plugins/css/plugins/viewport-overlay`](../../../primitives/plugins/css/plugins/viewport-overlay/CLAUDE.md),
"The runtime auditor".

Two faults, discriminated by `fault` in the payload:

- **`viewport-containing-block`** — an ancestor declares a `transform` /
  `filter` / `contain` / `container-type` / `will-change`, so it, not the
  viewport, is the containing block. `inset-0` then means "fill that element",
  and the box is clipped to its content area.
- **`viewport-stacking-context`** — an ancestor opens a stacking context
  (`opacity` < 1, `isolation`, a blend mode, a positioned element with a numeric
  `z-index`), so the box's `z-index` is compared inside that layer instead of
  against the app's chrome. It stops covering the rail however high it is set.

Both look *almost* right — a fullscreen that is 40px short, a fullscreen with a
rail still down the side — which is exactly why they survive review and need a
report rather than a console line.

This plugin **drains that sink**. The dependency deliberately runs one way: a
primitive may never import `reports`, so `ViewportEscapeCollector` (mounted via
`Core.Root`) registers the handler that maps the sink's body onto
`report({ kind: "viewport-escape", … })` — the same inversion `reports/crash`
uses for `error-boundary`'s `boundaryReportSink`.

**Until this plugin existed, nothing registered the sink at all**, and
`defineReportSink` is a silent no-op until something does. The auditor throws
under `import.meta.env.DEV`, so the fault was loud in development and dropped on
the floor everywhere else — precisely backwards for a bug whose whole character
is that it only shows up on someone else's machine
(`research/2026-08-17-global-class-strings-as-data-guardrail.md`, phase E).

## The duplicated enum

`fault` is a hand-copied twin of `ViewportEscapeFaultKind`, not an import. That
type lives on the primitive's **web** barrel (it travels with the sink it
describes), and this plugin's schema is `core` — shared with the server, which
must never pull a browser runtime in.

The two are pinned together at compile time from the one place that legitimately
imports both: the collector maps a `ViewportEscapeFault` into a
`ViewportEscapePayload` under `satisfies`. Add a fault kind to the primitive
without adding it here and the collector fails to typecheck — a `tsc` error at
the seam rather than a 400 at ingest.

## Fingerprint

`sha256(fault + "\0" + subject + "\0" + blocker)`, first 16 hex chars.

`subject` and `blocker` are **included**: they are the (what broke, who broke it)
pair, and that pair *is* the defect. A solo tab clipped by a surface backdrop and
an overlay clipped by a `filter` on `<body>` are two different bugs in two
different plugins; collapsing them onto one row would hide the second behind the
first's count. `subject` is also the only name the auditor has for what it is
protecting — it is pure CSS and the consumer supplies the wording.

`message` is **excluded**, and specifically because it quotes the computed value:
`transform: matrix(1, 0, 0, 1, 0, 240)` changes on every scroll of the offending
ancestor, so fingerprinting it would file a fresh row per frame for one defect.

## Re-arm

`notifCooldownMs: 6h`, like `adaptive-bar` and `render-loop`. The offending
declaration lives in a stylesheet or a component's class list, so the fault
reproduces on every activation of that surface — every time the user goes
fullscreen, every time the overlay opens. A recurring warning, not a one-shot
crash.
