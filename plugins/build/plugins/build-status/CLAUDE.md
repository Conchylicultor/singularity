# build-status

Single source of truth for "how did this build run end". `buildStatusOf(run)`
(core) is the **only** place an exit code is interpreted; `BUILD_STATUS_META`
(web) the only place a status gets a colour or a label. Consumers branch on the
`BuildStatus` string, never on a number. Mirrors `tasks/attempt-status` — pure
derivation in `core`, display metadata in `web`.

## Only `failed` is destructive

Four of the six statuses are not code defects, and their colour says so — muted,
so they never draw the eye the way a real failure must:

| status | meaning | colour |
|---|---|---|
| `running` | no `finishedAt` yet | warning (pulsing) |
| `success` | exit 0 | success |
| `superseded` | exit 75 — its tree was replaced mid-run, so it never had a subject | muted |
| `interrupted` | exit -1 — its owner was hard-killed by a newer build's restart | muted |
| `killed` | exit > 128 — a signal arrived from outside the build | muted |
| `failed` | any other nonzero code: it ran to a verdict and gave a bad one | destructive |

`killed` needs no new exit-code constant: `128 + signo` is the POSIX encoding the
CLI's own fatal-signal handlers already produce (SIGHUP → 129, SIGINT → 130,
SIGQUIT → 131, SIGTERM → 143). `killedSignalName(exitCode)` names it for the
detail line, and is total — an unmapped signo reads `SIG<n>` rather than
disappearing.
