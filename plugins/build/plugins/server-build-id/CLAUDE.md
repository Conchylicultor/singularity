# server-build-id

Server-only leaf that reads the two trailer files the build stamps into the
frontend dist it publishes, **fresh on every call — never memoized**:

- `.build-graph` (`getServerGraphHash`) — the content identity of the served web
  graph. This is the one a tab compares itself against: it is a function of the
  composed module graph, so two builds of an unchanged tree return the same
  value and nobody is asked to reload for a rebuild that changed nothing.
- `.build-commit` (`getServerCommit`) — the tree the bundle was built FROM. The
  build stamps the commit it sampled before reading a source file, so it names
  the tree these bytes came from, not whatever the checkout moved to during the
  compile. `build/deployment` turns it into the `web` carrier's pin.

The dist also carries `.build-id` (the run that produced it — `build_runs.id`,
the log and profile filenames). Nothing at runtime reads it; it is a run id, not
an identity, and the reader was removed when the last caller moved to `.build-graph`.
(The folder name predates that — it now reads neither a build id nor only ids.)

Never memoized because `./singularity build` swaps the `dist` symlink (what the
browser downloads) *before* it restarts this backend, so a value cached at
process start would disagree with the currently-served bundle during the
swap→restart window and leave the "Server updated" reload button stuck (the tab
loads the new bundle while the server keeps reporting the old value). Reading the
tiny dotfiles per call resolves through the same `dist` symlink the gateway
serves from, so what is reported always matches the bundle in the browser's
hands. Extracted out from behind the heavy `build/server` barrel so stale-tab
detection can read them without pulling `git-watcher`/`worktree` into its
closure. Its only dependency is `infra/paths`; synchronous, boot-safe reads
(reports' boot-time backfill reads eagerly).
