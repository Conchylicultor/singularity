# build-termination

`GET /api/build/runs/:id/termination` — what the host recorded about the death of
one build run: which signal arrived, and who sent it. Plus
`describeTermination`, the pure function that turns that into the words
`build-info` prints under the status badge.

## Why its own sub-plugin, and not `build-logs`

`build-logs` reads a per-run artifact this worktree wrote, and its web half is
the "Logs" section. This reads a **host-global** file written by a dying CLI
process, and its consumer is `build-info`'s section — so hosting it there would
have made `build-info` import `build-logs` to render a status line, naming the
wrong owner in the dependency graph for good.

## Nothing is a `build_runs` column, and nothing is a 404

The record deliberately lives in the sink, not the ledger: it is written from a
signal handler and an exit hook, where nothing may be awaited, so a DB write on
that path would trade a clean termination for a hang.

The endpoint answers with an empty record (`{signal: null, armFailure: null}`)
for the overwhelmingly common run that was never signalled. A 404 would make
"not killed" indistinguishable from "run does not exist".

## The three outcomes must stay distinct

`signal` and `armFailure` are independent fields because the UI has three things
to say and only two of them are "we know":

| record | what the pane says |
|---|---|
| `signal.origin` set | the sender, named — `formatSignalOrigin` owns the wording |
| `signal.origin` null | the signal, and *why* nobody is named (`armFailure.reason` when there is one) |
| no `signal` line | no record for this run — and for `interrupted`, that SIGKILL can never have one |

Collapsing these would recreate the exact ambiguity the feature removes: **"we
could not tell who" and "nobody sent a signal" must never render the same.**
