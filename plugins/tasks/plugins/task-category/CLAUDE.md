# task-category

Per-task **category** — the categorical "what kind of task is this" dimension
(conversations, system, agents, improvements, reports, …), replacing the old
meta-folder parenting. **Registry-driven and system-set only**: there is no user
picker; filing plugins stamp the category via `setTaskCategory` when they create
a task.

## Collection-consumer separation

Each filing plugin contributes its own category via the `TaskCategory`
server-contribution — the list is **never** hardcoded in a consumer:

```ts
// plugins/<owner>/server/index.ts
contributions: [TaskCategory({ id: "reports", label: "Reports", order: 4 })],
```

Consumers read only the generic aggregate:

- **Server:** `GET /api/tasks/categories` returns the registered categories,
  sorted by `order ?? 0` then id (static after boot, cached forever client-side
  via `useTaskCategories()`).
- **Web:** the plugin contributes a `category` enum `FieldDef<TaskListItem>`
  into the task-list's `Tasks.Fields` seam (`CategoryField` closes the field's
  `value` over `useTaskCategoryMap()`), so the tasks DataView can group/filter
  by category with no task-list code naming any category. Both hooks return a
  `ResourceResult` (`useTaskCategories()` → the registry,
  `useTaskCategoryMap()` → `taskId → categoryId`): not loaded yet is the
  loading arm, never an empty registry or an empty map (which would claim
  every task uncategorized). The field carries that state on to the DataView
  rather than folding it into `null` (the None bucket) or its options into
  `[]`: `pending` while EITHER read has never loaded, `readError` when either
  failed with nothing held (the map's first, each with its own Retry) — so
  its cells, and a view grouped / sorted / filtered by it, render loading or
  the failure instead of filing every task under None, or laying sections out
  under raw ids that relabel and reorder when the registry lands
  (`web/internal/category-read.ts`, tested beside it).

## Storage + live state

- `tasks_ext_category` is an entity-extension side-table on `tasks` (one row per
  categorized task, FK CASCADE on task delete). `setTaskCategory(taskId,
  category | null)` upserts / deletes.
- `taskCategories` (`shared/resources.ts`) is a `liveCollection` declared
  **`all`** (P8 v3 step 18): the whole ordered set of `{ taskId, category }`
  rows, ordered by `taskId`, `preload: "boot"` so the default category-grouped
  tasks view never flashes "None" on first paint. Served by `serveCollection`
  from the extension handle (`server/internal/resource.ts`, options in
  `serve-options.ts`): a routed, L2-persisted alias — a category set is one
  entrant (a refill + one `orderOf`), a change a one-row refill, a clear or the
  task's delete (FK cascade) an exit with no load, and no other tree write
  reaches it. Read only through the two hooks above (`useLive(taskCategories,
  { select })`); the declaration itself is plugin-private.
- **The wire row is the legacy row, under the legacy key.** A tab still on a
  bundle with the old param-less `queryResourceDescriptor` subscribes `{}`,
  passes the `all` gate and parses these rows with its own schema (C39). A
  change to the row must rename the key (`unknown-key` is a `skew` verdict).
- Tests: `server/internal/task-categories-oracle.test.ts` — the tree oracle
  (tasks-core `server/testing`, on a resource runtime of its own, so it
  coexists in one bun process with suites whose imports registered the real
  key on server-core's global runtime) with the category writes spliced in: every
  step's exact cost, FULL parity after each, the idle `{}` snapshot and its
  floor persist, and the C39 old-descriptor subscription.
