# Delete the dead `RuntimeName` type from `boundaries/core`

## Context

`plugins/framework/plugins/tooling/plugins/boundaries/core/types.ts:23` declares:

```ts
export type RuntimeName = "web" | "server" | "central" | "shared";
```

Two facts about it, both verified:

- **Nothing imports it.** A repo-wide search for `RuntimeName` finds only its own
  declaration, its re-export from the boundaries barrel
  (`boundaries/core/index.ts:2`), the two generated doc blocks that list barrel
  exports (`boundaries/CLAUDE.md`, `docs/plugins-details.md`), and prose in two
  historical research docs. No call site, no type position, nothing.
- **It is already wrong.** The runtime folder set is
  `web | server | central | core | shared | e2e | data-dirs`
  (`RUNTIME_FOLDERS` in `plugins/framework/plugins/plugin-id/core/plugin-id.ts:27`).
  `RuntimeName` omits `core`, `e2e` and `data-dirs`.

The type that actually governs the boundary config is `RuntimeFolder`, derived
from `RUNTIME_FOLDERS`: `BoundaryConfig.runtimes` is typed
`Record<RuntimeFolder, RuntimeFolder[]>` (`types.ts:28`), so the isolation map is
exhaustive by construction — adding a runtime folder is a type error until the
map declares its policy.

The hazard is that `RuntimeName` looks authoritative: a plausible union of
runtime names, exported from the barrel, sitting six lines above the map it
appears to describe. A reader adding a runtime folder finds it first and either
edits it believing it is the source of truth, or reads it as the list of
runtimes and is wrong twice over. That already happened once — when `data-dirs`
was added it was the first place that looked like it needed changing, and did
not. The 2026-06-09 facet-resolver doc noted the inconsistency as a follow-up;
this is that follow-up.

The fix is the top rung of the ladder: delete the concept, so there is no wrong
thing left to spell and nothing to keep in sync.

## Changes

**1. `plugins/framework/plugins/tooling/plugins/boundaries/core/types.ts`**

Delete the `RuntimeName` declaration (line 23). Everything else in the file
stays; the `RuntimeFolder` import at the top is used by `BoundaryConfig.runtimes`
and must remain.

**2. `plugins/framework/plugins/tooling/plugins/boundaries/core/index.ts`**

Drop `RuntimeName` from the type re-export on line 2:

```ts
export type { BoundaryConfig, ZoneDefinition, Edge, AllowEdge, DenyEdge } from "./types";
```

**3. `plugins/framework/plugins/tooling/plugins/boundaries/core/runtimes.ts`**

Same drift, one file over. `runtimeNames` is correct — it is derived
(`new Set(Object.keys(boundaryConfig.runtimes))`, and those keys are exhaustive
because the map is a `Record<RuntimeFolder, …>`) — but its comment enumerates
the set by hand as "(web/server/central/core/shared)", which is missing `e2e` and
`data-dirs` and is the same trap in comment form. Drop the parenthetical rather
than correcting it: the whole point of the derivation is that no second copy of
the list exists. The comment should say each key is a runtime whose import
permissions the map declares, and stop there.

`runtimeNames` itself stays. It is live — `plugin-boundaries/check/index.ts`
imports it at lines 314 and 387 — and it cannot drift from `RUNTIME_FOLDERS`,
since both trace to the same authority through the `Record<RuntimeFolder, …>`
type. Collapsing the two spellings is not part of this change.

**4. Generated docs — do not hand-edit.**

`plugins/framework/plugins/tooling/plugins/boundaries/CLAUDE.md` (its
`AUTOGENERATED` block, under `Exports (types)`) and `docs/plugins-details.md`
(around line 14458) both list `RuntimeName`. They are regenerated from the barrel
by `./singularity build`, and `plugins-doc-in-sync` fails on drift. Running the
build is the whole step.

**5. Historical research docs — leave alone.**

`research/2026-05-19-tooling-phase7.3-boundaries.md` and
`research/2026-06-09-global-facet-plugin-specifier-resolver.md` mention
`RuntimeName`. They are dated records of what was true when written, not live
documentation; rewriting them would erase the trail that leads to this doc.

## Out of scope

A check that fails when a barrel exports a symbol no other plugin imports would
be the rung-3 version of this problem, and the data for it already exists — the
cross-refs facet records symbol-level cross-plugin uses (`ApiUse.symbol` /
`importedBy` in
`plugins/plugin-meta/plugins/facets/plugins/cross-refs/core/types.ts`). It needs
an exemption story for symbols consumed by the non-plugin roots (`cli/`, `web/`,
`gateway/`), which makes it its own design job. Filed separately; not built here.

## Verification

1. `./singularity check plugin-boundaries` — the boundaries checker and the
   `plugin-boundaries` check are the only consumers of this barrel; they must
   still pass, proving nothing depended on the deleted type.
2. `./singularity build` (background) — regenerates `boundaries/CLAUDE.md` and
   `docs/plugins-details.md`, then runs the full check suite. `type-check`
   proves no type position referenced `RuntimeName`; `plugins-doc-in-sync`
   proves the two generated blocks were regenerated rather than left stale.
3. `grep -rn "RuntimeName" --include='*.ts' --include='*.tsx' --include='*.md' .`
   (excluding `node_modules`) should return only the two `research/` docs.
