# Terminal-menu relay + usage-limit card

## Context

When Claude Code opens an interactive menu other than AskUserQuestion — e.g. the
usage-limit menu ("What do you want to do? 1. Stop and wait for limit to reset /
2. Wait here, then continue automatically at Oct 13 at 6am / 3. Switch to usage
credits — Enter to confirm · Esc to cancel") — the conversation view shows only
the static fallback `PendingContentIndicator` ("Content pending in terminal —
waiting for your input"), and the prompt box says "Waiting for your answer in
the terminal". The user must open the terminal to read and answer it.

Root cause: `runtime-tmux/server/internal/pane-menu.ts` recognises only two
menus (question, rewind); every other live menu classifies as `idle`, so
`waitingFor` is the CLI's opaque string ("input needed" / "permission prompt"),
which no `JsonlViewer.PendingPrompt` variant matches.

Outcome:
1. **Generic** — any live numbered terminal menu is parsed into
   `{ title, options[], highlighted }`, carried to the browser, and rendered as
   a card with one button per option (+ Cancel). Clicking answers it in the
   pane. Future CLI menus work with zero code.
2. **Usage-limit variant** — the same menu, recognised by its options, renders
   "Usage limit reached · resets Mon Oct 13, 06:00 · in 3d 4h" with
   Wait & continue (primary) / Stop / Use credits.

Out of scope (user decision): health-report row, "Paused (limit)" list status,
launch gating, subagent-failure list, scheduled auto-continue.

## Design

### 1. Parse (runtime-tmux, pure)

`pane-menu.ts`: extend the classifier to return a structured result:

```ts
export type PaneMenu =
  | { kind: "idle" } | { kind: "question" } | { kind: "rewind" }
  | { kind: "menu"; menu: TerminalMenu };
```

- Same live-footer rule (walk up to `Esc to cancel`, a composer crossed ⇒ stale).
  Question / rewind keep precedence and their existing semantics.
- Otherwise, walk up from the footer collecting option lines
  `^\s*(❯\s*)?(\d+)\.\s+(.+)$` (continuation lines indented under an option are
  its description — appended to `description`), stopping at the first
  non-blank non-option line above the options = `title`. `❯` marks
  `highlighted`.
- The `❯ n.` option line must not be mistaken for the composer: the walk to the
  footer already stops at the footer first; the option walk runs *above* it and
  never consults `COMPOSER_RE`.
- No options parsed ⇒ `idle` (not a numbered menu — don't guess).
- `classifyPaneMenu` capture widens from `-S -15` to `-S -40` so a long menu's
  title is in frame.
- Existing callers (`escapeUntilPromptCleared`, `awaitPromptMenu`) switch on
  `.kind`; behaviour unchanged.

`TerminalMenu` (zod schema + type) lives in **tasks-core/core** next to the
conversation fields, since it becomes a conversation column:

```ts
{ title: string; footer: string;
  options: { n: number; label: string; description: string | null }[];
  highlighted: number }
```

### 2. Carry (reconciler → conversations row → live)

- `RuntimeInfo` (`conversations/server/internal/runtime.ts`) gains
  `menu: TerminalMenu | null`.
- `describePanes` (tmux-runtime.ts): on `kind:"menu"` force `working:false`,
  `waitingFor:"menu"`, `menu`. Other runtimes return `menu:null`.
- New column `waitingMenu: nullable(jsonField({ schema: TerminalMenuSchema }))`
  in `tasks-core/core/internal/fields.ts`; `touchedBy: false` like `waitingFor`
  (`tasks-core/server/internal/tables.ts`); excluded from all-conversations
  list reads like `waitingFor`. Migration generated by `./singularity build`.
- `plan-update.ts` `planLive`: `desiredMenu = desiredWaitingFor === "menu" ?
  info.menu : null`; patch when it differs (deep-equal) from `row.waitingMenu`.
  `updateConversation` patch type + `markConversationGone` clear it.
  Invariant (asserted in planLive): `waitingFor === "menu"` ⇔ `waitingMenu != null`.
- Rides `conversationsById` → `useLiveConversation`, already pushed.

Wake-up: a menu appearing is caught by existing signals (sessions-file write on
the turn ending, the unmatched `Notification` hook touch + 1 s recheck), with
the 1-min status sweep as backstop. No new signal. Verified during testing.

### 3. Answer (server)

- `ConversationRuntime.selectMenuOption(id, { n, label } | "cancel")`; tmux impl:
  `copy-mode -q`, fresh capture + parse; **refuse (throw) unless a live `menu`
  whose option `n` has the same `label`** (guards a stale card / changed menu);
  then `send-keys` `Down`/`Up` × (n − highlighted) and `Enter` (named keys, no
  `-l`); cancel = single `Escape` (only after the live-menu check, so it can't
  open rewind on an idle pane). Then touch the conversation's tmux signal so the
  reconcile + redraw recheck clears the card.
- Wrapper `selectMenuOption` in `conversations/server/internal/runtime.ts`,
  exported from the barrel.

### 4. New plugin `conversations/plugins/terminal-menu`

- `core/endpoints.ts`: `POST /api/conversations/:id/menu-select`
  body `{ choice: { n, label } | "cancel" }`.
- `server/`: implements it via `selectMenuOption`.
- `web/`:
  - `JsonlViewer.PendingPrompt({ match: "menu", component: TerminalMenuCard })`.
  - `TerminalMenuCard` reads `waitingMenu` via `useConversation(id)`; renders
    title, option buttons (description as secondary text, highlighted one
    primary), Cancel, and the existing `PendingPromptAction` (Open terminal).
    Buttons via `useEndpointMutation` (auto-pending, toast on error).
  - Slot `TerminalMenu.Variant: { id, match(menu): boolean, component }` —
    first match replaces the generic body (props `{ conversationId, menu,
    choose(n), cancel() }`); the card owns the mutation plumbing so variants
    never touch the endpoint.

### 5. Usage-limit variant `conversations/plugins/terminal-menu/plugins/usage-limit`

- `match`: an option label matches `/wait for limit to reset/i` or
  `/continue automatically at/i`.
- Reset time parsed from the "continue automatically at <Mon> <D> at <h[:mm]>am|pm"
  option (pure `parseResetTime(label, now)`, unit-tested: local time, next
  occurrence, year rollover). Unparsable ⇒ show the raw option text (no fake time).
- Renders: "Usage limit reached", "Resets Mon Oct 13, 06:00 · in 3d 4h"
  (`useNow` from `primitives/relative-time`), buttons
  **Wait & continue automatically** (primary), **Stop**, **Use usage credits**
  mapped by label regex to options; any unmapped option still gets a plain
  button (never drop a choice).
- One-line note under Wait: "Keeps this terminal session waiting; it ends if the
  session is closed."

### 6. Prompt input copy

`prompt-input.tsx` placeholder: `waitingFor === "menu"` ⇒ "Answer the menu above"
(was the generic terminal line).

## Verification

- `./singularity test` on runtime-tmux (fixtures: the real limit menu from the
  screenshot; menu with descriptions; `❯` highlight on option 2; stale menu
  above composer ⇒ idle; question/rewind unchanged), conversations
  (planLive menu patch), usage-limit (`parseResetTime`).
- `./singularity build`, then in the worktree: start a conversation and open a
  numbered menu in its pane (e.g. `/model` or `/rate-limit-options`), check the
  card appears with the right options, choose one from the web, confirm the
  pane advances and the card clears. Screenshot via `e2e-harness/e2e/screenshot.ts`.
- Usage-limit card: exhibit with a fixture menu (no real limit needed).
