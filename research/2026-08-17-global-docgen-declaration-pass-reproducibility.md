# Make `plugins-doc-in-sync` a pure function of the tree

_2026-08-17 — status: proposed_

## Context

`./singularity push` fails on `main` itself with:

```
docs/plugins-details.md is out of sync with plugin source
```

`main` is un-pushable for this check, which blocks a finished, verified change to
web-artifacts vendor resolution sitting on `claude-web/att-1786989598-wcnd`
(`b7fe359c1`, rebased onto `ce42e619a`, tree clean, every other check green).

### What actually happens

`docs/plugins-details.md` is generated by importing every plugin's
`web/index.ts` and reading `contributions` off the default export. For nearly
every plugin that array is a literal in the file, so importing it is enough.

`reorder` is the exception. Its array starts **empty**
(`plugins/reorder/web/internal/config-registrations.ts:30`) and is filled by a
callback that fires when `declarePluginSlots` runs — the pass that settles which
plugin owns which slot. It has to work this way: slots are minted as modules
evaluate, but ownership is only known once each plugin's definition is read.
Until that pass runs, `reorder` contributes 0 entries; after it, ~240 (one
config directive per reorderable slot).

So the generator's output depends on what else already ran **in the same
process**:

- `./singularity build` runs the slot-declaration guard step
  (`regen-pipeline.ts:178`) and *then* generates the docs. Array full → the doc
  gains reorder's 240 entries. That is the committed content.
- The check calls `renderDetailsDoc()` directly. Nothing runs the pass. Array
  empty → the regenerated doc lacks reorder's `Contributes:` block (and its
  `Web:` block sinks below `Server:`, since folder order is first-fact-wins) →
  mismatch → fail.

Verified on this checkout at `ce42e619a`: rendering as the check does drops the
block; rendering after one `declareSlotsFromBarrels(root)` call reproduces the
committed `docs/plugins-details.md` **byte for byte**. **The committed content is
correct** — the regenerated version is the broken reading, and committing it
would delete genuine content.

### Why it shipped, and why it surfaced four commits later

Checks are cached globally, keyed by `(working-tree hash, check id)`
(`checks/core/runner.ts:367`). `./singularity build` runs its checks
**in-process**, right after codegen (`cli/bin/commands/build.ts:1329`) — in the
process where the declaration pass already ran. So each build passed the check
for the wrong reason and recorded a durable PASS; `push` over the same tree hit
that entry and never ran the check body.

The cache is not stale, and codegen *is* in the key — the tree hash is a
`write-tree` over the whole working tree (`checks/core/tree-hash.ts:47`), so
`fa7e865e0` invalidated everything and the check genuinely re-ran. It re-ran and
recorded a wrong answer. Four different trees, four fresh runs, four wrong
passes — confirmed present in `~/.singularity/check-cache/`:

```
fa7e865e0  tree 59ccf796…  PASS recorded 18:50
e6592a8dd  tree d54a4b91…  PASS
9fed9a1a2  tree 5ee5c2b2…  PASS
ce42e619a  tree fa4051ef…  PASS recorded 21:35
```

`b7fe359c1` is the first tree with no entry, so it is the first push where the
check actually ran.

`fa7e865e0` is where the subscription-filled array replaced a module-eval array
read from the `reorderable-slots` manifest, and it regenerated the doc from
inside a build.

### Intended outcome

The check becomes a pure function of the tree: same tree ⇒ same verdict, in a
build, a standalone check, or a push. `main` is pushable, `docs/plugins-details.md`
is untouched, and reading contributions before slots are declared stops being a
silent smaller doc.

## Plan

### 0. Remove scratch

Delete the untracked `.tmp-plan/` directory created while reproducing (it would
otherwise enter the working-tree hash).

### 1. The enriched tree runs the declaration pass itself

`buildEnrichedTree` (`plugins/framework/plugins/tooling/plugins/codegen/core/docgen.ts:202`)
is the **only** construction site of a barrel-imported facet tree — every other
`buildPluginTree` caller passes `skipBarrelImport`. Everything that reads
contributions goes through it: the two docs, per-plugin `CLAUDE.md`,
`config-origin-gen.ts`, `reorderable-slots-gen.ts`, and
`plugins/page/plugins/editor/check/index.ts`. Today each of them silently relies
on the regen pipeline's ordering comment; only the pipeline honours it.

Make it own the precondition:

```ts
export function buildEnrichedTree(root: string): Promise<PluginTree> {
  let cached = enrichedTreeCache.get(root);
  if (!cached) {
    cached = (async () => {
      await declareSlotsFromBarrels(root); // memoized per root
      return buildPluginTree(resolve(root, "plugins"), { facets: true });
    })();
    enrichedTreeCache.set(root, cached);
  }
  return cached;
}
```

`declareSlotsFromBarrels` is already memoized per root
(`slot-declaration-guard.ts:60`), so inside a build this is a no-op — the guard
step ran first. **Build output does not change** (proven byte-identical above).

The pass must keep its own barrel-import loop: it models the *registry*, skipping
disabled plugins, while `buildPluginTree` imports every node's barrel. Folding
the declaration into `buildPluginTree` would give disabled plugins' slots owners
and mint descriptors the browser never registers, breaking
`config-v2:registrations-paired`. Do not do that.

**Module split (needed — otherwise this closes an import cycle).**
`slot-declaration-guard.ts:20` already imports `buildBarrelFreeTree` from
`./docgen`. Split `codegen/core` into three tiers:

| file | holds | imports |
| --- | --- | --- |
| `barrel-free-tree.ts` (new) | `buildBarrelFreeTree` (moved out of `docgen.ts`) | — |
| `slot-declaration-guard.ts` | unchanged | `./barrel-free-tree` |
| `enriched-tree.ts` (new) | `buildEnrichedTree` (moved out of `docgen.ts`) | `./slot-declaration-guard` |

`docgen.ts` and the five other `./docgen` tree importers (`reorderable-slots-gen`,
`config-origin-gen`, `plugin-registry-gen`, `data-views-gen`,
`token-group-vars-gen`) re-point their imports. `codegen/core/index.ts` keeps
exporting both names, so nothing outside the plugin moves. Keep the function
names; the module layout is what makes the order readable.

### 2. Make reading contributions too early loud

Rung 4 for the whole class, not just docgen. Add to
`plugins/framework/plugins/slot-declaration/core/declaration.ts` (+ its barrel) a
counter-backed read — a count, not `lastOwners.size > 0`, so a legitimately empty
pass is not misread as "never ran":

```ts
let passes = 0; // incremented in declarePluginSlots
export function slotDeclarationPasses(): number { return passes; }
```

Then in the contributions facet
(`plugins/plugin-meta/plugins/facets/plugins/contributions/facet/index.ts`), at
the top of the runtime block: if `importedModules.length > 0` and
`slotDeclarationPasses() === 0`, throw naming the cause — barrels are imported
but no slot-declaration pass has run, so any plugin whose `contributions` are
derived from the declaration reads as empty. Today that mistake produces a
slightly smaller doc, which is indistinguishable from a correct one; that is what
let this ship.

`skipBarrelImport` builds pass no modules, so they are unaffected. The browser
never runs facets. No current caller trips it once step 1 lands.

### 3. Tests

- Existing: `./singularity test plugins/framework/plugins/tooling/plugins/codegen`
  must stay green.
- New (small, bun:test): the guard in step 2 throws when handed a fake
  `importedModules` entry in a process where no pass has run. Put it beside the
  facet; if the collected-dir loader objects to a sibling `*.test.ts`, drop the
  test rather than restructure the facet — the check itself is the real regression
  test.

## Verification

1. `./singularity check plugins-doc-in-sync` — the source change gives a fresh
   tree hash, so this is a real run, not a cache hit. Expect `ok`. Re-run with
   `SINGULARITY_CHECK_NO_CACHE=1` to confirm repeatability.
2. `git diff --stat docs/` after `./singularity build` — must be **empty**. The
   fix must not rewrite a single byte of `docs/plugins-details.md` /
   `plugins-compact.md` / any `CLAUDE.md` AUTOGEN block.
3. `./singularity check` (full, `SINGULARITY_CHECK_NO_CACHE=1`) — everything
   green, including `page-editor:*` (the other `buildEnrichedTree` consumer) and
   `config-v2:registrations-paired` (the descriptor-set pairing the declaration
   pass feeds).
4. Sanity on the real blocker: rebase `claude-web/att-1786989598-wcnd` onto this
   and confirm `./singularity push` gets past checks.
5. `./singularity build` and confirm the app boots at
   `http://att-1786998115-pp70.localhost:9000` — reorder middleware is on every
   slot, so a broken declaration pass would be immediately visible.

No cache purge is needed: after the fix the check produces the committed content
for the trees that hold recorded passes, so those entries are correct.

**Cost:** ~+10s in a process that has no barrel-free tree yet (the pass builds one
to compute the disabled set) — measured 13s → 23s for a lone doc render. Zero in a
build, where the tree is already memoized.

## Out of scope (follow-ups to file)

- **Build runs checks in-process.** A build's ✓ can be earned in a process
  contaminated by codegen and is then written to the cache `push` trusts. Running
  checks in a subprocess would have failed the very first push after `fa7e865e0`,
  one commit from the cause. Bigger change, on the build's hot path.
- **240 information-free doc lines.** `reorder`'s web entries render as identical
  `ConfigV2.WebRegister` rows with no id or label, unlike the server side's
  `ConfigV2.Register "conversation.header"`. Either collapse repeats or print each
  id — both rewrite generated bytes, so they do not belong in a change whose point
  is that the bytes stay identical.
- **`inputKeyed` and impure checks.** The read-set cache path
  (`runner.ts:293`, used by `type-check` and `no-raw-event-source`) lets a pass
  survive into later trees. A check that is not a pure function of the tree must
  never be moved onto it — worth stating wherever that contract is documented.
