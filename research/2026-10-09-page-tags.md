# Page tags

## Context

Agents mark a page's state by hand-writing a prefix into its title:
`[In progress] Cold start performance`, `[Planned] …`, `[Done] …`, `[Parked] …`
(10 live pages on main, 4 distinct values). The prefix is prose, so nothing can
filter, group or recolor by it; it drifts in spelling; and an agent can only
change it on a page it may rename (an agent page) — a human's track page stays
stale.

Outcome: a **tag** is a first-class page property. A page carries an ordered set
of tags drawn from one **workspace vocabulary** (name + color). Agents read and
write a page's tags through the `<page-meta>` header `read_page` already emits
(its design reserved exactly this: "a future WRITABLE field (tags) is read off
`splitPageMeta`'s `meta` by the caller that owns it"). Humans see chips under the
title, a marker in the sidebar, chips on sub-page/link rows, and edit them with a
picker. Existing bracket prefixes are migrated into tags.

## Decision: a shared vocabulary, open to deliberate growth

Closed list? **Neither closed-in-code nor free-form.**

- Closed in code (a `core/` enum) would need a code change + push for every new
  status — the opposite of what agents need.
- Free-form strings drift (`In progress` / `in-progress` / `WIP` / `Ongoing`),
  which is precisely the failure tags exist to fix.

So the vocabulary is **data** (a DB table, managed in the UI), and writing a tag
**resolves against it**:

1. A name matching an existing tag (case- and whitespace-insensitive) resolves to
   it and is stored under its canonical spelling.
2. An unknown name is **refused** (nothing written) with the vocabulary and the
   closest names listed — the typo/synonym guard.
3. To create one, the agent says so explicitly: `<tag name="Blocked" new="true"/>`
   (optional `color="red"`, else a deterministic color from the name). Same
   two-step a human does in the picker ("Create “Blocked”").

Creation is one deliberate attribute, not a separate tool and not a code change.

## Agent surface: the `<page-meta>` header

```
<page-meta created="…" edited="…">
  <tags>
    <tag name="In progress"/>
  </tags>                         ← `<tags/>` when the page has none
  <breadcrumb>…</breadcrumb>
  <backlinks>…</backlinks>
</page-meta>
```

- `tags` comes first: it is the one writable section.
- **Write**: `edit_page` compares the edited header's tag list with the one it
  read. If it differs, the new list (order kept, duplicates collapsed) is
  resolved per the rules above and written to the page holding the scope root —
  on ANY page, human or agent: tags are metadata, not the author's prose.
  Unknown name without `new` → 400 before anything is written (content apply
  included). Tag write runs AFTER a successful content apply, so a refused
  content edit writes no tags. Result carries `tags_set: [...]` (and
  `tags_created: [...]`). Other header fields stay read-only (`page_meta_ignored`
  only when a NON-tag part changed).
- `markdown-apply/core/page-meta.ts` stays semantics-free: it emits/parses
  `tags: {name, attrs}` (`PageMeta.tags`, `ParsedPageMeta.tags`); the server's
  `loadPageMeta` fills it from `page/tags`. `agent-access` owns the write, as it
  owns the rename.
- `read_page` / `edit_page` descriptions document it, and say **status belongs in
  tags, never in a `[…]` title prefix**. An agent-page rename whose new title
  starts with `[X] ` is refused with that pointer (the one place an agent can
  still write a prefix).

## Data model — new plugin `plugins/page/plugins/tags` (`page.tags`)

- `page_tags` — the vocabulary: `id` (`tag-<uuid>`, a `defineIdKind`), `name`
  (unique on its normalized key), `color` (`TagColor` = editor's `ColorToken`
  minus `default`), `created_at`.
- `page_blocks_ext_tags` — one row per tagged page (entity-extension shape, PK
  `parent_id` → `page_blocks.id` ON DELETE CASCADE), `tag_ids` jsonb string
  array, ordered. No row ⇔ no tags (writing `[]` deletes the row).
- Live: `pageTagVocabulary` (`all`, unbounded: the vocabulary is user-curated and
  small) and `pageTagAssignments` (`all`, unbounded: one row per TAGGED page,
  ≤ pages.tree which is already whole-set). Change-feed invalidates both.
- Endpoints: `PUT /api/pages/:pageId/tags {tagIds}`, `POST /api/page-tags
  {name, color?}`, `PATCH /api/page-tags/:id {name?, color?}`,
  `DELETE /api/page-tags/:id` (removes the id from every page's array in the
  same transaction).
- Server API (barrel): `loadPageTagNames(pageId, executor)`,
  `resolveTagNames(names, {allowCreate})` → result union
  (`ok` | `unknown` with suggestions), `setPageTags(pageId, tagIds)`.
- Stored in a side table, not `PageData`: the feature is removable as a plugin,
  the editor core learns nothing, and history restore does not roll status back.

## UI (shape fixed by the mock `proto-1790691924-p8nh`)

- Header: `PageDetail.UnderTitle` contribution — chip row + `+`; picker popover
  (search/create, colored list, check on assigned, per-tag rename/color/delete).
  No tags → an "Add tag" entry in `PageDetail.HeaderTool` (the hover row with Add
  icon/cover), so an untagged page shows nothing.
- Sidebar: `PageTree.Fields` `tags` field (filter/group in the sidebar DataView
  for free) + the row marker the mock picks.
- Sub-page / link rows: new additive `PageReference.Trailing` render slot in
  `page/page-reference` (not `Decoration`, which is single-winner), rendered by
  `sub-page-block` and `page-link-block`; `page/tags` contributes chips.
- Chip colors: tints of the `--rt-color-*` palette tokens via `color-mix`.

## Migration

One data migration (`./singularity build --custom-migration --migration-name
page_tags_from_title_prefix`), claimed by the schema migration that creates the
two tables (expand → data → contract, one push): insert one vocabulary row per
distinct `^\[(.+?)\]\s*` prefix of a live page title (In progress → blue,
Planned → purple, Done → green, Parked → yellow, else gray), insert each page's
assignment, strip the prefix from `data.title`. Pure DML, idempotent by its
`WHERE` (only titles still carrying a prefix).
